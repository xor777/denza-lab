# HUD surfaces probe

Одноразовый пробник для одного короткого парковочного прогона. Отвечает на
четыре открытых вопроса [архитектуры вывода на HUD](../../docs/hud-output-architecture.md#текущее-состояние):

1. Рисует ли HUD этой машины штатные поля камер **без навигации** (поле 16 = 1)?
2. …и **с навигацией** (16 = 2) при заполненном блоке манёвра?
3. Можно ли без маршрута включить навигацию только на время предупреждения,
   заполнив блок манёвра самим предупреждением, и гаснет ли всё без следа?
4. Что на стекле, когда одна SOME/IP-сессия замолкает (без очистки), а другая
   начинает писать?

Один экран, по кнопке на сценарий и «Сбросить HUD». Каждый сценарий — заранее
заданный список шагов (`Plans.java`), сам заканчивается сбросом и коротким
окном «смотрите, не осталось ли следа». Каждый пакет пишется в лог с полями и
ответом службы: `adb logcat -s DenzaHudSurfaces`. Ответ `ret=0` доказывает
только, что пакет принят службой на IVI, а не что он виден на стекле: виденное
записывает владелец по чек-листу ниже.

Пробник обычного UID, без разрешений. Не пишет настроек машины, ADAS и
штатного знака, не транслирует видео, не трогает Denza Apps и YandexHUD.

### Поля камер в road-пакете `0x8001`

Номера и типы — из схемы штатного отправителя
(`LM/someip/hud/navi/info/service/SomeipHudNaviInfoService.java:811-839`; в
описании сообщения `:2028` все шесть полей — `uint32`). Значения — из того, как
их заполняет штатный навигатор (`PlatformHudImpl`, `LM/k/e/j/d.java`).

| Поле | Имя | Что пишет штатный отправитель | Откуда |
|---|---|---|---|
| 13 | `distance2SpeedLimitZone` | метры, уже пройденные по участку контроля средней скорости: длина участка минус остаток | `d.java:275-280` ← `NaviService.onUpdateIntervalCameraDynamicInfo`, `LM/com/autosdk/drive/navi/NaviService.java:972-974` |
| 14 | `lengthOfSpeedLimit` | длина участка, м | `d.java:275-280` |
| 15 | `speedLimit` | лимит участка: наибольшая допустимая скорость камер участка, кроме 0 и 255 | `LM/com/autosdk/drive/logic/NaviCameraHelper.java:251-270` |
| 17 | `cameraAheadStatus` | **только `1`** (камера впереди) или `0`; тип камеры в HUD не уходит | `NaviService.java:871-880` → `LM/k/e/j/g/e.java:260` → `d.java:226-229` |
| 18 | `theDistance2Camera` | метры до ближайшей камеры | `NaviCameraHelper.java:272-310` (ближайшая группа) |
| 23 | `dangerSigns` | `NaviRoadFacility.type`, тип дорожного объекта AutoNavi (3 крутой поворот, 6 зона аварий, 17 школа, 30 «внимание, опасность», …); держится до общей очистки | `NaviService.java:883-893` → `d.java:412-415`; `LM/com/autonavi/gbl/common/path/model/FacilityType.java`; сброс только в `d.java:283-322` |
| 11 | `currentMaxSpeedLimit` | наименьший из лимитов дороги, камеры и участка | `LM/com/autosdk/bussiness/vehicle/BydAutoSpeed.java:316` |

Главное: **штатный отправитель никогда не шлёт поля камер без навигации.**
Цикл road-пакета (каждые 100 мс, `e.java:155-178`) запускается в `onNavStart` /
`onNaviSimStart` (`e.java:84-103`, `P()` `:340-364`) и гасится в `onNavStop`
очисткой и stop (`e.java:380-386`, `d.java:283-322`). Камеры режима без
маршрута (круиз) идут только в лимит скорости, не в HUD-пакет
(`LM/com/autosdk/map/cruise/SpeedAndCruiseManager.java:262-273`). Поэтому
сценарий 1 спрашивает о том, чего штатный навигатор не делает: «нет» ожидаемо,
«да» — подарок.

**Открытый проект-образец** (локальная рабочая копия на 2026-10-18) пробует
те же поля road-пакета: 17–18 = `1 · 120 m`, 23 = `1`
(`HudCheckState.java:68-69`, `HudCheckPayload.java:227-231`). Это совпадает со
штатной формой; проект называет поле 17 «типом камеры», но штатный
отправитель пишет туда только 0/1, поэтому пробник шлёт `1`. Отдельные топики
проекта — «TrafficInfo f9–10» и «Matrix navigation action / camera»
(`HudCheckState.java:80-83`, `HudCheckPayload.java:17-27`, `:96-110`,
`:281-311`) — это штатные `NAVIGATION_STATUS_LINK_INFO_SERVICE_EVENT_TRAFFIC_INFO_NOTIFY`
(служба 7) и `SD_MAP_INFORM_SERVICE_EVENT_NAVI_ACTION_AND_CAMERA_NOTIFY` (служба
`0x8202`) (`LM/ts/car/someip/plugin/SomeIpTopic.java:327-329`, `:397`, `:409`).
Штатно их шлёт `SomeIPMatrixManager` из пакета пилота
(`LM/k/h/a0/c/c/a/f0.java:84`, `:212`; импорт
`com.autosdk.bussiness.pilot.someip`). **В пробник они не включены:**

- IVI предлагает службы 7, 266 и 33282 (`0x8202`)
  (`captures/hud-firmware-20260923/system/system/etc/someip/someip_stack.json`,
  `services`), а FSE — хост HUD на этой машине — из них подписан только на 266
  (`captures/fse-firmware-20260924/system/system/etc/someip/someip_stack.json`,
  `clients`). Получатель служб 7 и `0x8202` — домен вождения, не HUD.
- Пробник не должен писать камеру и лимит во входы вычислителя вождения — то же
  правило, что «никаких ADAS-сеттеров».

Если сценарии 1–2 ничего не покажут, эти топики остаются отдельным вопросом:
сначала прочитать образ, кто их потребляет, потом решать.

### Сессии службы SOME/IP

Вопрос: может ли одно приложение открыть две сессии с двумя типами. **Да**, и
для службы они неотличимы от двух приложений:

- `onBind` создаёт binder на каждый интент, uuid сессии = тип интента
  (`SIP/com/ts/car/someip/service/manager/SomeIpServerService.java:135-138`,
  `:413-415`). Android привязывает отдельно каждый различный интент:
  `Intent.filterEquals` сравнивает тип (`FW/framework/sources/android/content/Intent.java:8555-8563`),
  привязка ищется по `Intent.FilterComparison`
  (`FW/services/sources/com/android/server/am/ServiceRecord.java:823-824`).
  UID вызывающего служба не проверяет нигде.
- `startSomeIpService` (`:463-488`): первая сессия запускает службу в HAL
  (обычно 0), любая следующая входит в набор и получает `13`.
- `stopSomeIpService` (`:501-538`, jadx показал байткод): убирает свой uuid;
  HAL останавливает службу, только когда набор опустел, иначе ответ 0.
- `onUnbind` (`:140-176`): убирает все записи с этим типом, при пустом наборе —
  stop в HAL. Так уходит и умерший процесс.
- `fireEvent` (`:550-557`) сессию не смотрит вовсе: пакет любого binder идёт
  через одного клиента HAL (`SIP/.../SomeIpServerManagerImpl.java:309-322`,
  один `mProxyHandle`). На проводе одно предложение службы 266; сессии
  различаются только тем, когда оно появляется и снимается.

Поэтому сценарий 4 пробник гонит сам: сессия A — тип `dev.denza.hudsurfaces.probe`,
B — `dev.denza.hudsurfaces.probe.b` (`SessionId.java`). Ручная процедура с двумя
приложениями ничего не добавила бы.

<a id="сценарии"></a>
## Пакеты и сценарии

Road-пакет — `HudRoadInfo_EG{1: HudRoadInfoNotifyStruct}`; поле 2 = 2 и поле 16
всегда первыми, остальные по возрастанию (`SurfacePackets.java`). Карта —
`HudNavigationmap{1: Base64 PNG}` без конверта. Пакеты идут 2 раза в секунду;
фаза — 10 пакетов, 5 с. Картинки (`ProbeArt.java`): манёвр 80×80 на прозрачном,
карта 300×180 непрозрачная.

**Сброс R** (конец каждого сценария и кнопка): три раза через 120 мс — чёрный
кадр карты 300×180 и `{2=2 16=1}`; через 350 мс после первого — stop (сначала
прочие сессии, последним тот, кто очищал, — его stop снимает предложение),
затем unbind всех. Как `HudSession` в `:hud-link`. После R — 3 с наблюдения
(в сценарии 3 — 5 с).

### 1 · Камеры без навигации (`cameras-off`, 23,4 с)

Открыть A (ожидается 0 или 13), четыре фазы, R.

| Фаза | Поля каждого пакета |
|---|---|
| Камера | `2=2 16=1 17=1 18=300…210` |
| Камера и лимит 60 | `2=2 16=1 11=60 17=1 18=300…210` |
| Участок средней скорости | `2=2 16=1 13=200…380 14=2000 15=60` |
| Опасность | `2=2 16=1 23=30` |

Метры убывают на 10 за пакет, пройденное по участку растёт на 20. Окно карты
не открывается (16 = 1), кадров карты нет.

### 2 · Камеры с навигацией (`cameras-on`, 23,4 с)

Те же четыре фазы, но каждый пакет — навигация с полным блоком манёвра:
`16=2 8=стрелка 80×80 9=800 10="ПРОБА" 26="5,0 км" 27="10 мин" 28=11` плюс
поля камер фазы. Кадров карты нет: окно карты после R предыдущего сценария
чёрное.

### 3 · Камера в блоке манёвра (`warning`, 18,4 с)

Вариант B из [раздела 8 архитектуры](../../docs/hud-output-architecture.md#hud-out-scenarios).

1. «Исходное», 3 с: сессии нет.
2. Открыть A; 20 пакетов, 10 с:
   `2=2 16=2 8=значок камеры 80×80 9=300…110 10="60" 28=11`. Полей 26/27 нет,
   штатных полей камер (11, 13–18, 23) нет, карты нет.
3. R; «После очистки», 5 с.

Почему 28 = 11: штатная таблица переводит «прямо» AutoNavi (9) в 11
(`LM/k/e/j/e/b.java:5`). На этой машине поле 28 выбирает стрелку AR
([instrument-display-findings](../../docs/instrument-display-findings.md#hud-turn-by-turn-guidance),
2026-09-03), и «прямо» — единственная, что не обещает поворот. Связка 28 = 11
со своей картинкой в поле 8 уже видна на стекле этой машины
([moving-frames](../../docs/hud-projection-findings.md#hud-moving-frames),
[полосы](../../docs/hud-projection-findings.md#hud-native-lanes): маркер в поле 8
при 28 = 11). Штатный 0 (AutoNavi «нет манёвра») на стекле не проверен и
штатно идёт до первого манёвра — как раз когда блок пуст.

Компоновщик `:hud-link` такой пакет считает навигацией: в нём есть поле 9
(`HudRole.fillsNavigation`).

### 4а · Передача: A замолкает (`handover-quiet`, 23,4 с)

| Фаза | Что идёт |
|---|---|
| A пишет, 5 с | открыть A (0 или 13); 10 × [road A, карта A] |
| A молчит, 5 с | ничего; A не очищает, не останавливается |
| B без карты, 5 с | открыть B (ожидается 13: A ещё держит службу); 10 × road B |
| B с картой, 5 с | 10 × [road B, карта B] |
| R через B | stop A, stop B, unbind обоих |

Road A: `2=2 16=2 8=«A» 9=100 10="СЕССИЯ A" 26="1,0 км" 27="1 мин" 28=11`,
карта A — голубая «A». Road B: `9=200 10="СЕССИЯ B" 26="2,0 км" 27="2 мин"`,
розовая «B». Каждое читаемое поле называет свою сессию.

### 4б · Передача: A уходит (`handover-gap`, 23,4 с)

Как 4а, но вместо «A молчит»: stop A **без очистки** и unbind A — так
выглядит смерть хоста (обновление, запрет фоновой работы, падение; по коду
`onUnbind` даёт тот же stop). Если A держал службу один (open A = 0), служба
снимает предложение 266. Затем «A ушёл», 5 с; открыть B (ожидается 0 —
служба запускается заново); B без карты; B с картой; R через B.

Если open A ответил 13, службу держит кто-то ещё (Denza Apps с маршрутом или
другой пробник), предложение не снимется, и 4б повторит 4а. Записать это и не
бороться: повторить 4б позже без маршрута.

<a id="исход"></a>
## Что значит исход

| Наблюдение | Значит для [hud-output-architecture.md](../../docs/hud-output-architecture.md) |
|---|---|
| 1: в фазе «Камера» или «Камера и лимит» виден значок камеры / метры / знак | Вариант A жив: без маршрута камера идёт штатными полями без навигации; строка «Без маршрута, только камера, вариант A» ([8](../../docs/hud-output-architecture.md#hud-out-scenarios)) |
| 1: ничего ни в одной фазе | Вариант A на этой машине невозможен (как и у штатного отправителя): без маршрута — только вариант B |
| 1: знак только в фазе с 11 | Рисуется поле 11, не камера; отдельный факт о поле 11 без навигации |
| 2: значок камеры / участок / опасность видны | В строке «Маршрут, карта, камера» камера идёт штатными полями; плашка z 300 не обязательна ([3.5](../../docs/hud-output-architecture.md#hud-out-placement)) |
| 2: не видны | Камера при маршруте — только плашка z 300 в углу карты |
| 3: значок, метры и «60» видны, китайских подписей нет, после R чисто | Вариант B принят: 8/9/10 + 28 = 11, 26/27 пустые |
| 3: китайские подписи (записать, где) | Пустые 26/27 HUD заполняет сам: вариант B требует их заполнить; повторить с текстом в 26/27 |
| 3: что-то осталось после R | Очистка из [3.4](../../docs/hud-output-architecture.md#hud-out-modes) недостаточна; до варианта B её менять |
| 4а «A молчит»: «A» держится все 5 с | HUD сам старое не гасит: компоновщик не может полагаться на HUD, когда источник умер; передача без мигания возможна |
| 4а «A молчит»: «A» гаснет через N с | У HUD свой срок N с: разрыв передачи дольше N мигнёт |
| 4а «B без карты»: голубая карта «A» осталась | При передаче нужен чёрный кадр карты (или свой кадр нового писателя) — правка [5](../../docs/hud-output-architecture.md#hud-out-handshake), п. 4 «очистку при передаче не шлём» |
| 4а «B без карты»: окно карты пустое | Чёрный кадр при передаче не нужен |
| 4б «A ушёл»: картинка A осталась | Умерший писатель оставляет след: тот, кто подхватывает, сначала шлёт очистку / чёрный кадр |
| 4б «A ушёл»: стекло очистилось само | HUD чистит при снятии предложения; при смерти хоста очистка не нужна |
| 4б «B без карты»: карта «A» вернулась | Кадр карты переживает снятие предложения: чёрный кадр нужен при каждом новом старте службы |

## Сборка, установка, запуск, остановка

```sh
export JAVA_HOME=/opt/homebrew/opt/openjdk@17/libexec/openjdk.jdk/Contents/Home
export ANDROID_HOME=/opt/homebrew/share/android-commandlinetools
./gradlew -Pexperiments :hud-surfaces-probe:testDebugUnitTest :hud-surfaces-probe:assembleDebug
APK=experiments/hud-surfaces-probe/build/outputs/apk/debug/hud-surfaces-probe.apk
shasum -a 256 "$APK"                       # записать: хеш ставленной сборки

adb -s 127.0.0.1:5555 install -r "$APK"
mkdir -p captures/hud-surfaces-$(date +%Y%m%d)
adb -s 127.0.0.1:5555 logcat -c
adb -s 127.0.0.1:5555 logcat -s DenzaHudSurfaces | tee captures/hud-surfaces-$(date +%Y%m%d)/probe.log

# Экран с кнопками:
adb -s 127.0.0.1:5555 shell am start -n dev.denza.hudsurfaces.probe/.SurfacesActivity
# Или сценарий с хоста (id: cameras-off, cameras-on, warning, handover-quiet, handover-gap, reset):
adb -s 127.0.0.1:5555 shell am start -n dev.denza.hudsurfaces.probe/.SurfacesActivity --es scenario cameras-off

# В конце:
adb -s 127.0.0.1:5555 uninstall dev.denza.hudsurfaces.probe
```

Лог: одна строка на шаг. `open A type=… start ret=0 (ожидается: …)`,
`#12 +5530ms A road ret=0 {2=2 16=1 11=60 17=1 18=290}`,
`#13 +5530ms B map ret=0 {1=base64:png300x180/1234B}`, `stop A ret=0 (…)`,
`unbind B …`, `phase «…» 5000 ms: …`, итог `scenario … done: N fired, M not
accepted`.

<a id="сброс"></a>
## Сброс

- «Сбросить HUD» во время сценария обрывает его и шлёт R через сессию, писавшую
  последней (B, если она запущена, иначе A). Если службу не держит ни одна —
  например, в 4б между уходом A и стартом B, — R идёт через новую сессию A,
  открытую только для этого. Без сценария кнопка открывает A только ради R.
- Уход с экрана (Back) тоже обрывает сценарий с R.
- Не делать force-stop во время сценария: R не уйдёт. Если процесс умер —
  открыть пробник и нажать «Сбросить HUD».
- R не меняет никаких постоянных настроек. Чужую сессию он не трогает: если
  службу держит ещё кто-то, stop последней нашей сессии предложение не снимает.

## Чек-лист владельца

Перед прогоном (один человек владеет сессией, [governance](../../docs/governance.md)):

- [ ] P, скорость 0, HUD включён; ни в одном навигаторе нет маршрута; другие
      HUD-пробники не запущены.
- [ ] Записан SHA-256 ставленного APK; `logcat -s DenzaHudSurfaces` пишется в
      `captures/hud-surfaces-<дата>/`.
- [ ] «Сбросить HUD»: в логе `open A … ret=0` (или 13 — записать), 6 пакетов
      `ret=0`, `stop`, `unbind`. На стекле только штатная скорость.

Во время прогона — смотреть на стекло, фазу и подсказку читать на экране.
Снимать стекло на телефон по фазам.

- [ ] **1 · Камеры без навигации.** По фазам: Камера ___; Камера и лимит ___;
      Участок ___; Опасность ___ (значок камеры / метры / знак / полоса /
      значок опасности / ничего). После сброса чисто? ___

<a id="ограничения"></a>
## Чего прогон не покажет

- Только парковка: в движении HUD может вести себя иначе.
- Поле 17 только = 1, как у штатного отправителя; другие значения не штатные и
  не проверяются. Поле 23 — одно значение (30); другой тип объекта может
  рисоваться иначе или не рисоваться.
- Значения участка 13–15 правдоподобные, но выдуманные.
- Что рисует сам HUD (контроллер за FSE), в корпусе не разобрано: его образа
  нет, поэтому показ полей 13–18/23 из прошивки не вывести — только прогоном.
- 4б имитирует смерть хоста явным stop; настоящая смерть идёт через `onUnbind`,
  по коду с тем же итогом (`SomeIpServerService.java:140-176` против
  `:501-538`), но живьём это не то же самое.
