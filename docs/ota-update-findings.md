## Устройство

`OTAUpdatePlatformizedUI` (`com.byd.otaupdate`) содержит основной контроллер,
GCY-клиент и SDK, к которому подключены настройки машины и `OTAUpdate2`.
При пустом `persist.sys.ota.platform` фабрика выбирает
`PlanGcyAndGhyPlatform`; на машине свойство пустое, обе службы работают.

Для серии `denza` обычные адреса из конструкторов сетевых клиентов:

- GCY: `https://fota-tsp.denzacloud.com:6113/ota/otaService/…`.
- GHY: `https://api-ota-cn.denzacloud.com/client-service/fota/api/v1/service/…`.

Это адреса нормальной конфигурации данной прошивки. Код также содержит
отдельные bench/test-переключатели. Увиденные запросы сообщали
`isBentch=false`; полная URL-строка в выбранные журналы не выводилась.

Клиент использует TLS-идентичность и токен. Для входа он формирует VIN,
ICCID, UUID проверки и код страны. Дальше штатный путь получает `getEcuList`,
опрашивает версии контроллеров, отправляет `versionSync`, затем `checkVersion`
с версией автомобиля и данными ECU. При наличии пакета следует отдельный путь
загрузки и установки. Эта проверка не подтверждает работоспособность установки.

GCY передаёт часть работы GHY: в наблюдаемом проходе GHY выполнял `lockSync`
и `getNeedCheckEcuList`. Список сервера содержит кандидатов и варианты ECU,
а не гарантированно установленные блоки. Проценты вычисляются по обходу
списка и повторным попыткам. Опрос активный, включает штатные диагностические
запросы; его нельзя выдавать за пассивное чтение кэша.

## Экран и ошибки

В обоих клиентах `CheckVersionDownloadPresenter` вызывает
`carsettingDisplay.setLatestUi()` также при сбоях входа и `getEcuList`.
В GCY такой же вызов есть при ошибке `checkVersion`. Обёртка меняет экран
только при `isNeedShowSettingUI=true`; `CarSettingDisplayUtil.setLatestUi()`
передаёт в SDK тип отображения 0.

Поэтому надпись «Latest version installed» не доказывает успешного обмена.
Нужно сопоставлять её с ответом на конкретный запрос. Коды ниже — поле
`status` в JSON приложения, **не HTTP-коды**:

| Код | Значение в клиенте |
| --- | --- |
| `100` | Запрос успешен |
| `102` | Автомобиль не входит в партию обновления |
| `104` | Текущая версия последняя |
| `111` | Нет версии для обновления |
| `113` | VIN не существует в серверной базе |
| `117` | VIN привязан к другому ICCID |
| `101` / `114` | Нужен вход / регистрация |

Ошибки DNS, подключения, TLS и HTTP идут отдельными исключениями.
Само отсутствие новой версии не доказывает ни региональную блокировку,
ни неисправность соединения.

для других автомобилей или возможность её установки вручную. `104` в

## Стратегия OTA и кэш ProductLineOTA (2026-10-21)

Стратегия — рабочий план обновления. Модель `VehicleVersionInfo` содержит
`strategy`, `targetPackageInfo`, `sourcePackageInfo`, `configPackageInfo` и
`configSourceInfo`. Внутри стратегии есть партия и версия стратегии, порядок
обработки ECU (`sequence`), зависимости отката, флаг принудительного обновления
и условия по заряду, напряжению и температуре. Описание отдельного ECU
`ecuDescription` находится в метаданных пакета; поэтому этот источник также
интересен для установления назначения диагностических блоков.

Клиенты сохраняют объект в `strategy.json`, затем читают для продолжения
своего процесса загрузки/обновления. Это не словарь DTC и не независимый
переключатель права автомобиля на новую прошивку. Простое чтение файла не
запускает обновление и не меняет серверную стратегию; изменение файла уже
может повлиять на локальную работу клиента.

**Новый путь относится к другому клиенту.** ProductLineOTA имеет собственный
пакет и заводской процесс с `ManufactureConfig`, `validTime`, `upgradeType`,
проверкой ключа и этапами IPB. Его кэш нельзя считать сохранённым ответом
обычного GCY/GHY только из-за одинакового имени файла. Для текущего
`ro.vehicle.type=DiLink150_7.0UI` разрешённый исходниками путь:
`/data/ota_package/ota_productline/result/strategy.json`. Ранее проверялись
`ota_ghy/result/strategy.json` и `ota/result/strategy.json`.

Писатель ProductLineOTA пытается выставить `775` каталогу результата и `666`
файлу, но не меняет права предков. Проверка 21 октября прочитала только
свойство платформы и метаданные путей: `stat` получил `Permission denied`
начиная с `/data/ota_package`, `test -r` вернул отказ. Это не результат
«файла нет». Содержимое не читалось; BydLogTool, проверка версий, загрузка,
установка и изменение разрешений не запускались. Источники и результаты:
[`ecu-description-cache-lead-20261021.json`](../research/vehicle-diagnostics/ecu-description-cache-lead-20261021.json).

**Что это даёт для ошибки 111.** Сохранённый ответ 18 октября прямо сообщает
о несовпадении запрошенных ECU с деталями стратегии на сервере. При этом
`sequence` и все четыре массива пакетов пусты: сравнивать с фактическим
серверным списком ожидаемых версий пока нечего. Ответ не указывает виновный
блок, а наличие текстов изменений в предыдущем `versionSync=104` не доказывает,
что сервер предлагает этой машине новую версию.

Обычный GCY строит `checkVersion` из версии автомобиля, UUID, `encType` и
шести полей каждой записи ECU. Локальный `strategy.json` в этот запрос не
включается. Оба вызова — `versionSync` и `checkVersion` — используют
`getCurrentVehicleVersion()`, читающий `/collect2/SourceVehicleVersion2`.
Сохранённое там `V1.7.0` согласуется с этим путём. `VehicleVersion2`, где
сохранено `V1.0`, обслуживается другим getter и само по себе не доказывает
неверную версию в запросе.

Сохранённый `ECUVersion.json` по структуре соответствует данным запроса:
225 разных идентификаторов, 176 ненулевых кодов ПО, 23 нулевых значения и
26 маркеров `7F22`. В исходниках кэш пишется перед запросом, но возраст
полученной копии не установлен: это не гарантированная копия тела именно
запроса 18 октября. Нули и `7F22` могут относиться к отсутствующим вариантам
оборудования; их нельзя объявлять причиной отказа или заменять выдуманными
версиями. Разбор, точные поля и хеши:
[`ota-strategy-mismatch-20261021.json`](../research/vehicle-diagnostics/ota-strategy-mismatch-20261021.json).

Следующий содержательный вопрос — какой набор ECU/версий реально был
отправлен и какой набор ожидала назначенная сервером стратегия. Найденный
заводской кэш может дать дополнительные имена и зависимости, если он
существует, но способ получения нового пакета этим ещё не установлен.
Повторных обращений к серверу и изменения стратегии в этом исследовании нет.

### Происхождение версий ECU в запросе

Ограниченный разбор `DiagnosePresenter` показал конкретную подстановку, которую
нельзя отличить по одному `ECUVersion.json`. Сначала клиент копирует все записи
серверного списка и сбрасывает их поля в значения по умолчанию, затем выполняет
диагностику. Перед возвратом результата он вызывает
`adjustEcuResultListInfoAfterDiagnosing()`. Для версии ПО `0.00.00` или `6.55.35`,
кроме Media и служебной записи MCU, метод ищет тот же `ecuId` в сохранённой
истории `repairUpgradeEcuListInfo`. Если там `isRepairEcu=1`, он подставляет
`ecuSoftCode` из истории и `ecuSoftVer` из её `ecuOriginSVer`. Аппаратная версия
и поля конфигурации в этом блоке не заменяются.

Внутренний флаг `isRepairEcu` при этом устанавливается, но в шесть полей запроса
не входит. Поэтому запись может содержать сведения разного происхождения, а
кэш не доказывает, что каждое поле только что пришло от ECU. В сохранённой
проекции остались 23 версии `0.00.00`, ни одной `6.55.35` и 26 маркеров `7F22`;
это значения после обработки, не число подстановок. Сам `7F22` не входит в
два условия этой ветки. История ремонта не экспортирована, а в выбранных логах
нет строк подстановки; из-за набора тегов и перерыва наблюдения это не
доказательство отсутствия выполнения. Ветку подтвердили в исходниках,
но не установили её применение или связь с `111` на этой машине.

### Наследование плана и синхронизация с GHY

Две похожие идеи закрыты в пределах прослеженного пути. Во-первых, HTTP-обвязка
переводит прикладной статус, отличный от `100`, в ошибку до вызова `onSuccess`.
Поэтому `versionSync=104` не выполняет успешную запись пустого `latestVersion`
в `SourceVehicleVersion2`: обработчик ошибки продолжает `checkVersion` с обычным
getter текущей версии. Это согласуется с сохранённым `V1.7.0`.

Во-вторых, `isNeedDownloadCurrentVersion()` выбирает старую принудительную
стратегию только после успешного ответа и проверки корректности нового плана.
Ответ `111` до этой точки не доходит. Обработчик ошибки из настроек отправляет
координатору команду `NEED_DIAGNOSE`; в сохранённом instruction dump
`PlanGcyAndGhyPlatform` обработчик GCY явно пишет, что эта команда не включена.
В этой командной ветке переход к `checkVersion` другого backend после `111`
не реализован. Другие триггеры GHY существуют, но их запуск не был частью
этого исследования.

При этом утверждение «локальная стратегия не включается в `checkVersion`»
нельзя расширять до «она нигде не синхронизируется». GCY формирует отдельное
краткое описание сохранённого плана: партия, версия стратегии, дата, тексты,
зависимости отката и идентификаторы/версии целевых ECU. Он прикладывает его к
сообщениям состояния; у GHY есть обработчик, передающий такое описание в
`lockSync`. Это отличается от тела `checkVersion`. Тело того `lockSync` не
сохранено; успешный статус `100` подтверждает обмен, но не право на пакеты и
не причину последующего `111`. Промежуточный `dispatchPlatformStatus` не полностью
декомпилирован, поэтому цепочку нельзя выдавать за полностью воспроизведённый
runtime. Никаких изменений стратегии или повторных обменов не делалось.

Итог двух зацепок: происхождение части полей запроса может зависеть от истории,
но конкретный виновный ECU и ожидаемые сервером версии по имеющимся материалам
не определены; способ получить подходящий пакет не установлен. Следующий
решающий источник тот же — уже сохранённая применимая таблица ожидаемых
ECU/версий либо объяснение backend с полученными и ожидаемыми значениями.
Границы и дополнительные source anchors находятся в `boundedSourceLeads`
того же [`ota-strategy-mismatch-20261021.json`](../research/vehicle-diagnostics/ota-strategy-mismatch-20261021.json).
Офлайн-проверка хешей, строк исходников и проекций:
`python3 -B research/vehicle-diagnostics/check_ota_strategy_mismatch.py`.

## Обратный путь 111 и сохранность кэша

Офлайн-трассировка 21 октября установила действие, происходящее **до**
`CheckVersionDownloadPresenter.onFail()`. `HttpApiService` сначала журналирует
сырой ответ, затем читает только `status`. Для `111` он создаёт `ApiException`
с общим локализованным сообщением; серверное поле `cause` в исключение не
попадает. Retry-обвязка передаёт это прикладное исключение дальше, а
`BaseEntityObserver.onApiExceptionError()` для `102` и `111` вызывает
`VehicleOTAUtil.restoreFactorySettingsOfOTA()`.

Этот метод очищает download preferences, ставит задачу удаления файлов в
disk-очередь и скрывает доступность обновления. У GCY удаляется рабочее дерево
`/data/ota_package/ota/`, включая `result/strategy.json`; у GHY эквивалентный
обработчик удаляет `/data/ota_package/ota_ghy/`. Отдельные загруженные модульные
пакеты тоже включены в очистку. `ECUVersion.json` и `needCheckEcuList.json`
находятся уровнем выше и этим удалением дерева GCY не охватываются. Метод
не записывает `VehicleVersion2=V1.0`.

Это точная ветка исходников, но не наблюдение успешного удаления на машине:
соответствующие логи и состояние каталога до/после не сохранены. Нельзя
утверждать, что старый план существовал или что именно проверка в 14:43 его
удалила. Практическое следствие другое: повторная штатная проверка — плохой
первый шаг для сохранения прежнего плана, поскольку её отрицательный ответ
может очистить обычный кэш. При новом разрешённом исследовании уже имеющиеся
кэши надо сохранять до активной проверки.

Сохранившийся `needCheckEcuList.json` содержит локальный timestamp
`1792315088625`, то есть **18 октября 12:18:08.625 МСК**. Это время записи
данного ответа GHY, а не время `ECUVersion.json`. Наблюдаемые host mtime
экспорта — 14:19:22, до штатной проверки в 14:38; это вспомогательные
метаданные файловой системы, не подписанная дата источника. Поэтому прежний
экспорт с результатом `strategy.json: missing` нельзя обозначать как
состояние после конкретного `111` в 14:43. Возраст самих ECU-данных остаётся
неизвестным.

## Сравнение двух прошивок и кода Media

Оба локальных архива — разные компьютеры одной машины, IVI и FSE. Это не пара
«старая/новая версия всего автомобиля». Сохранённые составные версии в кэше
точно совпали с версиями в их именах; `metadata/post-outswver` независимо
подтверждает Android-часть каждой строки:

| Запись ECU | Android | MCU-часть составной версии |
| --- | --- | --- |
| `HTH-2021_Media_BYD_00200001` | `34.1.33.2605218.1` | `34.2.3.2605202.2` |
| `HTH-2021_ASSY_BYD_00100001` | `42.1.8.2605219.1` | `42.2.3.2605250.2` |

Для Media прослежено и формирование кода ПО. `MediaDiagnostic` собирает
версию из Android property и `getMcuVersion()`, а код выбирает через
`media_softcode_mapping.json`. В сохранённом MCU XCD код
`4B450011E0930034E2`; при `series=denza`, `fission=0` и `displayUser=0` или `1`
таблица возвращает **`4B450011E093003401`**, ровно как в `ECUVersion.json`.
Сохранённый IVI `build.prop` содержит `denza/0/0`. Это соответствие есть в
ресурсах всех трёх клиентов — GCY, GHY и ProductLineOTA. Подмена окончания
`01` на `E2` сломала бы штатное представление Media, а не исправила найденное
несовпадение.

В MCU-контейнере FSE есть `4B450011DF990042E2`, в составной записи ASSY —
`4B450011DF99004201`. Формирование составного FSE-кода здесь не прослежено;
правило Media нельзя автоматически переносить на него. Для ASSY подтверждено
совпадение семейства версий с архивом, а не правильность каждой части
серверного tuple. Совпадение двух медийных прошивок также не доказывает
соответствие остальных ECU назначенной стратегии.

## Конкретная запись для сравнения со стратегией

Вместо общего списка из 49 нулевых/отрицательных кодов выделилась одна точная
запись с заполненным основным ПО и особой конфигурацией:

| Поле `HTH-2021_F_ZCU_BYD_00100001` | Сохранённое значение |
| --- | --- |
| `ecuSoftCode` | `4B310011E001540100` |
| `ecuSoftVer` | `4.00.36` |
| `ecuHardVer` | `0.4.1` |
| `ecuConfigCode` | `FFFFFFFFFFFFFFFFFF` |
| `ecuConfigVer` | `6.55.35` |

Это единственный код конфигурации из девяти `FF` в 225 строках. Общий parser
версии читает два байта как unsigned integer, поэтому `FF FF` → `65535` →
`6.55.35`; это не отдельная ветка нумерации релизов. Parser кода отвергает
пустое значение и девять нулей, но пропускает девять `FF`. Конфигурационные
поля используют эти же parser-методы. Ранее найденная подстановка ремонтной
истории проверяет **основную** `ecuSoftVer`; `ecuConfigVer=6.55.35` эту ветку
не включает.

Так получен конкретный вопрос для ожидаемой серверной таблицы: должна ли
стратегия принимать именно `FFFFFFFFFFFFFFFFFF/6.55.35` при этом основном ПО
и аппаратной версии или ожидает другую конфигурацию переднего ZCU. Значения
похожи на незаполненную конфигурацию, но без ответа ожидаемой стратегии это
**не доказательство неисправного ECU или причины `111`**. Заменять их
предположительными значениями оснований нет.

Дополнительная проверка клиента уточняет механизм: в
`CanDiagnostic.isEcuConfigDiagnosisSuccess()` исключены нули и `7F22`, но не
девять `FF` и не `6.55.35`. В `DiagnosePresenter.isNeedLoopDiagnoseAgain()`
эта конфигурация сама по себе тоже не вызывает повтор; другие записи могут
его вызвать. Следовательно, штатный клиент способен передать такую пару
серверу как результат диагностики. Это подтверждает путь передачи, но не
правила сравнения на сервере и не фактические сырые ответы ZCU 18 октября.

В том же кэше семь других записей имеют ненулевые коды конфигурации, отличные
от `FF`; 185 содержат нули и 32 — `7F22`. У CDC, заднего и бокового ZCU
сохранены обычные коды конфигурации. Различие делает передний ZCU удобным
кандидатом для сравнения, но не определяет допустимую конфигурацию именно
этого блока. В более позднем заводском списке от 20 октября его запись имеет
адрес `722/72A` и `ecuConfigDid=FF95/FF94` (версия/код). Это метаданные
кандидата, а не сохранённый обмен с блоком или доказательство точного маршрута
проверки 18 октября.

## Что именно возвращает GHY

GCY отправляет GHY весь шестипольный список в отдельном envelope
`version/timestamp/ecuInfo`, параллельно своему `versionSync`.
`OTAUpdate2.loadSyncAllEcuVersion()` получает `CommonStatusCodeInfo`; его
`100` означает, что отчёт принят. Этот путь не возвращает модель стратегии,
ожидаемые версии или пакеты.

`getNeedCheckEcuList` — другой запрос, с телом `{}`. Его `ecuId/ecuSoftCode`
выбирают, для каких записей уже полученного плана дополнительно проверять
адрес загрузки по CDN-списку. При пустом `ecuList` клиент просто вызывает
`onCheckLegal()` и пропускает эту проверку. Следовательно, пустой список не
означает «нет ECU, которым доступно обновление», и не сужает виновный ECU.
Механизм freshness в десять минут относится к этому локальному списку CDN,
а не к серверному сравнению версий в GCY.

Скрытая таблица не нашлась и в соседних полях сохранённых ответов:
`checkVersion=111` содержит `upgradeDetails=null`; у `versionSync=104`
все четыре поля `upgradeDetailsFilePath/SecretKey/EncZipSHA256/Iv` пусты.
Развёрнутые release notes или дополнительный файл с ожидаемыми ECU по этим
ответам получить нечем. Дополнительных сетевых запросов не делалось.

## Сервисное обновление и границы диагноза

21 октября владелец уточнил: машина обновлялась **диагностическим компьютером**,
из облака — никогда. Состав обновлённых блоков и отчёт с пакетами пока не
получены. Поэтому нет подтверждённого события «OTA работало, затем сломалось»
и нет основания объявлять сервисное обновление причиной отказа.

Рабочая гипотеза — установленный сервисом набор версий не совпадает с исходной
комбинацией, которую допускает облачная стратегия. С ней остаются совместимы
как неверное назначение кампании на сервере, так и неполное/неподходящее
значение одного ECU в запросе. Ответ `111` не различает эти случаи. Наличие
`batchId` при `strategyVer=null` также не доказывает, что применимый план
для автомобиля был выбран.

`V1.7.0` — сохранённая метка: `getCurrentVehicleVersion()` читает файл, а не
вычисляет согласованность версий всех блоков. Штатный обработчик успешного
обновления записывает туда `strategyVer`, кроме заводского `strategyType=1`;
успешный `versionSync` имеет отдельный путь записи. Это не доказывает, что
диагностический компьютер оставил метку устаревшей. Проверенный ответ `104`
её не обновляет, как показано выше.

Название `repairUpgradeEcuListInfo` тоже недостаточно для связи с сервисной
историей. В прослеженном писателе `BootCompletedBroadcastPresenter` сохраняет
из результата штатного обновления только записи с `isRepairEcu=1`.
Использование внешнего диагностического компьютера само по себе не доказывает
создание этого кэша или подстановку полей в отказавшем запросе.

Промежуточный диагноз остаётся точным, но ограниченным: **сервер не выдал
пакет из-за несовпадения данных ECU со стратегией; конкретное несовпадение
не установлено**. Очистка локального плана происходит после такого ответа,
поэтому не объясняет первоначальный серверный отказ. Она может лишить
следующий разбор старых артефактов.

## Можно ли получить ожидаемые версии без обновления

Запрос метаданных отделим от скачивания и установки. Это уже подтверждено
для **другого endpoint**, `getEcuList`: успешная отдельная сессия 20 октября
сохранила 225 кандидатов и их маршруты, завершилась с закрытым экспортом и
освобождённой сессией. Источники:
`captures/diagnostics-next-20261020/approved-map-session/session.json`,
`research/vehicle-diagnostics/factory-ecu-map-20261020.json` и
`tools/vehicle-diagnostics/EcuMapMetadataProbe.java`. Этот результат не является
таблицей ожидаемых версий и не подтверждает изолированный `checkVersion`.

У GCY `UpdateOTAModel.loadCheckVehicleVersion()` выполняет отдельный POST
`ota/otaService/checkVersion`. Продолжение к загрузке находится в callback
презентера. Можно подготовить отдельный клиент, который передаст подлинные
сохранённые данные ECU, сохранит разрешённые поля ответа и завершится, не
вызывая штатные presenter, observer, загрузчик или планировщик. Использовать
штатную HTTP-обвязку для этого нельзя без учёта её auth/retry/cleanup действий.
Такой клиент `checkVersion` пока не реализован и не проверен; успешный
`getEcuList` доказывает доступность отдельного транспорта, а не весь этот путь.

Даже изолированный запрос **не гарантирует получения ожидаемой таблицы**.
Сохранённый `111` не содержит ни исходных, ни целевых пакетов. Успешный ответ
или подходящий старый `strategy.json` могут дать версии для конкретного плана,
но не обязательно полную серверную матрицу допустимых исходных сочетаний:
наличие `sourcePackageInfo` зависит, в частности, от `needSourcePkg` и способа
перепрошивки (`CheckVersionInfoIsLegalUtil.isEcuInfoPackageLegal`).

В просмотренных URL-ресурсах и моделях GCY, GHY и ProductLineOTA отдельного
запроса «вернуть ожидаемые ECU для отклонённой стратегии» не найдено.
`getManufactureConfig` содержит режим и сроки заводской операции, не версии;
второй путь `ota/checkVersion` в GCY обращается к IP/порту локального Ethernet
ECU, а не к серверной таблице кампании. Это граница найденного интерфейса,
не доказательство отсутствия служебного API на backend.

Практический порядок: искать сохранённый применимый план и сервисный отчёт,
затем при необходимости подготовить изолированный запрос только метаданных.
Если он снова вернёт `111` без деталей, повторение с теми же данными не
раскроет ожидаемые значения; потребуется штатное объяснение backend.
В этой проверке интерфейса новых запросов к машине или OEM-серверам не было.

## Следующий минимальный шаг

Уже имеющихся файлов достаточно для точного обращения к штатной стороне:
для партии `SALE-BYDHTH-2021-BATCH-00004`, исходной версии `V1.7.0` и
сохранённого шестипольного списка запросить **конкретный несовпавший ECU и
ожидаемый/полученный tuple**, начиная с конфигурации переднего ZCU выше.
Дальше сервис должен проверить назначение кампании и исходный набор версий,
чтобы предложить совместимую официальную кампанию либо штатное восстановление
baseline, если оно действительно требуется. Новую применимую прошивку и
способ её получить это исследование ещё не установило.

С учётом сервисной истории полезен также отчёт диагностического компьютера:
какие блоки и какими пакетами обновлялись, были ли незавершённые операции и
какой итоговый набор версий получился. Его надо сопоставить с ожидаемым
сервером набором, не подменяя значения в запросе.

**Повторная штатная проверка не является гарантированно только диагностикой.**
Callback настроек возвращает `false` из `isNeedAloneLoadFileSizeToShowConfirm`,
после чего допустимый план может перейти прямо к скачиванию. При завершении
скачивания `downloadAllFileOnSuccess()` вызывает `setForceUpgradeAlarmIfNeed()`:
для `isForce=1` и имеющихся пакетов назначается установка без нового
подтверждения в этом методе. Поэтому ограничение времени логирования не
останавливает OTA, а прежний `111` не гарантирует такой же следующий ответ.
Цепочка ранее разобрана в
`captures/diagnostics-discovery-20261018/ota-route-observer-plan/stock-check-scope.md`;
ключевые исходники повторно проверены и закреплены в JSON ниже.

Для следующего шага с машиной нужны актуальная доступность и конкретный объём
работ: сначала ограниченное чтение имеющихся кэшей с сохранением времени
источника, без повторного запуска OTA. Само это исследование не выполняло
ADB-команд, подписи, облачных запросов, активации OTA, скачивания или изменения
стратегии.
Хеши, source anchors, точные проекции и границы:
[`ota-strategy-followup-20261021.json`](../research/vehicle-diagnostics/ota-strategy-followup-20261021.json).
Воспроизведение только по локальным файлам и двум имеющимся архивам:
`python3 -B research/vehicle-diagnostics/check_ota_strategy_followup.py`.
