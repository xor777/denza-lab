# Штатное OTA-обновление

Как головное устройство проверяет обновления автомобиля и чем ответ сервера
отличается от надписи в настройках. Образы прошивок и их извлечение описаны
отдельно в [firmware-corpus.md](firmware-corpus.md).

## Устройство

`OTAUpdatePlatformizedUI` (`com.byd.otaupdate`) содержит основной контроллер,
GCY-клиент и SDK, к которому подключены настройки машины и `OTAUpdate2`.
При пустом `persist.sys.ota.platform` фабрика выбирает
`PlanGcyAndGhyPlatform`; на машине свойство пустое, обе службы работают.

Для серии `denza` обычные адреса из конструкторов сетевых клиентов:

- GCY: `https://fota-tsp.denzacloud.com:6113/ota/otaService/…`.
- GHY: `https://api-ota-cn.denzacloud.com/client-service/fota/api/v1/service/…`.

Это адреса нормальной конфигурации данной прошивки. Код также содержит
отдельные bench/test-переключатели. Увиденные запросы сообщали
`isBentch=false`; полная URL-строка в выбранные журналы не выводилась.

Клиент использует TLS-идентичность и токен. Для входа он формирует VIN,
ICCID, UUID проверки и код страны. Дальше штатный путь получает `getEcuList`,
опрашивает версии контроллеров, отправляет `versionSync`, затем `checkVersion`
с версией автомобиля и данными ECU. При наличии пакета следует отдельный путь
загрузки и установки. Эта проверка не подтверждает работоспособность установки.

GCY передаёт часть работы GHY: в наблюдаемом проходе GHY выполнял `lockSync`
и `getNeedCheckEcuList`. Список сервера содержит кандидатов и варианты ECU,
а не гарантированно установленные блоки. Проценты вычисляются по обходу
списка и повторным попыткам. Опрос активный, включает штатные диагностические
запросы; его нельзя выдавать за пассивное чтение кэша.

## Экран и ошибки

В обоих клиентах `CheckVersionDownloadPresenter` вызывает
`carsettingDisplay.setLatestUi()` также при сбоях входа и `getEcuList`.
В GCY такой же вызов есть при ошибке `checkVersion`. Обёртка меняет экран
только при `isNeedShowSettingUI=true`; `CarSettingDisplayUtil.setLatestUi()`
передаёт в SDK тип отображения 0.

Поэтому надпись «Latest version installed» не доказывает успешного обмена.
Нужно сопоставлять её с ответом на конкретный запрос. Коды ниже — поле
`status` в JSON приложения, **не HTTP-коды**:

| Код | Значение в клиенте |
| --- | --- |
| `100` | Запрос успешен |
| `102` | Автомобиль не входит в партию обновления |
| `104` | Текущая версия последняя |
| `111` | Нет версии для обновления |
| `113` | VIN не существует в серверной базе |
| `117` | VIN привязан к другому ICCID |
| `101` / `114` | Нужен вход / регистрация |

Ошибки DNS, подключения, TLS и HTTP идут отдельными исключениями.
Само отсутствие новой версии не доказывает ни региональную блокировку,
ни неисправность соединения.

## Проверка 2026-10-18

По явному разрешению владельца нажата ровно одна штатная кнопка `Update`
в System → About, 14:38:31 МСК. Перед нажатием экран показывал `V1.7.0` и
`Latest version installed`. Использован существующий ADB-туннель; APK,
ключи и прошивка не менялись, установка не запускалась.

Зафиксированы:

- 14:38:33, GHY `lockSync`: `{"status":"100"}`.
- 14:38:38, GCY `getEcuList`: `status=100` и непустой список ECU.
- 14:38:38, GHY `getNeedCheckEcuList`: `status=100`, список CDN и `ecuList=[]`.
- Далее GCY начал штатный опрос версий; в 14:40–14:41 менялись индекс
  кандидата и рассчитанный прогресс.
- 14:43:27.749, GCY `versionSync`: `status=104`, `latestVersion=""`,
  заполненные тексты дополнений и изменений. Клиент трактует код как
  `Current version is the latest` и всё равно делает итоговый `checkVersion`.
- 14:43:28.474, GHY `allEcuVersionSync`: `status=100`.
- 14:43:28.716, GCY `checkVersion`: `status=111`, причина
  `请求的ECU与策略中ECU版本升级详情不匹配!` — «запрошенные ECU не соответствуют
  деталям обновления ECU в стратегии». Ответ содержит
  `batchId=SALE-BYDHTH-2021-BATCH-00004`, пустые `sequence`,
  `targetPackageInfo`, `sourcePackageInfo` и конфигурационные пакеты.
- 14:43:28.747, проверка закончена: `isCheckUpdateDataLoading=false`,
  `stop_diagnose`, GCY не занят. Последующие `monitorDataReport` и GHY
  `lockSync` также получили `100`.

**Вывод этой проверки:** обмен с серверами состоялся; они приняли запросы
и не предложили подходящего пакета по переданному набору ECU/версий.
Это не наблюдение сетевого тайм-аута или отказа авторизации. Код `111` —
прикладной ответ сервера; строка исключения клиента `HTTP code: 111`
не делает его HTTP-статусом.

Ответ не называет конкретный несовпавший ECU и не объясняет внутренние
правила стратегии. Из него нельзя установить региональную блокировку,
исправность каждого результата диагностики, наличие более новой версии
для других автомобилей или возможность её установки вручную. `104` в
`versionSync` также не доказывает глобальное отсутствие новых прошивок.

Доказательства и дальнейший результат:
`captures/ota-status-20261018/README.md`. Текст ответа со списком ECU обрезан
лимитом одной Android log-записи; это не полный экспорт списка.

## Наблюдение

Изначально при `log.tag=M` в доступных main/system-буферах ответов OTA не было.
Для проверки временно включались только выбранные `OTA_GCY_UPGRADE_*` и
`OTA_GHY_UPGRADE_*` теги. Заголовки авторизации и параметры идентичности
исключались или скрывались на хосте. Исходные значения сохраняются, после
окна наблюдения восстанавливаются и проверяются. В 14:44 подтверждено
восстановление всех 19 временных тегов, глобальный `log.tag=M` сохранён.
Диагностика завершилась, оба OTA PID остались прежними, экран вернулся
к `Latest version installed` / `V1.7.0`. В crash-буфере только две старые
записи libc от 17 октября, новых падений не обнаружено. Временный XML
удалён с машины, восстановлен прежний экран штатной карты.

Глобальный `log.tag` менять не нужно. Не следует запускать OTA-приложение
заново ради логов: его `Application.onCreate()` выполняет действия над
состоянием OTA. `persist.service.ota.enable` принадлежит BydLogTool и его
`RecoveryLogEnable`, а не разрешению проверять обновления.
