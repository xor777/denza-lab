# Split Screen: продуктовый и алгоритмический контракт

Статус: нормативная спецификация перед полным рефакторингом (редакция
2026-08-23). Раздел 1 — пользовательский контракт; все технические разделы
обязаны выводиться из него и не могут ему противоречить. Продуктовым
контрактом split screen владеет этот документ: где он расходится с
историческим списком в [split-screen-findings.md](split-screen-findings.md),
действует этот документ, а findings остаётся журналом live-доказательств.
Датированный аудит кода вынесен в Приложение А.

Зафиксированные решения владельца продукта от 2026-08-23:

1. Выключение тумблера при двух живых приложениях завершает split: фокусное
   приложение остаётся на весь экран, второе продолжает жить в фоне.
2. Пока тумблер выключен, продукт полностью нейтрален к штатному BYD split:
   «будто Denza Apps о нём вообще не знает».
3. Denza Apps — обычное приложение; любая защитная/исключающая логика вокруг
   него удаляется.
4. Рефакторинг ведётся по политике delete-first (раздел 9); в основе — один
   простой автомат (раздел 7).

## 1. Пользовательский контракт

Язык раздела — только действия и наблюдения пользователя: ни task, ни ADB, ни
автоматов. Каждая строка — проверяемое обещание; на номера строк ссылаются
технические обязательства (раздел 5), сценарии приёмки (раздел 11) и тесты.

### 1.1. Пять базовых обещаний

- **U1. Ничего не происходит само.** Экран меняется только от явного действия
  пользователя: тапа, жеста, Back, Home. Запуск процесса, таймер, фоновое
  событие, «память» прошивки или восстановление после сбоя никогда не двигают
  окна сами.
- **U2. Живое приложение неприкосновенно.** Выбранное приложение не
  перезапускается, не подменяется и не прерывается (музыка продолжает играть)
  при Home, ресайзе, свопе, повторном открытии split и возврате навигации.
- **U3. Denza Apps — обычное приложение.** Его можно выбрать в панель, открыть
  и закрыть как любое другое; его запуск ничего не делает со split. Никакой
  специальной логики для него не существует.
- **U4. Выключено значит невидимо.** При выключенном тумблере продукт не
  оставляет следов: ни кнопки, ни окон, ни реакций на события, ни влияния на
  штатный split.
- **U5. Рабочий исход вместо объяснения.** Продукт не рассказывает
  пользователю о своих внутренних неудачах: он приводит экран в состояние,
  которым можно пользоваться. После любого явного действия пользователь
  получает либо сцену с приложениями, либо панель с пикером, готовым к
  выбору, — и ничего третьего: ни пустоты, ни половины сцены, ни вечной
  «крутилки». Есть приложение — тап по нему запускает приложение; куда его
  посадит прошивка, решает прошивка (1.5.3), и это не повод объявлять
  отказ. Текст ошибки — признак того, что рецепт не додумали: место
  диагностики — support-экран, а не глаза пользователя. Так устроена и сама
  система: то, что не может работать, не предлагается (U4), а то, что
  предлагается, просто работает.
- **U6. Интерфейс отзывчив.** Любое явное действие даёт видимый отклик не
  позднее чем через секунду. Ожидание без видимого прогресса дольше секунды —
  дефект; «нажал и жду десять секунд» неприемлемо ни в одном сценарии.
  Нормы отзывчивости — в 1.13. Итог действия виден там, где пользователь
  действовал; сбой фоновой сверки не трогает ни экран, ни карточку — только
  диагностический лог.

### 1.2. Тумблер

| # | Действие | Пользователь видит |
|---|---|---|
| 1.2.1 | Включить | Появилась кнопка «Разделить экран». Больше ничего: split не открылся, экран не мигнул. |
| 1.2.2 | Выключить, split не открыт | Кнопка исчезла. Больше ничего. |
| 1.2.3 | Выключить при двух выбранных приложениях | Split завершён: приложение в фокусе — на весь экран, второе живо в фоне и доступно через Recents, пикеры исчезли. |
| 1.2.4 | Выключить при приложении и пикере | Приложение — на весь экран, пикер исчез. |
| 1.2.5 | Выключить, когда открыты только пикеры | Пикеры исчезли, показан Home. |
| 1.2.6 | Выключить во время запуска split | Запуск отменён, окно ожидания снято, затем правила 1.2.2–1.2.5. Позже ничего «не доезжает». |
| 1.2.7 | Пока выключено | Система ведёт себя так, будто Denza Split не установлен. Штатный split живёт своей жизнью (см. 1.12). |

Выбор панелей при выключении не забывается: после включения и нажатия кнопки
восстанавливается последняя пара (1.3.2).

### 1.3. Кнопка «Разделить экран» и ожидание

| # | Ситуация | Пользователь видит |
|---|---|---|
| 1.3.1 | Тап по кнопке | Сразу окно «Запускаю разделение экрана». Это единственное действие, создающее окно ожидания. |
| 1.3.2 | Есть сохранённый выбор | Сцена с теми же живыми приложениями — без перезапуска, музыка не прервалась. Холодный запуск — только если приложение реально не работало. Что не восстановилось — та панель просто показывает пикер, готовый к выбору; текста об этом нет (U5). |
| 1.3.3 | Сохранённого выбора нет | Два пикера. |
| 1.3.4 | Одна панель была закрыта, во второй приложение | Приложение на месте, в закрытой панели свежий пикер. Закрытое раньше приложение не воскресло. |
| 1.3.5 | Сцена уже открыта | Показана как есть; ничего не пересоздано и не перезапущено. «Открыта» — про сцену, отвечающую сохранённому выбору: панели, стоящие на пикерах при живом сохранённом выборе (например, после неудавшегося открытия), — незавершённое восстановление, и тап его доводит, а не считает работу сделанной (1.3.2). |
| 1.3.6 | Сцена скрыта (Home/чужое приложение) | Та же живая сцена поднята; чужое приложение не закрыто. |
| 1.3.7 | Повторный тап во время запуска | То же одно ожидание; второго запуска нет. |
| 1.3.8 | Ожидание дольше предела | Окно исчезло, ввод разблокирован, экран остался тем, что уже стоял, — и им можно пользоваться (U5); текста об этом нет. Опоздавший результат отменён: позже ничего не «всплывает». |
| 1.3.9 | Home во время запуска | Только что запрошенная сцена появляется в пределах потолка 1.13 — это и есть заказ пользователя; сверх потолка запуск отменяется, и поверх Home позже ничего не появляется. |
| 1.3.10 | На экране чужой/штатный split | Чужие окна не тронуты, экран остался прежним и рабочим (U5); продукт не объясняет, почему не вмешался. |

### 1.4. Пикер

- 1.4.1. Пикер — каталог всех запускаемых приложений и постоянное «дно»
  каждой панели: пустая панель показывает пикер, выбранное приложение живёт
  над ним, после закрытия приложения панель снова показывает свой пикер.
- 1.4.2. Каталог актуален: установленное появляется, удалённое исчезает.
- 1.4.3. Denza Apps присутствует в каталоге как обычное приложение (U3).
- 1.4.4. Пикер никогда не появляется сам поверх того, чем занят пользователь
  (U1).

### 1.5. Выбор приложения

| # | Действие | Пользователь видит |
|---|---|---|
| 1.5.1 | Тап по приложению | Оно открылось в этой панели. Соседняя панель не изменилась. |
| 1.5.2 | То же приложение во второй панели | Разрешено: две независимые копии. Если приложение технически не умеет второй экземпляр — первая копия не тронута, панель осталась на пикере (U5). Живая вторая задача того же пакета — обычный житель мира: её показывают, а не запускают поверх неё копию и не отменяют из-за неё сборку. |
| 1.5.3 | Выбрать Denza Apps | Открылась и работает как обычное приложение; split не перестраивался. Сторону панели для собственного split-способного пакета решает прошивка (live v22): продукт записывает фактическую сторону, не требуемую, и не объявляет вставшее окно отказом. Это обязательство одинаково на пути ВЫБОРА в пикере и на пути ВОССТАНОВЛЕНИЯ пары (1.3.2): прошивка вправе посадить наш пакет не в ту панель, которую просили, — законный исход, и восстановление обязано записать фактически занятую панель тем же способом, что и выбор. |
| 1.5.4 | Двойной/очень быстрый повторный тап | Один запуск, не два. |
| 1.5.5 | Быстро выбрать в обеих панелях | Оба запуска выполняются, каждый в своей панели. |
| 1.5.6 | Приложение удалили, пока пикер открыт | Список обновился; ничего не сломалось. |
| 1.5.7 | Приложение не открылось (запуск не удался) | Пикер панели никуда не уходил и остаётся рабочим — можно выбрать снова или выбрать другое; сосед не тронут, текста об ошибке нет (U5). Приложение, которое прошивка посадила не в ту панель, — не «не открылось»: оно открылось (1.5.3). То же верно и при восстановлении сохранённой пары (1.3.2): чужая сторона — не провал запуска, а факт, который путь восстановления записывает так же, как путь выбора (1.5.3). Краш уже работавшего приложения — нативный исход, 1.7.3. |
| 1.5.8 | Home сразу после выбора | Home побеждает; выбранное не выскочит поверх Home позже. |

Чужая задача в панельном корне — задача пользователя, чем бы она туда ни
попала (нативное втягивание, прежний выбор, вторая копия). Продукт никогда
её не удаляет: расчищая корень под сцену, он выселяет чужое фоном в
полноэкранный корень (инвариант 3). Удалять продукт может только своё по
точному компоненту (пикер-базы, retired host, штатный bootstrap) и задачи,
созданные текущей операцией.

### 1.6. Back и завершения — нативно

Решение владельца (2026-08-23): наперекор прошивке продукт не идёт. Реакцию
на Back и на завершение приложений определяет прошивка; продукт её не
переопределяет, ничего не перестраивает поверх и не воскрешает. Его
обязанность одна — после нативного исхода вычистить своё (аренды, огрызки
задач, память сцены), чтобы следующий тап «Разделить экран» открывался
чисто.

- 1.6.1. Внутри выбранного приложения Back работает штатно по его
  собственной истории.
- 1.6.2. Последний Back в приложении панели: исход принадлежит приложению
  и прошивке (Яндекс-приложения по root-Back минимизируются, не выходят —
  live 2026-08-24). Пока наш пикер остаётся в корне панели, панель
  показывает его, сосед не тронут и его звук не прерывается (live v16 срез
  шаг 6; v18 S13). Продукт гарантирует только не-воскрешение (U1) и уборку
  своего.
- 1.6.3. Back в пикере — нативный исход зависит от роли панели: широкая
  панель — якорь сплита у этой прошивки (ground-v18, 2026-08-23).
  Back в пикере УЗКОЙ панели → сосед в широкой (приложение или пикер)
  разворачивается на весь экран, звук не прерывается, всё чисто
  (live: срез v16 шаг 6; ground-v18 B1 — прошивка сама откатывает ключи).
  Back в пикере ШИРОКОЙ панели при «пикер|пикер» → прошивка завершает split
  и уводит на Home (`startDockOrHome` → `removeIviStack`, ground-v18 B2),
  бросая узкий пикер невидимой задачей и не откатывая ключи — эту уборку
  обязан выполнить продукт: после нативного конца огрызков наших задач и
  наших следов в firmware-ключах не остаётся.
  Back в широком пикере при живом приложении в узкой панели → прошивка
  прячет весь сплит в Home; сцена остаётся жива-скрыта, ключи сессии не
  откатываются, следующий тап открывает по 1.3 (наблюдено каскадом v20 S7;
  одиночный шаг подтверждается отдельной пробой).
- 1.6.4. После любого нативного завершения сессии повторный тап «Разделить
  экран» даёт корректное открытие; ничего не воскресает само (1.3.4).

| 1.10.8 | Выключить тумблер во время projection | Незавершённые split-операции отменяются (включая возврат — навигация покажет свой повтор); сцена на IVI разбирается по правилам 1.2; навигатор остаётся жить на приборке, его возврат своим механизмом приводит его на весь экран. Ничего не воскресает. |

### 1.11. Перезагрузка, обновление, сбои

| # | Событие | Пользователь видит |
|---|---|---|
| 1.11.1 | Перезагрузка ГУ | Ничего не запускается само (U1). Тумблер и выбор панелей помнятся; первый тап «Разделить экран» восстанавливает выбор — здесь холодный запуск допустим. |
| 1.11.2 | Обновление Denza Apps | Живые приложения не тронуты; ничего не запускается фоном. |
| 1.11.3 | Краш/перезапуск Denza Apps при живом split | Чужие приложения продолжают работать; ничего не двигается. |
| 1.11.4 | Сбой управления (нет ADB) | Текущий экран продолжает работать: это штатные окна прошивки. Тумблер и его иконка — решение пользователя, продукт их не отзывает за него; вместо ошибки тап приводит туда, где канал чинится, — на экран хаба с ADB-гейтом. Вечного ожидания и текста об отказе нет ни в каком случае. После восстановления связи ничего не происходит само. |
| 1.11.5 | Камера заднего хода, ассистент, системное окно | Перекрывает сцену; сцена живёт под ним и возвращается как была. Автоматика в это время ничего не двигает. |
| 1.11.6 | Смена языка системы | Сцена и выбор переживают; пикеры просто перерисовываются. |

### 1.12. Честное ограничение прошивки

Выбор приложения в split делает его «split-способным» для прошивки до
перезагрузки ГУ: у прошивки нет операции отмены. При выключенном тумблере
Denza в это не вмешивается (U4): если пользователь сам пользуется штатным
split, прошивка может подставлять такие приложения по своим правилам — это её
штатные списки, а не действия Denza. Полностью очищает их только перезагрузка.
Продукт обязан не расширять этот след без необходимости и фиксировать каждое
такое добавление в диагностическом логе.

### 1.13. Нормы отзывчивости

Числа не выдумываются из головы: единственная норма, заданная владельцем —
«нажать и ждать десять секунд — неприемлемо». Остальное выводится из двух
источников: из измеренного поведения этой же машины и из ощущений человека
за рулём. Прежняя таблица фиксированных бюджетов (3 с на сцену и т.п.)
удалена: её числа не были ничем обоснованы. Четыре правила, по убыванию
строгости:

1. **Отклик — сразу.** После явного жеста видимая реакция (окно, подсветка,
   смена экрана) появляется без паузы, в которой палец усомнился бы, что
   нажатие принято. Машинная проверка считает «сразу» как ≤ 1 с.
2. **Ожидание — честное.** Пока операция идёт, экран не врёт: виден
   индикатор, и внутри операции пользователю не показывается посторонний
   контент — чужие приложения, промежуточные состояния, мигания. Грязное
   ожидание — красное при любой длительности.
3. **Не хуже штатного.** Операция продукта не проигрывает заметно
   аналогичному штатному действию этой же машины на этой же прошивке.
   Референс — измеренные приёмкой времена штатных действий (вход в штатный
   split, запуск приложений), записанные в findings как справочник. Пока
   референс не измерен, правило записывается, но не гейтит.
4. **Потолок — 10 с.** Ни одна операция не длится дольше 10 с до результата
   или честной ошибки. Аварийный потолок отмены 1.3.8 (15 с) — граница,
   после которой операция обязана умереть сама; это не норма ожидания.

Роли: приёмка измеряет и записывает секунды каждого шага всегда — и когда
нарушения нет; окончательный судья «напрягает или нет» — человек в машине.
Замер без вердикта — норма, вердикт без замера не принимается.

## 2. Оси состояния

Одно enum-состояние, смешивающее выбор, живые задачи и технические lease,
снова запрещено (см. раздел 8). Независимые оси:

### 2.1. Функция

`DISABLED` | `ENABLED`.

### 2.2. Слот панели (их две)

`CLOSED` | `PICKER` | `APP(package)`. Оба слота могут независимо содержать
один и тот же package. В слоте никогда нет task/root ID.

### 2.3. Сцена — две независимые оси

- Существование: продуктовая сцена есть (`SPLIT(left, right)` | `FULL(x)`)
  либо её нет.
- Видимость существующей сцены: `VISIBLE` | `COVERED(home | recents | чужое
  fullscreen | системный захват)`.
- Отдельный маркер: `PROJECTED(pane)` — навигатор этой панели временно на
  приборке.

Home на экране при отсутствии сцены — это «сцены нет», а не отдельное
состояние сцены.

### 2.4. Операция

`IDLE` | `OPEN` | `SELECT(pane, package)` | `EDGE_COMMIT` | `RECONCILE` |
`NAV_RETURN` | `DISABLE`. У каждой изменяющей операции: монотонный
`operationId`, исходный live-снапшот, deadline и итог — `COMMITTED`,
`ROLLED_BACK` либо `CANCELLED`. Операции, overlay-lease и любые task ID не
переживают процесс и reboot.

## 3. Неослабляемые инварианты

1. **Нейтралитет DISABLED.** При выключенном тумблере продукт не выполняет ни
   одной split-мутации ни по какому поводу: ни при старте процесса, ни при
   запуске Denza Apps, ни по событиям прошивки. Не закрывает и не открывает
   gate, не удаляет пикеры, не двигает задачи, не меняет resizeability.
2. **Нейтралитет к чужому при ENABLED.** Пока нет живой продуктовой сцены,
   штатные split-потоки пользователя не перехватываются: штатный пикер не
   подменяется, чужие задачи не трогаются. Продукт вмешивается в штатный
   пикер только когда тот открылся в панели живой продуктовой сцены (1.8.5).
   Выключение тумблера подчиняется тому же правилу: разбор сцены снимает
   штатный пикер только если на главном экране жива задача нашей точной
   identity — пикер или host Denza. Сама задача штатного пикера двух случаев
   не различает: «прошивка заняла освободившуюся панель нашей сцены» и
   «пользователь собрал штатный split» выглядят одинаково, и её task ID не
   принадлежит нам ни в одном из них, поэтому доказательство берётся со
   сцены, а не с задачи. Не осталось ничего нашего — чужой пикер остаётся.
3. **Мутация только по identity.** Любая мутация адресует задачу, root или
   lease, чья принадлежность текущей операции подтверждена свежим
   live-снапшотом. Package сам по себе identity не доказывает: два одинаковых
   приложения различаются задачами, а пикер и приложение Denza Apps в одном
   package — компонентами.
4. **Task/root ID эфемерны.** В durable state их нет; process death, reboot
   и update они не переживают. Между операциями допустима только
   внутрипроцессная live-сцена-подсказка, обнуляемая вместе со сценой;
   каждое её использование перепроверяется свежим снапшотом по exact
   identity.
5. **Home ≠ close.** Home скрывает сцену, не очищает слоты и не перезапускает
   приложения. Машинная правда (live v21 + корпус, ред. 2026-08-24):
   обычный Home выселяет в display area детей ШИРОКОГО (SECOND) контейнера —
   безусловно и только их; дети узкого (PRIMARY) остаются на месте под
   защитой контейнера. Выселенные задачи отвязываются живыми, с сохранёнными
   панельными границами («сфокусированная панель» ранней редакции была
   совпадением — выселение выбирает контейнер, не фокус). Нативный конец
   всего split (например, Back в широком пикере) распускает оба контейнера.
   Отвязка накрытой сцены — не закрытие и не жест пользователя: продукт не
   убирает такие задачи как сирот и умеет возвращать их на место.
6. **Close реален.** Закрытие приложения переводит `APP → PICKER`, закрытие
   панели — `→ CLOSED`, до того как это состояние сможет участвовать в
   каком-либо восстановлении. Закрытое не воскресает (1.3.4, 1.7.5).
7. **Resize меняет только геометрию.** Task, PID, package, playback и слот
   сохраняются (1.8.1).
8. **Пассивные события — только сигналы.** Lifecycle/accessibility события
   помечают live-снапшот устаревшим; сами они не порождают мутаций и не
   отменяют более новый пользовательский ввод.
9. **Отказ не оставляет непроверенного состояния.** Результат ошибки — либо
   исходная стабильная сцена, либо новая полностью проверенная; частичный
   результат не объявляется успехом. «Исходная стабильная сцена» никогда не
   означает пустой экран: если панельные базы уже стоят, отказ оставляет их —
   панель на рабочем пикере проверена и пригодна (U5). Сохранённый выбор при
   этом не стирается: пользователь ничего не закрывал.
10. **Fencing тотален.** После timeout/cancel ни одна команда старого
    `operationId` не меняет задачи, gate, persisted state или overlay новой
    операции.
11. **Никаких самовольных пар.** Обычный запуск после Home остаётся обычным
    полноэкранным запуском (1.9.2); продукт никогда не инициирует
    восстановление «запомненной пары» прошивки.
12. **Единственный писатель.** Semantic state меняет только автомат
    (раздел 7); никакой другой код не пишет слоты, сцену или операцию.
13. **Границы задачи равны границам её корня.** Ни одна задача не остаётся с
    границами, не равными границам своего корня, после завершения операции.
    Живой дефект 2026-08-27: задача в полноэкранном корне сохранила панельные
    границы 832 px, и пользователь получил треть экрана и пустоту рядом.
    Прошивка нормализует границы не всегда: ветка `startIviFullWindow` с
    `changeWindowingMode == false` переносит задачу в полноэкранный корень с
    `updateBouds=false` и границы не трогает (корпус 2026-08-28, findings,
    «Internal Activity transitions»). Поэтому нормализация — обязанность
    продукта, а не прошивки.

## 4. Приоритет конфликтующих событий

1. `DISABLE` — отменяет все незавершённые операции.
2. Подтверждённый `HOME` — отменяет `SELECT`, `RECONCILE` и запрещает
   поздние мутации. Явно запрошенный пользователем `OPEN` в пределах потолка
   1.13 Home НЕ отменяет: его завершение и есть заказанное действие (запуск
   идёт с Home — Home на экране не новость); сверх потолка `OPEN` убивает
   дедлайн, и после него поверх Home ничего не появляется. Подсказка «виден
   Home» от наблюдателя — не событие Home: переподключение сервиса и оконные
   эхо запуска не отменяют пользовательский ввод (инвариант 8).
3. Navigation lease — владеет перемещаемой задачей навигатора.
4. Явный тап в пикере (`SELECT`). Два `SELECT` в разные панели не
   конфликтуют: сериализуются и выполняются оба (1.5.5).
5. Явный тап «Разделить экран» (`OPEN`).
6. Подтверждённый edge commit или collapse.
7. Пассивные hints: lifecycle, accessibility, resize.

Явное действие пользователя не ждёт фоновый шум: сабмит `DISABLE`, `OPEN`
или `SELECT` отменяет пассивный hint/`RECONCILE` не только в очереди, но и
в полёте — тем же механизмом (токен, fence, откат по журналу), которым
Home уже отменяет их; фоновая сверка перечитает мир после пользовательской
операции (U6; live v20: сверка перед open стоила пользователю ~2 с
очереди).

Проигравшее событие не воспроизводится из очереди: после завершения операции
читается один свежий live-снапшот. Историческая очередь
`TYPE_WINDOWS_CHANGED` не переигрывается никогда.

## 5. Технические обязательства к строкам раздела 1

Дополнительно к видимому поведению приёмка проверяет:

- **К 1.2 (тумблер).** Выключение: fence всех операций → свежий снапшот →
  фокусная задача в полноэкранный root с сохранением её task id → задача
  второго приложения остаётся живой → удаляются только собственные
  picker-задачи по exact identity → восстанавливаются только собственные
  lease (resizeability, наблюдатель); gate закрывается только если его
  открывали мы (по lease), иначе не трогается (решение №2) → слоты в
  persisted сохраняются. Включение: запись состояния и кнопка; ноль
  shell-мутаций.
- **К 1.3 (открытие).** Один overlay-lease на операцию; deadline отменяет
  операцию, а не только окно. «Сцена интерактивна» определено измеримо:
  сфокусированное окно принадлежит ожидаемой задаче, оба root'а
  соответствуют ожиданию, наш пикер принимает ввод. Успех — только после
  финального read-back. Повторный тап присоединяется к живой операции и
  получает её итог, а не мгновенный «успех».
- **К 1.5 (выбор).** `SELECT` замкнут на одну панель. Persist слота — после
  проверки, что новая задача действительно над нужным пикером. Same-package:
  две независимые задачи; отказ второго экземпляра не двигает первый. Denza
  Apps выбирается как обычный компонент приложения; исключающих списков нет.
- **К 1.6–1.7 (закрытие, краш).** «Закрыто» подтверждается топологией
  (задача покинула панельные root'ы либо умерла), а не одним
  lifecycle/accessibility событием. Прошивка асимметрична: secondary-задачу
  жест может лишь увести за следующую — критерий закрытия формулируется по
  топологии, не по факту удаления. Краш обрабатывается как закрытие;
  авторестарта нет.
- **К 1.8 (divider, edge).** Resize сохраняет task/PID/package/playback;
  привязка логического слота к стороне — по фактической топологии после
  settle, не по старым меткам. Edge-путь: до подтверждения — ноль наших
  мутаций и окон; generation отменяет опоздавшие callbacks (1.8.6).
- **К 1.9 (Home).** Home — приоритетное событие (раздел 4); приостановка
  собственного gate — только по lease и только после подтверждения Home;
  очередь не имеет права «потерять» Home за старой работой.
- **К 1.10 (навигация).** Durable-слот панели навигатора остаётся `APP(nav)`
  на всё время projection; временное приложение вакансии — эфемерная запись:
  краш или перезагрузка теряют её, но не место навигатора. Возврат читает
  свежую топологию непосредственно перед перемещением; вытесненное удаляется
  только по exact identity. Навигация и split используют один протокол
  операций и ownership — второго жизненного цикла нет.
- **К 1.11 (сбои).** Холодная инициализация — строго read-only. Durable
  переживают только тумблер и слоты (package). Потеря ADB: exact rollback по
  журналу операции либо принятие последней полностью проверенной топологии.
  Системный захват экрана (камера, ассистент) в снапшоте — операция
  откладывается или отменяется fail-closed, без мутаций под захватом.
  Сбой фоновой сверки не публикует ошибок в UI (U5).
- **К 1.12 (gate, allowlist).** Открытие gate — только при старте или явном
  возобновлении своей сессии (включая повторный подъём сцены после
  Home-suspend) и только если он закрыт (lease «мы открыли»); закрытие —
  только по этому lease при завершении сессии. Добавление пакета в split-список
  прошивки — только в момент его выбора и с записью в диагностический лог.

## 6. Persisted state

Единое атомарное хранилище; один snapshot — одна запись:

- `featureEnabled`;
- слот каждой панели: `CLOSED` | `PICKER` | `APP(package)`;
- revision последней полностью завершённой операции;
- ownership и исходные значения глобальных lease (resizeability,
  наблюдатель, gate).

Никогда не сохраняются: task/root ID, физическая сторона wide/narrow,
незавершённые операции, overlay-lease, projection, hints.

Переходы записи: последний Back, закрытие, краш, uninstall — `APP → PICKER`;
закрытие панели, collapse — `→ CLOSED`; Home — ничего; restore фиксируется
только после полного live read-back; toggle-off слоты сохраняет. Два
одинаковых package хранятся независимо. Uninstall при выключенной функции
деградирует лениво: инвариант 1 запрещает реакцию в момент удаления, поэтому
слот с исчезнувшим package пересматривается в `PICKER` при первом следующем
построении сцены.

Миграция при первом старте новой версии: старые ключи (автомат с task ID,
отдельная «последняя пара», состояние retired-роутера) читаются один раз,
конвертируются только в package-слоты и удаляются. Никакие сохранённые ID не
интерпретируются.

## 7. Ядро: один актор, один автомат

- **Автомат** — маленькая чистая синхронная функция
  `(state, установленный факт) → (state', нужен ли разбор сцены)`. Он ничего не
  знает про ADB, время, потоки и task ID; оперирует только осями раздела 2. Это
  единственное место, где меняется semantic state (инвариант 12).

  Редакция 2026-08-27: здесь было «→ (state', план мутаций)», и автомат
  действительно выдавал `SplitPlan` из семи вариантов. Их никто не исполнял —
  создавались все семь, а весь продукт спрашивал у списка одно — пуст он или
  нет, и ровно в одном месте. Рецепты прошивки живут в операциях, написаны
  императивно и выверены на машине; план был вторым описанием тех же намерений,
  которое ничего не решало и потому могло молча разойтись с оригиналом. Осталось
  единственное, что у автомата и спрашивали.
- **Актор** — единственный владелец очереди с приоритетным вытеснением по
  разделу 4, а не FIFO-executor: `DISABLE` и `HOME` отменяют и обгоняют
  очередь, пассивные hints схлопываются до одного признака «снапшот устарел».
- **Установленные факты, а не сырые события.** Перед подачей в автомат
  событие превращается в проверенный settled-факт (например «задача X
  покинула панельные root'ы», а не «пришёл onStop» или «мигнул
  TYPE_WINDOWS_CHANGED»).
- **Операция** строит и исполняет СВОЙ план (автомат ей его не выдаёт) по
  алгоритму:
  1. назначить `operationId`, приоритет, deadline, cancellation token;
  2. снять read-only live-снапшот;
  3. проверить предусловия: функция, ownership, отсутствие системного
     захвата;
  4. построить полный план без единой мутации;
  5. исполнять exact-мутации по одной, проверяя token до и после каждой;
  6. вести mutation journal: исходные lease, созданные и перемещённые
     задачи;
  7. сделать финальный read-back и проверить продуктовый postcondition;
  8. одним атомарным commit сохранить persisted-снапшот;
  9. освободить overlay/lease и сообщить итог;
  10. при ошибке, timeout или отмене — прекратить новые мутации и выполнить
      exact rollback по журналу либо принять только полностью доказанную
      стабильную сцену;
  11. при ЛЮБОМ исходе — коммите, отказе, откате или броске — выполнить
      терминальные обязательства операции (`cleanUp`). Именно после отката, а не
      вместо него: откат может ещё пользоваться тем, что уборка забирает.
- Live-снапшот из нескольких shell-чтений принципиально приблизителен;
  консистентность обеспечивают не «атомарные снимки», а token-проверки
  вокруг каждой мутации и финальный read-back.

## 8. Работа над ошибками: почему прошлый автомат выродился

Прошлая попытка тоже начиналась с «простого чистого редьюсера». Причины
вырождения установлены построчным аудитом кода (Приложение А); каждая из них
закрыта конкретным правилом этого документа.

1. **Автомат не был единственным писателем.** Рядом жило второе хранилище
   («последняя пара»), коммитившееся отдельно и в другом порядке; хранилища
   расходились — live-регрессия 2026-08-22. → Инвариант 12, раздел 6.
2. **Автомат моделировал слоты, но не операции.** Асинхронные сайд-эффекты —
   открытие, restore, cleanup — жили вне модели: без deadline, отмены и
   отката. Overlay-таймер снимал окно, а операция продолжала мутировать
   экран. → Ось 2.4, раздел 7, инвариант 10.
3. **На вход шли сырые события, а не факты.** Каждый `TYPE_WINDOWS_CHANGED`
   порождал работу до фильтрации; in-flight флаги отбрасывали свежие
   события, а устаревшие задания исполнялись над уже другой сценой. →
   Инвариант 8, «установленные факты» в разделе 7.
4. **Один FIFO-executor на всё.** Home и выбор пользователя стояли в очереди
   за многосекундными пассивными ожиданиями; порядок исполнения не совпадал
   с приоритетом событий. → Актор с вытеснением, раздел 4.
5. **Live task ID утекли в durable.** Автомат сохранял host/app task ID без
   boot-epoch; после перезагрузки чистка оперировала чужими номерами. →
   Инвариант 4, раздел 6.
6. **У события было несколько интерпретаторов.** Три поколения архитектуры в
   одном дереве (роутер, редьюсер, explicit-режим) плюс синхронный
   навигационный путь параллельно основному: одна сцена обрабатывалась
   дважды по-разному. → Раздел 9, обязательство к 1.10.
7. **Рост заплатками.** Около тридцати подряд коммитов «fix(split)» чинили
   по одному симптому, добавляя ветку каждый раз; комбинаторика этих веток и
   есть наблюдаемая непредсказуемость. Тесты при этом проверяли редьюсер в
   вакууме: ни один не мог упасть от реальных классов отказов — порядка,
   отмены, атомарности, identity. → Разделы 9–11: сначала контракт и
   сценарные тесты, затем реализация; точечные фиксы без сценария запрещены.

## 9. Политика delete-first

Сначала удаление, потом реализация. История хранится в git, а не в дереве.

1. До первого нового кода из production-дерева удаляются:
   `SplitRoutingReducer`, `SplitShellRouter`, `SplitPlaceholderActivity`,
   `SplitAppHostActivity` и их манифест-записи; legacy-ветка маршрутизации в
   координаторе (`EXPLICIT_PICKER_MODE`, циклический `startAsync`,
   `runRoutingSession`); хранилище состояния роутера; исключающие списки и
   любая «защитная» логика вокруг Denza Apps (U3); тесты всего
   перечисленного.
2. Никаких флагов совместимости и переключателей старого режима: в дереве в
   любой момент ровно одна архитектура.
3. Persisted-ключи старых поколений удаляются одноразовой миграцией
   (раздел 6).
4. Удаления идут отдельными bisect-friendly коммитами до коммитов новой
   реализации.
5. «Может пригодиться» — не аргумент: уроки зафиксированы в findings и в
   этом документе, код восстановим из истории.

## 10. Тесты

### 10.1. Вердикт аудита (2026-08-23)

Аудит выполнен независимым агентом с чистым контекстом по снапшоту
`a1ff965`: 156 @Test в split из 512 в модуле. Полные таблицы — Приложение Б.

| Категория | Тестов | % от 156 |
|---|---|---|
| DEAD — тестируют retired-код | 43 | 27.6 % |
| TAUTOLOGY — пересказывают реализацию или проверяют собственный fake | 5 | 3.2 % |
| DUPLICATE — не добавляют различающей силы | 7 | 4.5 % |
| NARROW — честный юнит-контракт вдали от реальных отказов | 77 | 49.4 % |
| REAL — защищают инвариант shell/lease-слоя | 24 | 15.4 % |

**Тест-театр подтверждён частично, и диагноз хуже театра: 155 из 156 тестов
не могут упасть ни от одного из семи реальных классов отказов (раздел 8).**
Ни один тест не конструирует `SplitScreenCoordinator`, `SplitScreenSettings`
или активности — весь слой, где живут реальные отказы, не покрыт по
построению. Отдельный класс — **пять анти-контрактных тестов**, закрепляющих
дефекты как ожидание (закрытие чужого gate при `DISABLED`, перемещение чужого
foreground, два overlay-lease на два тапа, deadline без отмены операции): они
упадут при реализации контракта, и это правильно.

Ключевые находки сверх известного: на пути Home автомат обнулялся, а
«последняя пара» не трогалась — расхождение хранилищ воспроизводимо по
построению и невидимо для CI; тестовый `FakeShell` симулирует host-механику,
которую продукт уже не вызывает.

### 10.2. Решения по аудиту

1. Удаляются вместе с retired-кодом (43): `SplitRoutingReducerTest` (29),
   `SplitShellRouterTest` (12), два `PROJECTED`-теста автомата с их приватным
   хелпером.
2. Переписываются с инверсией ожидания (5 анти-контрактных):
   `disabledProductClosesGateAndMovesForegroundEvenWithoutOurPicker`,
   `expandedSplitWithStockVacancyBecomesTrueFullscreenWhenProductIsOff`,
   `closeAcceptsNewFullscreenForegroundWhilePickerCleanupIsInFlight`,
   `hardDeadlineReleasesWindowWithoutCoordinatorCallback`,
   `overlappingRequestsStayVisibleUntilEveryLeaseEnds` — новые ожидания: ноль
   мутаций чужой сцены, deadline ⇒ `CANCELLED`, один lease на одну `OPEN`.
3. Сливаются или удаляются: 7 DUPLICATE и 5 TAUTOLOGY;
   `SplitNativePickerEventPolicyTest` заменяется одним тестом маршрутизации
   `onAccessibilityEvent` (фильтр до reconcile).
4. Сохраняются 24 REAL + 77 NARROW как нижний слой shell/lease-инвариантов;
   `FakeShell` выносится в общий `SplitShellFixture`, его мёртвая host-ветка
   удаляется; тесты автомата переписываются на package/slot-идентичность без
   task ID.
5. Обязательный минимум нового покрытия — сценарные тесты координатора
   K1–K15 (Приложение Б.3). Пока их нет, покрытие координации считается
   нулевым независимо от числа зелёных тестов.

### 10.3. Правила

1. Первичны сценарные тесты координатора: fake shell + fake clock + fake
   store; каждый сценарий раздела 11 — минимум один тест, проверяющий
   выданные команды, их порядок и отсутствие лишних мутаций.
2. Анти-театральный критерий: тест засчитывается в покрытие, только если
   способен упасть от реального класса отказов — переупорядочивания, отмены,
   двойной доставки, устаревшего снапшота, неатомарного persist, чужого
   task id.
3. Тесты мёртвого кода удаляются вместе с кодом (раздел 9), не переносятся.
4. Live-приёмка — по методике governance.md: один сценарий за прогон,
   before/after снапшоты (task/root/PID/playback), документированный reset.

## 11. Адверсариальные приёмочные сценарии

Каждый сценарий проверяет и видимое поведение (раздел 1), и технические
обязательства (раздел 5): task/PID, package, root, persisted, overlay,
gate/lease, playback.

1. `Music | Yandex` → Home → сразу Yandex: только Yandex fullscreen; Music и
   ADAS не появляются рядом (1.9.2).
2. `Music | Yandex` → Home → «Разделить экран»: те же живые task; музыка не
   перезапускается и продолжает играть (1.9.4).
3. Десять быстрых ресайзов: те же task/PID, ноль перезапусков, итог по
   последнему положению (1.8.1, 1.8.3).
4. `FULL(Music)` → edge-drag → cancel: точный исходный экран, ни overlay, ни
   нового пикера (1.8.6).
5. `FULL(Music)` → edge-drag → commit: тот же Music task + один пикер
   (1.8.5).
6. Во время edge-drag выбрать приложение в штатном списке: выбранное не
   удаляется поздней Denza-командой (1.8.7).
7. Тап «Разделить экран» → сразу Home: сцена либо появляется в пределах
   потолка 1.13, либо после дедлайна не появляется никогда; «внезапных»
   поздних открытий нет (1.3.9).
8. Тап «Разделить экран» → выключить тумблер: операция отменена; поздних
   мутаций нет; окно снято (1.2.6).
9. Тап при недоступном ADB: прежний экран цел, окно снято, persisted
   прежний, вечного ожидания нет; тап приводит на экран починки канала
   (1.11.4, U5).
10. Оборвать ADB после первого созданного пикера: rollback либо проверенная
    частичная сцена, которой можно пользоваться. Gate не остаётся открытым
    без сцены; открытый gate под стоящей рабочей сценой — её законная часть.
11. Два быстрых тапа кнопки: одна операция, один набор задач, один overlay и
    один итог (1.3.7).
12. Один package в обеих панелях: две независимые задачи либо видимый отказ
    второй попытки без перемещения первой (1.5.2).
13. Выбрать Denza Apps, открыть и закрыть её: сосед и split не
    перестраиваются (1.5.3).
14. Запустить Denza Apps при выключенном тумблере поверх любого штатного
    split: топология прошивки не меняется ни одной командой (инвариант 1).
15. Закрыть Music последним Back → пикер → Home → «Разделить экран»: Music
    не воскресает (1.3.4).
16. Back при «пикер|пикер» в узком пикере: широкий пикер на весь экран,
    заголовок не обрезан (1.6.3). Затем воссоздать «пикер|пикер» и Back в
    широком: нативный уход на Home, после которого продукт убрал
    сироту-пикер и вернул firmware-ключи (1.6.3); повторный тап после
    каждого из исходов — корректное открытие (1.6.4).
17. Nav → приборка, выбрать Temp в вакансии, сменить Music на Radio, вернуть
    Nav: exact Temp закрыт, Nav возвращён, Radio сохранено и не перезапущено
    (1.10.4, 1.10.5).
18. Nav → приборка, схлопнуть его панель, вернуть Nav: Nav fullscreen;
    companion не воскрешается (1.10.6).
19. Убить процесс Denza Apps при `Music | Yandex`: оба приложения продолжают
    работать; холодный старт ничего не двигает (1.11.3).
20. Перезагрузка ГУ: старые числовые task ID не используются; до явного тапа
    приложения не запускаются (1.11.1).
21. Одновременно активировать Simulcast и Split: пока совместный ownership
    не доказан, вторая функция fail closed — не двигает задачи и оставляет
    экран рабочим, без объяснений (U5). Владелец один на процесс и берётся на
    срок: отпускание обязано работать на успехе, откате, отмене и падении, а
    срок страхует от колбэка, который не пришёл, — иначе закрытый отказ
    становится вечным. Разрешения спрашивают обе стороны и до первой команды:
    `OPEN` и `SELECT` — прежде чем открыть сессию, запуск проекции — прежде
    чем поднять мост. Исключений ровно два, и оба — про отказ от владения, а
    не про просьбу о нём: выключение тумблера разбирает сцену при любом чужом
    владельце (§11.31), и завершение проекции не блокируется никогда.
22. 100 `TYPE_WINDOWS_CHANGED` во время `SELECT`: выбор не ждёт очередь из
    100 reconcile и не применяется поверх более нового Home (раздел 7).
23. Краш приложения в панели при играющей музыке соседа: нативный исход
    зафиксирован (дописать в 1.7.3), автоперезапуска нет, наших поздних
    мутаций нет (1.7.3).
24. Toggle off при `APP | APP`: фокусное fullscreen с тем же task id, второе
    живо и видно в Recents, пикеров нет (1.2.3).
25. Камера заднего хода во время `SELECT`/`OPEN`: под захватом ни одной
    мутации; после выхода — корректный итог либо чистая отмена (1.11.5).
26. Выключение и включение зажигания во время операции: после рестарта
    ничего не доделывается само (1.11.1, U1).
27. Смена языка системы при живой сцене: приложения живы, пикеры
    перерисованы (1.11.6).
28. Смахнуть пикер в Recents: нативный исход зафиксирован, огрызков наших
    задач нет (1.7.4).
29. Два `SELECT` в разные панели подряд: оба приложения открыты, каждое в
    своей панели (1.5.5).
30. «Очистить всё» в Recents во время projection: задача навигатора живёт на
    приборке и не считается закрытой — его слот и projection переживают,
    остальные `APP`-слоты становятся `PICKER`, возврат навигатора работает
    (1.7.5, 1.10).
31. Выключить тумблер во время projection (в том числе посреди возврата):
    split-операции отменены без поздних мутаций, IVI-сцена разобрана по 1.2,
    навигатор жив на приборке, его последующий возврат даёт fullscreen
    (1.10.8).
32. Собрать штатный split штатными средствами, не имея продуктовой сцены, и
    выключить тумблер: чужой split цел, штатный пикер на месте, ни одной
    команды на его задачу (инвариант 2).
33. Довести нашу сцену до состояния, где нашей identity на главном экране не
    осталось, и выключить тумблер: выключение всё равно доходит до полного
    экрана, оставив штатный пикер в скрытом панельном корне. Это сторона
    отказа инварианта 2, и она единственная в этой паре ещё не проверена на
    машине.

## 12. Протокол живой приёмки

Приёмку на автомобиле проводит независимый агент с чистым контекстом. Он
знает только этот документ и ADB; внутренности реализации ему не сообщаются.
Вердикт выносится в терминах раздела 1.

### 12.1. Правила прогона

- Один владелец машины на сессию; методика — governance.md, «Firmware
  Behavior Method»; reset — по разделу «Acceptance reset» в
  split-screen-findings.md.
- Перед прогоном фиксируются: SHA-256 и versionCode установленного APK,
  прошивка, baseline (четыре ключа SmartMulti, состояние gate, area mode,
  снапшот root/task, `force_resizable_activities`, пустота crash-буфера).
- Каждый сценарий: reset → before-снапшот → ровно одна описанная
  последовательность действий → after-снапшот → сверка с ожиданием.
  Наблюдения: `am stack list`, `service call activity_task 30`,
  `dumpsys input` (фокус, указатель), playback через `dumpsys media_session`,
  `logcat -b crash`. Фазовый лог продукта читается с support-экрана (ринг
  диагностики); доставку своего тега в `logcat` продукт не обещает —
  logd этой прошивки фильтрует приложения по UID. Действия — только
  пользовательские (tap, keyevent, жесты), не внутренние API продукта.
- Красный сценарий останавливает группу (вертикальный срез P1.0 —
  исключение: его останавливают только собственные стоп-правила из 12.2).
  Любая запись `com.byd.avc` в crash-буфере — немедленная эскалация по
  правилу CLAUDE.md.
- Шаги с перезагрузкой ГУ или циклом зажигания — только при человеке у
  машины: канал управления (ADB через гейтвей) перезагрузку без него не
  переживает, а endpoint транспорта агенту заранее неизвестен.
- Приёмка идёт глазами пользователя и на машине в том состоянии, в каком её
  оставил пользователь: стерилизация системы запрещена, «грязная» машина —
  норма и часть проверки. Сброс между сценариями — только пользовательскими
  действиями (закрыть приложения, выключить тумблер, Home); хирургия
  (чистка prefs, force-stop) — только там, где сценарий явно требует особого
  состояния, и с фиксацией причины в evidence.
- Тайминги замеряются: каждый сценарий с действием пользователя
  сопровождается `screenrecord` либо серией timestamped `screencap`; секунды

### А.3. Архитектурные расхождения снапшота

1. **Критично: destructive init при выключенной функции.**
   `SplitScreenCoordinator.initialize()` вызывает `stopAsync()`; cleanup ищет
   также штатный `SplitScreenListActivity` и безусловно закрывает глобальный
   gate.
2. **Критично: overlay deadline не отменяет работу.** Таймер освобождает
   только окно; `openPickerSession()` без cancellation token продолжает
   ADB/move/restore.
3. **Критично: операции не транзакционны.** Gate, accessibility,
   resizeability, пикеры и приложения меняются по шагам; catch не возвращает
   изменённое к исходному снапшоту.
4. **Высоко: один блокирующий executor для всех событий.** Edge-ожидание —
   до ~15 секунд; Home, selection и launch стоят за старыми passive events.
5. **Высоко: accessibility-шторм.** Каждый `TYPE_WINDOWS_CHANGED` до
   фильтрации пытается запустить divider reconcile; in-flight флаги
   выбрасывают новые hints, старая queued job работает с другой сценой.
6. **Высоко: два неатомарных источника persisted truth.** Автомат с task ID
   и last-pair package сохраняются отдельно и в разном порядке.
7. **Высоко: task/root ID переживают process/reboot без epoch.**
8. **Высоко: self-client неоднозначен.** Пикер и приложение в одном package;
   часть проверок опирается на package; process init сам запускает
   координатор.
9. **Высоко: у навигации два жизненных цикла.** Reducer-путь
   `ProjectionReturned` практически недостижим; фактический return идёт
   отдельным синхронным путём вне актора.
10. **Средне: несколько поколений архитектуры в production-дереве.** Router,
    reducer, exported `SplitAppHost`, placeholder и их тесты при hardcoded
    explicit mode.
11. **Средне: тесты проверяют детали, но не координатор.** Подробный вердикт
    и категоризация — в разделе 10.

Два усиления, установленные независимой построчной проверкой 2026-08-23:

- `closePickers()` из `initialize()` при `DISABLED` не только закрывает gate:
  найденную foreground-задачу он перемещает в полноэкранный root, а при её
  отсутствии нажимает `KEYCODE_HOME` — холодный старт процесса способен
  увести пользователя с текущего экрана.
- Повторный тап кнопки получает мгновенный «успех» (`null`) и собственный
  overlay-lease вместо итога общей операции — что и наблюдается как «окно
  мигнуло и ничего не произошло».
