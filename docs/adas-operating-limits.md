# Пределы работы ACC, ICC и NOA

Владелец сообщил о потолке 130 км/ч и попросил проверить гипотезу о его
региональном происхождении и настройке в инженерном меню. Эта страница хранит
результат анализа Java-кода, native HAL и доступного состояния машины;
конкретный параметр снятия ограничения пока не установлен.

## Машина и границы проверки

2026-10-18 использован существующий ADB transport `127.0.0.1:5555`.
`ro.build.display.id=TP1A.220624.014 release-keys`,
`ro.build.version.incremental=eng.build20260705.011226`.
Названия старых каталогов корпуса не заменяют проверку установленного файла:
полные хеши 13 APK, `framework.jar` и `auto.default.so` совпали с текущей машиной.

Доказательства находятся в локальном, git-ignored каталоге
`captures/adas-speed-20261018/reports/`:

- `live-identity-hashes.txt` — модель, сборка и девять хешей с машины;
- `live-extra-menus.txt` — хеш CarResMgr и отсутствие `com.byd.countrycodetool`;
- `live-native-and-ecu-cache.txt` — дополнительные хеши с машины;
- `provenance.json` — сопоставление локальных и установленных бинарников,
  источники, границы проверки и ограничения декомпиляции;
- `jadx-*.log` — протоколы новых декомпиляций.

Первый проход включал чтение свойств и Settings, инвентаризацию пакетов,
вычисление хешей, проверку каталогов ECU-кэша и копирование APK на Mac.
Затем владелец разрешил самостоятельно открыть экран ADS через интерфейс.
Выполнена навигация в штатных настройках и BluetoothPhone; перед входом повторно
прочитан P=1. На предоставленном владельцем OPPO профиль Phone calls один раз
переключён off/on и возвращён в исходное включённое состояние: после этого
клавиатура машины стала активной. Подтверждённая по коду сервисная комбинация
открыла `VerificationActivity`, но обязательная авторизация остановила переход
до `LogControlAndTestToolsActivity` и `ADSVersionActivity`. На том этапе ответы
версий ADS не получены; позднее они прочитаны отдельным ограниченным пробником
по запросам из кода этого экрана — [результат ниже](#прямое-чтение-версий-ads).
Не выполнялись запись параметров ADAS, перепрошивка,
перезапуск головного устройства или проверки в движении. Позднее для
сравнения оформления карты установлен отдельный APK-пробник, описанный ниже.
Сам предел 130 км/ч в этой сессии известен со слов владельца.
Версия головного устройства не является версией ADS-контроллера.

Дополнительные APK и два словаря сопоставлены с машиной в
`reports/followup-provenance.json`; `reports/live-followup-hashes.txt` хранит
исходные хеши. Снимки интерфейса, включая личные идентификаторы, остаются только
в локальном git-ignored каталоге и не предназначены для публикации.

### Пункты конфигурации за меню

Дополнительно прослежены обработчики, а не только названия экранов:

- `LogControlAndTestToolsActivity.H()` создаёт разделы из локальных layout;
  `onCreate()` добавляет пять групп: логи, тесты, расширенная конфигурация,
  самодиагностика и версии. Успешная авторизация разрешает открыть эту Activity;
  её код уже находится в APK, для его анализа аккаунт не нужен.
- `offline_config` → `O(View)` → `StartActivityUtils.c(...,14)` →
  `VehicleConfigActivity`. `VehicleConfigManager.getPadConfigFromMCU()` и
  `getCarConfigFromMCU()` читают значения из конфигурационных слов, но список
  редактируемых полей берут из локальных `padconfig_*` и `finalconfig_*`.
  В Pad пять полей: тип силовой установки, преобразователь уровней, число
  динамиков, аудиопрофиль и тип карты. В Car три: число динамиков, аудиопрофиль
  AVAS и тип микрофона. Разрешённые варианты и идентификаторы сохранены в
  `reports/menu-vehicleconfig-items.json`.
- `res_mgr` → `StartActivityUtils.c(...,22)` → `CarResMgr.CipherActivity`:
  выбор профиля цвета кузова, обновление ресурсов и интервал их запроса.
- `setting_config` → `StartActivityUtils.c(...,31)` →
  `RecommendConfigActivity`: кнопка обновления рекомендаций через
  `RemoteClient.startReq`; редактора параметров ADS в этой Activity нет.
- `Cota.CloudConfigTestActivity` отображает интервалы запросов/кэша,
  переключатели статистики, список приложений и запрос ресурсов цвета кузова.
  `FeatureControlActivity` содержит тесты APN, плагинов, Android overlays и
  тестового сетевого окружения. `mock_acc_on/off` вызывает `AccModeMonitor`:
  это имитация состояния питания для COTA, не переключатель круиз-контроля.

Граница вывода: `VehicleConfig.StrategyConfigManager` отдельно принимает

### Прямое чтение версий ADS

2026-10-18 получены прямые ответы ADS через существующий ADB, без открытия

Изолированный `experiments/ads-version-probe/AdsVersionReadProbe.java` в первом

перебора адресов, смены диагностической сессии или доступа к записи.
Транспорт SDK: устройство 1033, TX `0xAA00010A`, RX `0x9900010A`, owner 5,
CAN request `0x712`, response `0x71A`, UDS service `0x22`.
Пробник работает через `app_process` с UID 2000, не устанавливает APK.

| Поле штатного экрана | DID | Полезные данные положительного ответа, hex | Отображение по коду OEM |

| ADS software | F195 | `A1BF1A061D00` | **4.14.07** |
| ADS hardware | F193 | `03170C0C00` | **0.0.3** |
| Host SoC | 0178 | `29171A0303` | **10519** |
| Host MCU | 0170 | `290F1A0106` | **10511** |
| Host MCU application | 0172 | `003EA6841D` | **1051100189** |

сохранён без трактовки как даты или калибровки. Эти версии не устанавливают

### Скрипты приборки и TOR

С машины прочитан каталог `/system/lib64/cluster_hmi.pck` (Godot 4.3.0,
PCK v2), затем только нужные диапазоны файлов. Полный пакет имеет размер

Прослеженная цепочка в этой реализации:

2. `cluster_hmi::PopupMsgHandle::OnDataItemUpdateString` (`0x446898`, ветка

   двух в little-endian и собирает `TOR_<номер>_L<уровень>`.
   Далее испускает `sig_adas_toast`.
3. `common_mgr.gd:602` соединяет этот сигнал с
   `middle_area_arbitrate.gd:695`; обработчик выбирает расположение и
   видимость предупреждения. `popup_zjd_mgr.gd:124` передаёт ключ в поиск.
4. `popup_json.gd:170` удаляет суффикс `_L…`, проверяет уровень 1–4 и
   выбирает запись словаря по `key`. `popup_zjd.gd:151` берёт `clusterText`
   и поля оформления. Для `TOR_144`/`TOR_145` это ранее найденные тексты о 130.

во входных данных. Это не устанавливает конкретный ECU-источник или его
условия срабатывания. FID `0x99000331` нельзя без дополнительного доказательства
называть физическим CAN arbitration ID. В Cells `CanReadThreadBase::GetInstance`

начальное значение которого —
`/sys/devices/platform/soc/4a80000.spi/spi_master/spi0/spi0.0/spidev_cluster`.
Это статическая точка входа реализации; поток устройства в сессии не читался.

1920×720. `bg_arbitrate.gd:119` при `oversea=true`, сцене карты и
поставщике `GAS=8` выбирает тёмную тему даже в дневной части суток;
при `false` применяется обычный выбор темы по времени суток.

В отдельном варианте 1920×480, `scenes_1920_480/drive_map/scripts/drive_map.gd:69`,
`false` скрывает маску. При `true` выбираются маски `cp` для supplier 9,
`aa` для 10 и `gas` для остальных. Значения поставщиков определены в
`common/global_define/hmi_def.gd:1364`.
Эти обработчики оформляют проецируемую карту; они не переключают поставщика,
не меняют маршруты и не открывают доступ к навигации. Регион и штатные
обработчики не изменялись; отдельное воспроизведение масок описано ниже.

Отдельного переключателя этого результата в просмотренном коде нет.
`common_mgr.gd:492` при старте берёт сохранённый `vehicle_id`, а
`recv_vehicle_code_id` (`:1042`) обновляет его по входному сигналу.
`set_vehicle_id` выбирает также разрешение, компоновку, пакет оформления
и набор сцен: подмена модели не изолирует настройку карты.
`scenes/telltale/scripts/telltale.gd:10` содержит `@export debug_is_oversea`,
но его setter подставляет тестовые значки; к карте он не подключён.
Для независимого переключения именно оформления потребовалось бы изменение
кода его обработчиков. Возможность загрузки такой правки на действующей
приборке не проверена.

### Пробник масок

По просьбе владельца сравнение двух вариантов подготовлено отдельным
пакетом [oversea-map-probe](../experiments/oversea-map-probe/README.md),
для центрального дисплея. В нём один сохранённый фрагмент штатной
`com.byd.launchermap`: в текущем месте виден указатель машины, но отсутствуют
картографические детали. Кадр Яндекса, просмотренный при подборе подложки,
в пробник не вошёл. Это сравнение слоя оформления приборки на снимке с IVI,
а не запуск штатной сцены Godot или переключение региона.

Четыре оригинальные ASTC-текстуры, shader и `drive_map.scn` прочитаны
из текущего `/system/lib64/cluster_hmi.pck`; MD5 совпали с каталогом PCK,
SHA-256 закреплены в подготовщике. RSRC-сцена разобрана автономным
`research/cluster-native/read_binary_scene.py` без исполнения ресурсов.
Центральные текстуры имеют фактический размер 1920×720 и растягиваются
до 2560×720. Боковые — 960×720, занимают x=0…960 и x=1600…2560.
В `oversea_mask.gdshader` RGB заменяется на #384858 или #CFDAE5 с сохранением
alpha. Граница PiP/AVM в этом пробнике выключена.

Корпус и протокол проверки:
`captures/oversea-map-probe-20261018/`. Сборка проверяет все входные хеши,
геометрию сцены, неизменную прозрачную середину и непрозрачные края обеих тем.
Сам APK не содержит автомобильных API и разрешений; параметры машины
не записывает. План live-проверки и reset записан в README пробника.
Обе темы, увеличение и закрытие проверены на display 0; новых записей
в crash buffer нет. Пользователь ожидал увидеть саму карту, а на пустом
исходном кадре заметен преимущественно градиент. Такой пробник не проверяет
появление картографических данных и не ответил на это ожидание. Он закрыт,
штатная `com.byd.launchermap` возвращена на передний план.

## Кэши и загружаемые сценарии

Дальнейшая трассировка ProductLineOTA установила источник описания ECU:

2026-10-18 проверен существующий локальный экспорт

| Поле | Значение |
| --- | --- |
| ecuId | `HTH-2021_ADC_BYD_00100001` |
| ecuSoftCode | `48450011DF83000000` |
| ecuSoftVer | `4.14.07` |
| ecuHardVer | `0.0.0` |
| ecuConfigCode | `000000000000000000` |
| ecuConfigVer | `0.00.00` |

Версия ПО совпадает с прямым ответом ADS, но аппаратная версия в кэше не равна
полученной 0.0.3. Нули нельзя считать доказательством отсутствия конфигурации:
код OTA использует их как значения по умолчанию. Возраст этого кэша не известен;
в нём нет `ecuDiaId`/`logicAddress`, поэтому связь записи с адресом 712/71A ещё
нужно было подтвердить. **Позднее в этот же день F194 ADS вернул точно такой же
код ПО, а сервер дал маршрут; связь подтверждена**, см. ниже. Имя ECU также не
доказывает изготовителя физической платы.

Соседний `needCheckEcuList.json` содержит пустой `ecuList` и восемь допустимых
CDN-доменов, в том числе `download-ota-cn.denzacloud.com`. Это список разрешённых
хостов, не адрес файла. Два уже выполненных экспорта установили отсутствие
стратегий `ota/result/strategy.json`, `ota_ghy/result/strategy.json`, файла
`ota/result/upgradeInfo.json` и ключа `ecuDiagnosisResultListInfo` у обычных
OTA-приложений. Отчёты — в `approved-export-{1,2}/files/report.json`.

По коду ProductLineOTA и обычного OTA восстановлен путь получения пакета:

1. `getEcuList` возвращает описание ECU, включая диагностические DID и адреса.
   Полный маршрут зависит от OTA-приложения; различия приведены ниже.
2. `checkVersion` возвращает `VehicleVersionInfo`: `strategy.sequence`,
   `targetPackageInfo`/`sourcePackageInfo`, `configPackageInfo`/`configSourceInfo`.
3. В записи `EcuVersionInfo.versionPath` находится URL; `fileName` формируется
   отдельно из адреса, кода и версии. Само знание локального имени ZIP не даёт URL.
4. `DownloadFileHelper.saveOrUpdateDownloadFileInfo` сохраняет `fileUrl`, имя,
   размер и состояние в **отдельный** `download_info_prefs.xml`, под ключом
   `DOWNLOAD_FILE_INFO_<url>`. Предыдущие экспорты эти файлы не читали.
5. После завершения/ошибки штатный код умеет удалять стратегии и пакеты;
   наличие этих файлов сейчас нужно проверять отдельно.

Указатели: `ProductLineOTA/.../api/base/download/DownloadFileHelper.java:222`,
`.../base/util/SpWrapper.java:24`, `.../model/EcuVersionInfo.java`,
`.../ui/vehicleota/checkversion/CheckVersionDownloadPresenter.java:713,1480`.
В обычном `OTAUpdatePlatformizedUI/.../api/base/download/DownloadFileHelper.java`
та же запись находится в `saveOrUpdateDownloadFileInfo`.

Запуск штатной кнопки проверки обновления не является изолированным чтением
списка: callback запускает диагностику, а обработчик HTTP-ошибок умеет сам
войти/зарегистрироваться. Эти процедуры здесь не запускались. Подготовлен
`tools/read_ads_package_metadata.py`: шесть фиксированных файлов метаданных и
списки шести каталогов sourceECU/targetECU; на машину он не пишет, ECU и сервер
OTA не опрашивает, прошивки не скачивает. Сырые preferences не сохраняет,
поля токенов и SecurityAccess исключает; сведения о декодировании пакета и URL
только подходящего ADS остаются в приватном локальном capture.

Доступный механизм такого чтения — штатный экспорт BydLogTool. Его
`FileTransferServer.start()` слушает все интерфейсы, а handler принимает также
команду удаления. Поэтому localhost-forward сам по себе не ограничивает доступ
к серверу на машине. Подготовленный клиент использует только list/read,
ограничен 20 секундами и 1 MiB на файл; перед отдельным запуском сервера нужны
ограниченное окно, device-side STOP-watchdog и проверка закрытия портов. Этот
сеанс был отдельно разрешён владельцем («один сеанс с автоостановкой») и
выполнен ровно один раз. Ранее выданные другому исследованию разрешения не
переиспользовались.

Результат этого сеанса:

- `com.byd.otaupdate` и `com.byd.otaupdate2`: оба `download_info_prefs.xml`
  имеют размер 65 байт и не содержат записей `DOWNLOAD_FILE_INFO_*`.
- У ProductLineOTA оба выбранных файла preferences отсутствуют; отсутствуют
  также `ota_productline/result/strategy.json` и `ota_ghy/result/upgradeInfo.json`.
- Все шесть проверенных каталогов `package/vehicle/{sourceECU,targetECU}`
  для `ota`, `ota_ghy`, `ota_productline` отсутствуют.
- Клиент успешно завершил проверку всех целей. Хост отправил STOP через
  0.903 секунды после взведения watchdog; отдельный device-side STOP через
  30 секунд подтверждён ответом broadcast. Порты 5320/5321/5322 закрыты,
  собственный forward и временные файлы удалены. Состояние и crash buffer
  совпали до/после. Это не доказывает отсутствие прошивки в других каталогах.

Перед экспортом менеджер диагностики оказался в `r@2_1&w@-1_0`;
первый preflight завершился **до запуска**. По коду `LogReceiver` и socket-классов
подтверждено, что START/STOP файлового экспорта не вызывает диагностический
менеджер; стартовый ZMQ DEALER отправляет только `CLIENT_REGISTER`.
Пробник к ZMQ не подключается. Поэтому второй preflight допустил это точное
состояние без его изменения и сохранил проверку свободных портов. После
единственного сеанса состояние осталось тем же. Позднейшее отдельное чтение
увидело idle; это не результат нашего STOP.

Доказательства: `reports/ads-acquisition/approved-export/session.json`,
`files/report.json`, `files/01-metadata.json`, `files/02-metadata.json`;
ранний отказ — `preflight-abort/session.json`. Разрешение на этот сеанс израсходовано.

| `com.byd.otaupdate2` (GHY) | `https://api-ota-cn.denzacloud.com/` | `client-service/fota/api/v1/service/getEcuList` | `/collect2/SourceVehicleVersion` |

`VehicleVersion2` равен V1.0: для запроса основного клиента нужен именно первый
файл. Это не значение версии ADS 4.14.07.

Конструктор основного `Api` восстановлен отдельно в simple-mode:
`reports/ads-acquisition/OTA-Api-simple.java`. Он выбирает сервер марки и
вызывает `SecurityUtil.getGcyDefaultSslParams()`. Последний использует
`SecurityKeyUtil.getPrivateKeyGcy()` / `getPublicCertGcy()`; `SafetyUtil`
читает типы 12/11 через `FUNCTION_OTA_GET_CERT`. Код сохраняет резервные
`files/dkey.key` и `files/dcrt.crt` внутри приложения. Их наличие на машине
на первом этапе не проверялось. **После нового прямого разрешения владельца
эти два файла и сохранённый токен прочитаны в память и использованы успешно**,
см. ниже. SafeKey для этого не вызывался. Публичные CA берутся из assets APK.

Без передачи идентификаторов машины проверено TLS-соединение с основным сервером.
Стандартное хранилище доверия не подошло. OpenSSL с публичными CA из APK,
`-partial_chain`, проверкой подписи и имени сервера успешно установил TLS 1.2
**без клиентского сертификата**. Это подтверждает доступность сервера и его
цепочку, но само по себе не доказывает достаточность такой сессии для OTA API.
Настройка клиентского сертификата в APK также не доказывает, что сервер
потребует его для каждого метода. Протокол — `ota-tls-openssl.txt`.

Затем выполнен **один** POST на
`https://fota-tsp.denzacloud.com:6113/ota/otaService/getEcuList` с телом
`{"version":"V1.7.0","uuid":""}`, без Authorization, VIN, клиентского
сертификата/ключа. Использованы публичные CA из APK, проверка TLS не отключалась;
лимит 10 секунд / 128 KiB, без redirect/retry. Ответ: **HTTP 400**,
`No required SSL certificate was sent` (202 байта HTML). Таким образом,
клиентская идентификация действительно нужна для этого проверенного маршрута.
Эта ошибка ничего не говорит о пригодности токена или наличии обновления ADS:
до обработки запроса приложением сервера мы не дошли. Login/register,
`checkVersion`, отчёты и запросы подписи на том первом этапе не выполнялись.
Доказательства — `unauth-geteculist-headers.txt`,
`unauth-geteculist-response.html` и `evidence.json`.

Тогда работа остановилась перед использованием клиентской идентификации:
прежнее разрешение было на шесть файлов метаданных, не на ключ/сертификат/токен.
**Этот барьер снят следующим прямым указанием владельца использовать штатный
сертификат для получения метаданных, прошивки и конфигурации ADS.** Результаты
нового ограниченного чтения и запросов приведены далее. URL пакета не получен.

В текущем проходе ADB подтвердил прежний профиль170/сборку и autoservice PID135;
состояния менеджера и обоснование файлового чтения при занятом reader приведены
выше. Пассивный запрос выбранных OTA-тегов logcat вернул пусто.
Оба известных OTA-архива инвентаризированы по ZIP-каталогу: отдельного пакета
ADC/ADS в корне нет (IVI содержит Android/Anc/Dsp/Mcu/Screen, FSE — update/DSP/MCU).
Это не полная отрицательная проверка содержимого всех разделов. Точный поиск
кода ПО и ECU ID в публичном веб-поиске не дал результатов; руководства вместо
прошивки не использовались.

### Аутентифицированные метаданные OTA

По новому разрешению владельца `tools/ads_ota_metadata.py` прочитал ровно пять
файлов: штатные `dcrt.crt`, `dkey.key`, `share_data_prefs.xml`, текущую

Выполнены четыре ограниченных сеанса файлового чтения: две первые попытки

Первая ошибка была недостаточно детализирована (`https_failed`). Во второй
локально подтверждено `ERR_SSL_CA_MD_TOO_WEAK`, `stage=tls_setup`,
`requestStarted=false`: штатный клиентский сертификат RSA-2048 подписан SHA-1.

цепочки и точного SHA-256 отпечатка серверного сертификата сохранена. Сервер
предварительно независимо проверен с обычной политикой OpenSSL, CA из APK и
partial_chain. Это не отключение TLS-проверки и не свидетельство истечения
срока сертификата машины.

### Аппаратная авторизация GHY

Исследован matching `OTAUpdate2.apk`, SHA-256
`1529790d11ecf3c3a6883096f30a685e9af6ca3c6d57eb4359daec90a7afdb04`.
`CheckVersionDownloadPresenter.loadEcuListInfo` отправляет только
`version` и собственный `upgradeUuid` на
`https://api-ota-cn.denzacloud.com/client-service/fota/api/v1/service/getEcuList`.
Заголовок — `Authorization: basic<user_token>` из настроек **com.byd.otaupdate2**.
`/collect2/SourceVehicleVersion` отсутствует; `VehicleOTAUtil` в этом случае
возвращает **v1.0.0**. Это точный штатный fallback, не подставленная версия GCY.

Важная поправка к чтению Java: `SecurityUtil` передаёт null KeyManagers,
но `Api` выбирает **BYD_TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256**. Из null нельзя
заключать, что GHY не требует клиентского сертификата. `SecurityKeyUtil` и
`SafetyUtil` различают аппаратную GHY-цепочку и GCY public/private slots11/12.
Проверка сервера без учётных данных дала доверенный TLS1.2 и имя хоста, но
последующий HTTP-шлюз потребовал клиентскую идентичность.

| Попытка одного getEcuList | Результат | Доказательство |
| --- | --- | --- |
| Собственный токен GHY, без client certificate | HTTP400, «No required SSL certificate was sent» | 230 байт, SHA-256 `c9388859587ae2ba40265df5502a9b5343e8926f589990024400bdbad75c41c3`; тот же ответ на публичный GET / без учётных данных |
| Тот же GHY-формат со штатным GCY-сертификатом | HTTP400, «The SSL certificate error» | 208 байт, SHA-256 `54440431d379900ee2cb05fdedc4f84b013dad56efdf38a1211ddac3524092f2`; точное совпадение с проверенным шаблоном ошибки nginx |
| Аппаратный сертификат GHY, собственный GHY-токен | **HTTP200 / status100 / ecuList=[]** | Успешный mutual TLS, одна подтверждённая подпись, полный разобранный HTTP-ответ |

В рабочей попытке прочитаны public certificates selectors5/6/7 через
`safekeyservice`, function10102/transaction14; выполнена ровно одна подпись
TLS function10106/transaction6, параметр0x01003100. Отпечаток leaf —
`8a220bf91c7d9eefba6b942665413dfc5d3c0a2ac8b6e4a45bb89cd899fad832`,
отличный от GCY `5baa0eaf…`. Библиотека safekeyservice предварительно сверена
с изученным SHA-256, цепочка и подпись проверены локально. Закрытый аппаратный
ключ не экспортировался. Серверный CA, hostname и заранее проверенный leaf pin
проверены **до подписи**, без снижения уровня TLS-проверки.

Клиент `tools/ads_ghy_factory.py` + `tools/ads_ghy_factory_tls.c` использует
Mac TCP/443 и только аппаратную подпись машины через существующий ADB.
Нет login/register, versionSync, отчётов, checkVersion, диагностики ECU,
перезаписи кэшей или обновления. При пустом ECU-list штатный GHY-код сам
вызывает onFail до проверки пакетов; выдумывать ECU-list для продолжения нельзя.
Пустой ответ относится к этому запросу/версии/машине, не доказывает отсутствие
пакетов ADS на всём сервере.

Три файловых сеанса имели device-side STOP через30 секунд и ранний host STOP;
во всех подтверждены закрытые5320/5321/5322, удаление forward/своих staging-файлов,
неизменность проверяемых свойств/PID и crash buffer. Аппаратная crypto-операция
не классифицируется как чистое чтение: штатные API могут внутренне
инициализировать/восстанавливать чип. Прямых команд смены PIN/ключей не было.
После неё проверенные свойства/PID и crash buffer также не изменились.
Public certificates были только во временных файлах0600 в каталоге0700,
удалённом после TLS; токен/UUID и ответы с личными полями не сохранены.

Перед машиной рабочий клиент прошёл независимый локальный TLS-сервер с
синтетическими ключами: обычный/фрагментированный chunked-ответ, неверные
hostname/CA, неверная подпись и попытка вставки заголовка. Ещё четыре случая
проверяют отказ на неполном/неоднозначном HTTP. Все проверки прошли.
Артефакты: `captures/adas-speed-20261018/reports/ads-ghy/`, планы, snapshots
фактически запущенного кода, `run-{1,2,3-factory}`, хеши и верификация.
Прошивка и конфигурационный пакет этой веткой **не получены**.

После получения серверных DID allowlist пробника расширен на F194/FF95/FF94.

| --- | --- | --- | --- |
| F194 | код ПО | `48450011DF83000000` | `48450011DF83000000` |
| FF95 | версия конфигурации | `000418081604` | **0.00.04** |
| FF94 | код конфигурации | `4845FF11E083000319` | **4845FF11E083000319** |

доказательством отсутствия конфигурации или установленной причиной status111.
Штатный `DoipDiagnostic.requestDataByDid` предварительно вызывает
`requestSessionControl(3)`; для нашего чтения этот путь не использовался.

P/ручника/нулевой скорости и `UNREGISTERED`. После каждого запроса проверены
idle менеджера, неизменные autoservice135/BydLogTool4822 и crash buffer.

`f8a286b50b5364bd309ce930be3307b3ce202d15c1273ddb0c743bc21548bbec`, DEX
`8b158b7ac14011a15ee435f16e9ab35f1abea973427e31fd8d703cb48d9537ae`.

показывает содержимое памяти `yqzx_service` или другого контроллера.

Оставшиеся пять кандидатов получили статус `missing` от нашего клиента.
Граница этого результата: `FileTransferHandler.handleList()` штатного
BydLogTool отвечает ошибкой 1 при `!exists()`/`!isDirectory()`, но также
возвращает успешный пустой список при `listFiles() == null`. Наш клиент
объединяет отсутствие каталога и отсутствие имени в списке в один статус.
Поэтому доказано лишь, что эти файлы **не получены через экспорт**, а не
физическое отсутствие всех кэшей или облачных параметров. Другие пакеты,
временные ресурсы и память приложений в этот сеанс не читались.

STOP с хоста отправлен через 0,560 с после постановки watchdog; после
30-секундного watchdog отдельно подтверждены его успешный STOP, отсутствие

Прошивка и настройки не менялись, облачных и диагностических запросов не было.

## Что осталось неизвестным

**Не найдено место, где штатно снимается потолок 130 км/ч на этой машине.**
Поиск сузил задачу: проверенные настройки головного устройства описывают
следование знакам и пользовательские предпочтения; подтверждённой связи с
максимумом ассистента нет. Гипотеза о калибровке/прошивке контроллера ADS
остаётся гипотезой. Получены прямые идентификаторы этого ADS: ПО **4.14.07**,
аппаратная версия **0.0.3**, bootloader **2.3**, версии Host SoC/MCU — в таблице
выше. Его исполняемый код и калибровки в этой сессии не получены и не разобраны.

Аутентифицированное описание ECU GCY уже получено; его сертификат и токен
работают. Отдельная аппаратная авторизация GHY тоже подтверждена, но его
getEcuList вернул пустой список. Локальный выбранный кэш пакетов пуст, а GCY возвращает 111 без
URL даже с прямо прочитанными идентификаторами конфигурации. Для получения
образа ещё нужен подходящий пакет/его серверный versionPath либо доказанный
способ чтения содержимого контроллера.
Прямой DoIP-транспорт уже подтверждён, но запрос каталога в текущей сессии
отвергнут; расширенная сессия не проверена из-за отрицательного ответа на F186.
Идентификатор конфигурации известен: `4845FF11E083000319`, версия 0.00.04.
Дополнительный заводской OTA-путь пока остановился на DNS с Mac.

установить штатного вызывающего клиента, значение запроса и удалённого
поставщика сервиса. Наличие этих имён не доказывает доступ к калибровке ADS.
Дополнительный поиск прямых Java-вызовов оказался отрицательным в описанных
границах. Готовые IDC-журналы зашифрованы; разрешённое чтение исходного каталога
подтверждено, но сам журнал не прочитан из-за проверки размера. Следующий
экспорт, если понадобится, требует нового разрешения: одноразовый сеанс уже
завершён. Нельзя считать журналы заменой пока не полученным образу и калибровке.

следующий содержательный шаг — сравнение исполняемого кода и конфигурации

известного изменённого варианта, привязанных к полученным идентификаторам.
Полный номер аппаратной детали, идентификаторы экспортного блока и происхождение
образов ещё нужны, чтобы не принять отличие другой комплектации за найденный предел.
