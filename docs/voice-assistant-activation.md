# Голосовая активация со всех мест салона

Исследование для [прототипа помощника](voice-assistant-architecture.md): как
перейти от кнопки к обращению голосом и сохранить слышимость пассажиров.
Содержит исследование прошивки и ограниченную живую проверку захвата микрофонов;
в ветке прототипа добавлен собственный детектор, качество фразы и мест в салоне пока открыто.

**Open questions**

- Как каналы PCM соответствуют микрофонам и опорному звуку? Проверить по

- Достаточен ли обычный моно `MIC` для всех мест? Проверить тем же набором фраз

## Звук салона

В `audioflinger.txt` активный вход `VOICE_RECOGNITION` имеет 16 кГц,
PCM16, **Channel count: 10**, **index mask 0x800003ff**. В audio policy есть
`tenchannels input` с этой маской, `maxOpenCount=1`, `curOpenCount=1`.
Это ограничение числа аппаратных входов, само по себе оно не доказывает
ни возможность, ни невозможность второго клиента общего потока.

`audio.txt` описывает тот же поток как `11ch`. Для index mask нужно смотреть
AudioFlinger и число установленных битов, а не это форматирование. Более
ранний дамп от 2026-08-25 аналогично пишет `9ch`, тогда как AudioFlinger
показывает **8** и маску `0x800000ff`. Имена пакетов у записи с UID 1000
меняются (`com.byd.avc`, `com.byd.drivemode.service`, `com.byd.xcall`): shared
UID не позволяет по этой подписи приписывать запись конкретному приложению.

Код `RecorderConfigProducer` задаёт 16 кГц, PCM16, index mask и переупорядочивание.
В движке `com/byd/autovoice/j/a.java` (`AudioRecordTask.b`) это буквально:

```java
new AudioRecord.Builder()
    .setAudioSource(6) // VOICE_RECOGNITION
    .setAudioFormat(new AudioFormat.Builder()
        .setEncoding(2) // PCM16
        .setSampleRate(sampleRate)
        .setChannelIndexMask(channelMask)
        .build())
    .setBufferSizeInBytes(bufferSize)
    .build();
```

`CAR_TYPE.java` относит 168/169 к `SZ`/`SZ_NO_HIDDEN`, задаёт 10 входных
каналов и 6 зон. `com/byd/aiSpeech_processor/g/g.java` указывает ресурс:
`sspe_nnaec_mcfnr_wkp_10ch_6mic_4ref_6zone_...BYD_SZ_HM_...bin`
либо вариант `NHM`. Название и конфигурация показывают штатную схему
«6 микрофонов + 4 опорных канала», но не назначение каждого индекса PCM
и не доказанный выбор HM/NHM на текущем запуске.

`AISpeechMvwImpl` подаёт сырой многоканальный звук в `AIFespCarEngine`.
`onResultDataReceived(byte[], byte[])` отдаёт раздельные обработанные данные
внутреннему callback. Следовательно, обычный моно `MIC` нельзя автоматически
считать готовым штатным потоком нужного места с тем же эхоподавлением.

## Штатное пробуждение

Цепочка в исследованных APK:

```
AudioRecord: салонные микрофоны и опорные каналы
 → AIFespCarEngine: обработка, зоны, wake word
 → BaseProcessor.handleWakeUpSuccess
 → ProcessorCallBackImpl.e(Bundle)
 → основной MvwListener
 → MvwListenerImpl.W4
 → MVWHandlerManager.A / SoundAreaMerge
 → штатный диалог и команда с позицией говорящего
```

В Bundle есть `wakeupWord`, `mvwSceneId`, `wakeupWordId`, `mvwDoa`,
`mvwType`, `sessionId`. Само событие уже содержит позицию, её не надо
угадывать по экрану или кнопке.

В `IStateManager` есть зоны 1/2 (передние), 3/4 (задние), а также
отдельные значения третьего ряда. Не переносить знак/нумерацию между
сырой зоной движка, `SEOPT_BEAM` и целевым местом исполнения: в коде
есть преобразования. Для «открой моё окно» нужна проверенная карта мест;
сама способность услышать фразу с любого места такой карты ещё не даёт.

## Подключение к движку

В манифесте `com.byd.autovoice.engine` экспортирован
`com.byd.autovoice.service.SpeechEngineService`, action
`com.byd.autovoice.action.engine.speech`, без permission на сервисе.
`onBind` возвращает `EngineManagerImpl`. Прочитанный Binder-диспетчер
проверяет interface token, но не подпись/UID. Это отдельный интерфейс:
закрытость `com.byd.autovoice.permission.thirdapp` не доказывает его закрытость.
Доступ с обычного app UID пока не проверен.

**Подключение не равно безопасной подписке.** Главный Binder:
descriptor `com.byd.autovoice.engine.speech.EngineManager`, transaction 3
с одним `int engineType` возвращает `MvwEngine`; transaction 5 возвращает
глобальный `RecordEngine`. Первый вызов только получает интерфейс, второй
не выдаёт PCM: его метод меняет состояние общей записи.

`MvwEngineImpl.c0` (transaction 1, регистрация listener) вызывает
`ProcessorCallBackImpl.H`. Последний делает
`map.put(engineType, listener)` в слоте Android-пользователя.
`ProcessorCallBackImpl.e` отправляет главное пробуждение в `w(1).get(0)`.
Другой слушатель с тем же слотом заменит штатный; другой `engineType`
не станет независимым получателем главного события.

В `MvwEngineImpl` действительно есть `RemoteCallbackList`, но путь доставки
главного пробуждения использует **один** listener из map. Отписка удаляет
запись только из `RemoteCallbackList`, прежний callback не восстанавливает.
Аналогично `SrEngineImpl` хранит одного актуального слушателя на слот.
Нельзя проверять эти регистрации на машине как якобы безвредное чтение.

Возможный отдельный исследовательский путь — явная замена клиента движка
с сохранением его фронтенда. До практического решения не хватает выдачи
обработанного PCM, разделения штатных/наших диалогов и восстановления callback.
Это не первый шаг кнопочного прототипа.

`action_autovoice_wakeup_mictest` отправляется при входе в диалог, но без
места/слова; это не перехват с отменой штатного ответа. Парсинг logcat тоже
не заменяет контракт: у машины встречается `log.tag=M`, видимость события
не гарантирована и штатный диалог уже запускается.

## Предлагаемая активация

Для независимой русской фразы — свой детектор слова активации (KWS),
использующий салонный звук. Кнопка и детектор вызывают один и тот же вход
текущего помощника. Первый пробник должен сравнить моно и многоканальный путь;
усложнять обработку нужно по результатам слышимости, а не по числу каналов.

Целевая схема при необходимости многозонного захвата:

```
один AudioRecord / microphone FGS
 → проверенная карта каналов микрофонов и опорного звука
 → эхоподавление / шумоподавление / выбор речевой зоны
 → лёгкий KWS, отдельно учитывающий зоны
 → арбитр одного срабатывания + позиция + кольцевой буфер
 → краткий сигнал и временное приглушение музыки
 → существующие VAD → ASR ru/en → парсер → исполнитель
 → короткое окно продолжения → снова KWS
```

- Не усреднять все 10 каналов: среди них опорный звук, в том числе собственная
  музыка машины. Даже сырые микрофоны нельзя без проверки усреднять по фазе.
- Сначала можно выбирать канал с лучшим отношением речи к шуму, сохраняя
  кандидатов других зон. Максимум общей громкости не равен месту говорящего.
- Кольцевой буфер примерно 1–2 с нужен, чтобы не потерять начало команды в
  «слушай, машина, закрой окно» без паузы. Это параметр проекта, не замер.
- До активации тяжёлый ASR выключен, но захват и KWS работают постоянно.
  Обещание «ноль CPU до кнопки» к этому режиму неприменимо.
- До слова активации музыка ещё играет. Приглушение **после** срабатывания
  облегчает распознавание команды, но не решает обнаружение самого слова.
  Для близкого к штатному качества нужны AEC/опорный звук либо доказанная
  устойчивость выбранного аудиотракта к музыке.
- Службу типа `microphone` сначала запускать из видимой Activity после
  предоставления `RECORD_AUDIO`, затем проверять уход в фон. Автозапуск после
  сна/смерти процесса — отдельная проверка, `appops allow` её не заменяет.
- При звонке, занятом/заглушённом входе или смене устройства детектор должен
  приостановиться и показывать причину. Проверять `isClientSilenced`, устройство
  и фактический формат через `AudioRecordingCallback`.

Временный вариант со штатным детектором — обычное голосовое «открыть наше
приложение», у которого есть явный вход в режим слушания. Путь открытия по
имени уже известен в [Shortcuts findings](shortcuts-automation-findings.md#registration-apis-and-adjacent-paths).
Он сохраняет штатное пробуждение с мест пассажиров, но требует китайского
обращения/команды запуска; это не собственное русское слово и не доказательство
слышимости последующей русской команды из нашего `MIC`. Новый сценарий не запускался.

## Слово активации

Фраза выбирается отдельно от языка команд. Для первой проверки тракта можно
взять английскую фразу: у sherpa-onnx есть готовый KWS `zh/en` на 3 млн
параметров с Android-вариантом. В официальном каталоге KWS нет заявленной
готовой русской модели; наличие русского **ASR** не означает русский **KWS**.

Для русской фразы быстрый исследовательский вариант — Vosk small ru с
ограниченной грамматикой, отказом `[unk]` и проверкой целой фразы. Проверить,
что каждое слово и `[unk]` реально присутствуют в словаре модели. Это ASR
с ограниченным словарём, его постоянную нагрузку и ложные срабатывания надо
измерить; для лёгкого итогового режима предпочтителен отдельно обученный KWS.

На 2026-10-16 openWakeWord заявляет поддержку английского; официальный список
языков Porcupine также не включает русский. Они не являются готовым решением
для произвольного русского «Привет, Денза» без дополнительной разработки.

Штатный `CustomWakeDialog.l0/k` фильтрует ввод выражением `[^一-龥]`.
`AISpeechMvwImpl` рассчитывает пороги через `evaluatePinyin`. Простая запись
русского имени в настройку не является подтверждённым русским wake word.

## Чего ещё не знаем

Проверка Навигатора 2026-10-11 показывает одновременно несглушённые
системный поток и обычный моно `MIC` в видимой Activity
(`captures/alice-navigator-20261011/live-semantic-button/audio-2.0.txt`).
Сегодняшний `audio.txt` также содержит историю несглушённых записей Навигатора.
Это доказательство сосуществования потоков в тех условиях, не акустическое
испытание пассажирских мест и не доказательство фонового захвата.

> **Superseded 2026-10-16:** ограничение «только чтение, запись из нашего UID
> не проверена» снято [проверкой фонового захвата](#проверка-фонового-захвата).
> Свой wake word, качество с каждого места и распознавание на выходе штатного
> фронтенда по-прежнему не проверены.

## Проверка фонового захвата

2026-10-16, N9 `AutoType=168`, те же голосовые APK по SHA-256. По просьбе
владельца диагностика добавлена в существующий пульт ветки
`codex/vehicle-control-remote`, а не в ещё один APK. Установлено обновление
`dev.denza.vehiclecontrol.probe` **0.3.5 / code 9**, SHA-256:

`8f0d2a5f44d67fcb47c11183bf4f8d9c37e80a92510a39b66f6d2ed89718678b`.

`MicrophoneProbeActivity` видима первые семь секунд и намеренно закрывается.
`MicrophoneProbeService` продолжает захват 30 секунд в FGS типа `microphone`:
PCM16, 16000 Гц, `VOICE_RECOGNITION`, index mask `0x3ff`, обычный **UID 10132**.
Нет ASR, аудиофокуса, vehicle controller или сохранения PCM. Уже разрешённый
ключ пульта используется пассивно и только для `dumpsys audio`: один контроль
штатной записи не чаще двух секунд. Изменение/глушение/исчезновение штатной
сессии или ошибка чтения останавливают диагностику без повтора.

| Прогон | Время захвата | Отсчёты на каждый из 10 каналов | Сессия пробника | Штатная сессия |
| --- | --- | --- | --- | --- |
| `tench-01` | 30019 мс | 479680 | 505 | 161, не менялась |
| `tench-02` | 30036 мс | 480000 | 513 | 161, не менялась |
| `tench-03` | 30019 мс | 480000 | 521 | 161, не менялась |

В каждом прогоне 29 отчётов с `silenced:false` и 15 дополнительных проверок
штатной записи, тоже `silenced:false`. AudioTimestamp продвигается. В
AudioFlinger во время фоновой фазы — **две активные дорожки одного 10-канального
входа**, обе `800003FF`, 16000 Гц, source 6, `Sil=n`. У штатного клиента PID
4398 / session 161 растёт Server frame counter; у пульта отдельный PID 25316
и отдельная сессия. В `activities` на переднем плане Launcher, диагностическая
Activity закрыта. После остановки остаётся одна штатная дорожка.

Все десять слотов получают одинаковое количество отсчётов; это **не десять
независимых микрофонов**. В тишине каналы 0/1/4/5/8/9 имеют разный живой
сигнал; пары 2=3 и 6=7 почти постоянны, в третьем прогоне их пики выросли
до 2141 и 1545 соответственно. Это согласуется с четырьмя
опорными каналами, но акустическая карта мест этим не установлена.

Первые попытки голосового вызова были неоднозначны: владелец не успел понять
порядок, затем сообщил об отсутствии ответа, а после отметил нестабильное
произношение даже без пробника. Они не доказывают конфликт захвата. В третьем
прогоне владелец вызвал штатного помощника китайским обращением и подтвердил
«работает». Одновременно `sys.voice.windowshow` и `sys.bydvoice.vr.state`
стали `1` в секундах устройства **1792147710–1792147711**, внутри 30-секундного
захвата; собственная запись и штатная дорожка при этом не заглушались.

Хэш приватного ADB-ключа и SHA-256 `files/actions/actions.jsonl` до/после
совпали. PID штатного клиента/движка остались **4398 / 4873**. Crash-журнал
не получил новых строк. Диагностическая служба остановлена, обычный экран
пульта восстановлен. Команды машине не исполнялись. 55 JVM-тестов,
`assembleDebug` и `lintDebug` прошли.

**Вывод:** на этой N9 обычное приложение может получать все 10 каналов в фоне
рядом со штатным помощником, сохраняя его голосовое пробуждение в проверенном
сценарии. Фоновая фаза была около 23 секунд, это не soak. Телефонный звонок,
сон/перезапуск, другая прошивка и качество со всех пассажирских мест остаются
непроверенными.

Артефакты: `captures/voice-activation-20261016/probe-035/`: `build.json`,
`analysis.json`, `tench-0{1,2,3}-events.jsonl`, `*-summary.json`, дампы

Источник пробника и способ повторить —

## Следующий эксперимент

Текущий режим уже живёт отдельно от исполнителя в `experiments/vehicle-control-probe/`; исходный план отдельного `voice-probe` заменён по указанию владельца. Оставшаяся приёмка:

1. **Закрыто для точного 10-канального варианта на N9** проверкой выше; моно
   сравнение по акустическому качеству ещё открыто. В видимой Activity получить
   разрешение и запустить `microphone` FGS.
   Проверить обычный `MIC`, затем отдельным запуском точную штатную конфигурацию
   `VOICE_RECOGNITION`, PCM16, 16 кГц, index mask `0x3ff`. Не перебирать
   параметры и не трогать `RecordEngine`/регистрации listeners.
2. **Закрыто в трёх ограниченных прогонах для 10 каналов.** До и после каждого варианта снять AudioFlinger/audio policy/recording config,
   подтвердить, что системный поток жив и не заглушён. Если второй клиент
   мешает штатному — остановить пробник и зафиксировать отказ.
3. При владельце записать ограниченные фрагменты одинаковых фраз с **каждого
   реального места**, включая третий ряд, если он есть: тишина, музыка, климат,
   затем дорожный шум. Разметить микрофоны/опорные каналы и сравнить с моно.
4. На этих записях сравнить детекторы: пропуски по каждому месту, ложные
   активации на час разговора/музыки, задержка. Порог нельзя оценивать только
   на произнесениях самого слова. CPU/RSS замерить на головном устройстве.
5. Повторить при скрытой Activity, в split, при звонке и после сна/пробуждения.
   Проверить фразу «слово + команда» без паузы, команду после сигнала и короткое
   продолжение. На этом этапе команды только показываются, не исполняются.

Результат первого этапа — выбор пригодного источника и доказательство
сосуществования. Результат всей серии — проверенная активация со всех мест.
До этих проверок нельзя обещать качество штатного ассистента.

## Прототип своей фразы

В существующем `:vehicle-control-probe` ветки `codex/vehicle-control-remote`
установлена0.3.8/code12: отдельные `WakeProbeActivity` / `WakeProbeService`.
Вызов только отмечается на экране, классы не связаны с контроллером автомобиля.
**Слушать** включает microphoneFGS до10мин; **Оставить в фоне** сохраняет его,
Back/возврат/остановка выключают. Только `dumpsys audio` через существующийADB,
без аудиофокуса, vendorcallbacks и команд автомобилю.

Поток source6/index0x3ff, PCM16×10/16кГц. Проверки своей конфигурации1с и штатной
записи5с останавливают пробник при потере, глушении или изменении штатного
потока. Наблюдавшиеся микрофонные кандидаты0,1,4,5,8,9 используются для речи;
2,3,6,7 исключены как опорные. Нет утверждения о физическом порядке микрофонов.
В памяти до5с моно,200мс предыстории, один выбранный на начало речи микрофон.
RawPCM не сохраняется; пишутся только последние текст/оценки/уровни/времена.

В словаре закреплённой VoskRU0.22 нет `денза`, но есть `ден`, `дэн`, `за`.
Узкая фонетическая грамматика сама по себе ошибочно принимала синтетические
«Привет, Денис» / «Привет, где заправка», поэтому кандидата проверяет полный
словарь.60JVM-тестов, сборка и lint проходят;2положительных/7отрицательных
синтетических реплик через реальный Java gate/gain и hostVosk дают нужный ответ.
Это не оценка качества в салоне. В0.3.6 владелец подтвердил отметку, обе модели
дали `привет дэн за` за332мс, полный confidence имени0.519391 возле порога0.5.

**Нестабильное имя подтверждено диагностикой0.3.8.** В реальных последующих
вызовах узкий детектор давал `привет дэн за` сconfidence1, а полная модель
`привет бензо` (0.747864/1 для второго слова) и отклоняла фразу по несовпадению.
Это доказанный путь конкретных отказов после успешного захвата, а не потеря
доступа к микрофону. Какая доля всех пропусков связана с ним, пока не измерено.

В0.3.6 распознавание и калибровка были связаны, а фильтры работали без ясной
обратной связи.0.3.8 заменяет это живыми уровнями, фазами «слышу речь» /
«распознаю», полным **Услышано** каждой реплики, явной причиной отказа и
счётчиками. Калибровка больше не требует успешной активации/ASR:60с на кресло,
3захвата с0.3..4с озвученных кадров и началом после выбора заменяют профиль.
Сохраняется средний нормированный вектор6уровней. Владелец подтвердил3/3 со всех6кресел, JSON содержит18образцов; старый одиночный водительский образец заменён новой тройкой.

Порядок6мест: водитель, передний пассажир, второй ряд слева/справа, третий
слева/справа. После6×3 сравнение cosine>=0.94 и отрыв>=0.015 дают
«предположительно: …», иначе «место не определено». Это оценка по уровню,
не штатнаяDoA/beamforming/AEC. Точность всех мест/шумов ещё не принята.
Промежуточная0.3.7 для одного водителя была собрана, но не устанавливалась;
владелец выбрал калибровку всех6мест.

Установленная0.3.8 SHA256

проверена после `install -r`; ключADB, журнал действий и прошлый профиль
