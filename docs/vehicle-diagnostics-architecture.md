# Диагностика автомобиля: архитектура

Раздел «Сервис → Диагностика»: автоскан блоков машины, их память ошибок,
потоковые данные OBD, идентификация и системные экраны (высоковольтная часть,
ВВБ, привод, тормоза, ассистенты). Только чтение. Документ владеет устройством
раздела: транспортом до блоков, белым списком запросов, каталогом блоков,
движком опроса, моделью экранов и порядком приёмки. Факты о машине — что
отвечает, коды, прогоны — остаются в
[vehicle-data-findings.md](vehicle-data-findings.md#diagnostics-and-dtc-2026-10-18).
Вид экранов — холст «Диагностика · инженерное меню», страница «Сканер (v3)»,
одобрен владельцем 2026-10-20: <https://claude.ai/artifact/KKgyNjETKzx6kxxbzMZBim>.

Решение владельца 2026-10-20: раздел — строка в «Сервисе», без своего значка в
лаунчере и без отдельного APK. Отдельный APK не может: диагностике нужен shell,
а новая ADB-идентичность на этой машине не получает окна разрешения
([adb-authorization-recovery.md](adb-authorization-recovery.md#the-prompt-is-never-drawn-on-this-car-live-2026-08-29)).

## 1. Что такое раздел

«Сервис» → строка «Диагностика» → полноэкранная страница. Назад — в «Сервис».
Строка существует только в сборке `-Pdiagnostics` (`BuildConfig.DIAGNOSTICS`,
`ServicePanel`), пока владелец не примет раздел на машине; флаг снимает он.

Экраны — по одобренной странице «Сканер (v3)»:
- **Автоскан** — две вкладки: «Список» (блоки по системам, адрес, протокол,
  DTC активные и в истории, статус) и «Топология» (те же блоки плитками в
  колонках по системам). Сверху итог: ответило, DTC активных, в истории,
  память прочитана, MIL.
- **Блок** — вкладки «Ошибки DTC» (коды, тип отказа, биты статуса матрицей,
  что запрошено и какой маской), «Идентификация» (что ответил блок и что знает
  кэш обновлений), для OBD-блоков ещё «Готовность» (мониторы) и «Потоковые
  данные» (PID таблицей: значение, мин/макс, норма, график 60 с).
- **Системы** — «Высоковольтная система» (мнемосхема), «ВВБ», «Электропривод»,
  «Тормозная система» (ESP/IPB `782` и OBD-интерфейс `7E5`), «Ассистенты»
  (семь блоков рядом).

Раздел заменил окно v1 целиком; окно удалено 2026-10-20 (шаг 3,
[10](#diag-arch-work)): `VehicleDiagnosticsWindow`, `DiagnosticRenderer`,
`DiagnosticFrame*`, `DiagnosticReadQueue`, `VehicleDiagnostics`, `VehicleDtcProxyMain`,
`DtcProtocol`, `DtcDescriptions`, лампы `DiagnosticSignals`, доски `main-diagnostics*`.
Показания из `autoservice` (`DiagnosticExtras`) перешли в раздел как источник
системных экранов.

## 3. Транспорт

<a id="diag-arch-wire"></a>
### 3.1 Провод (доказан)

- `BYDAutoMqttDevice` (устройство 1033) из shell UID: `set(int[]{0xAA00010A},
  BYDAutoEventValue)` с `bufferDataValue` = запрос; ответы — слушатель на
  `0x9900010A` (`onDataEventChanged` или `onDataChanged`).
- Запрос: `0A`, адрес запроса big-endian (2 байта), длина UDS (1 байт), UDS.
- Ответ: `0A`, адрес ответа (= запрос + 8), длина фрагмента, число кадров,
  номер кадра с 1. В первом кадре — результат шлюза (`1` ответ, `2`
  отрицательный ответ, `3` нет ответа, `4` таймаут диагностики, `5` занят), и
  данные с байта 7; в следующих — с байта 6.
- Буфер приходит длиннее объявленного (240 байт с мусором в хвосте): читаем
  ровно объявленную длину. Одинаковый кадр может прийти дважды — второй
  отбрасываем.
- Многокадровая сборка: число кадров одно на весь ответ, номера подряд, иначе
  ответ битый. Все ответы исследований были однокадровыми.

<a id="diag-arch-resident"></a>
### 3.2 Резидентный помощник

Один процесс shell UID на открытый раздел, а не процесс на запрос, как у v1.
Причина — цена: у v1 одно чтение стоит ≈14 с (2 с тишины + окно 12 с), автоскан
43 блоков по три запроса занял бы полчаса, потоковые данные невозможны.

- `DiagnosticBusMain.java` запускается через `LocalAdbClient.ResidentSession`
  так же, как помощник поворотников (`AdbTurnSignalEventChannel`): стейджер
  кладёт jar по SHA-256, команда `exec app_process ... serve <nonce> <пауза мс>`.
  Jar — `diagnostic-bus.jar`, на машине `denza-diag-bus-<sha256>.jar`
  (`ShellProxyJar.DIAGNOSTIC_BUS`); в jar входят `DiagnosticBusMain.java`,
  `DiagnosticWhitelist.java`, `DiagnosticFrameAssembler.java` и общий
  `ShellProxyBootstrap.java` (`ShellProxyJarAssetsTest` держит список против
  классов, которые помощник называет). Из APK помощник не грузится никогда: не
  положился jar — раздел без канала.
- Старт: UID 2000; общий замок `/data/local/tmp/denza-dtc-read.lock` берётся
  на всю жизнь процесса (исключает исследовательские пробники, второго себя и
  читателя ADS); проверка стоянки; регистрация слушателя; **2 с тишины** — любой
  кадр в это время значит, что канал занят кем-то ещё; затем `READY`. Старт,
  который не удался, тоже кончается `READY` — см. «Отказ старта» в
  [3.3](#diag-arch-protocol).
- Процесс умирает вместе с потоком ADB (EOF на stdin), по `quit` и сам — после
  **60 с без запросов**. Приложение откроет его снова при следующем запросе;
  своему помощнику оно доверяет 50 с после последнего обмена, чтобы не попасть в
  его уход.

<a id="diag-arch-protocol"></a>
### 3.3 Построчный протокол

Запросы (одна строка — один обмен, по одному за раз):

```
x <seq> <адрес 3 hex> <uds hex> <таймаут мс>     например: x 17 7E0 190109 4000
g <мс>                                           пауза между обменами, 0…500, например: g 20
s gb                                             подписаться на страницы BMS (6.3)
u gb                                             отписаться
quit
```

Ответ — между `DENZA_SERVE_<nonce>:BEGIN` и `…:END ok` / `…:END err <КОД> <пояснение>`:

```
a <seq> <кадров> <мс> <нс> <uds hex>   на x: полный ответ блока, положительный или 7F
n <seq> <результат> <мс> <нс>          на x: 3, 4 — нет ответа; 5 — шлюз занят; T — таймаут помощника
g <мс>                                 на g: та же строка — пауза, которая теперь действует
s gb / u gb                            на s / u: та же строка
```

Между ответами, пока приложение подписано, помощник сам печатает строки страниц:

```
DENZA_SERVE_<nonce>:PUSH b <нс> <id 3 hex> <payload hex>   страница BMS: 43A, 43C или 43D
DENZA_SERVE_<nonce>:PUSH e <КОД> <пояснение>               сеанс кончился, пока страницы шли
```

Время в каждом ответе — измерение, а не допущение: по нему строится график
потоковых данных с честными промежутками и меряется шаг автоскана (шаг 2
приёмки). `мс` — от вызова `set()` до последнего кадра ответа, а для `n` — до
кадра с результатом шлюза или до своего таймаута. `нс` — момент этого кадра на
машине, `SystemClock.elapsedRealtimeNanos`, снятый в слушателе до перехода на
main Looper. В приложении это `DiagReply.latencyMs` и `DiagReply.receivedNanos`.

Пауза между обменами — параметр запуска, `serve <nonce> <пауза мс>`, от 0 до
500, по умолчанию 100 (`ResidentDiagnosticBus(gapMs)`): на приёмке её подбирают
без пересборки.

Строка `g <мс>` меняет паузу живому помощнику со следующего обмена; шины она не
касается, часы простоя не трогает. Ответ — та же строка `g <мс>` между `BEGIN` и
`END ok`; `g` вне 0…500, без числа или с лишним словом — `END err REFUSED`, как
любая незнакомая строка; помощник, чей сеанс уже кончен, отвечает на неё своим
вердиктом, как на `x`. В приложении это `DiagnosticBus.setGap(мс)`:
`ResidentDiagnosticBus` запоминает просьбу и перед следующим обменом шлёт `g`, если
пауза помощника другая, — так и новому помощнику после потери: он стартует с
параметра запуска (100) и получает `g` перед первым `x`. Ответ не той строкой — ошибка
программы (`Refused`). Так страница одного параметра опускает паузу до 20 мс
([6.2](#diag-arch-param)). `FakeDiagnosticBus.setGap` пишет просьбы в `gaps` и
ведёт поддельные часы машины с новой паузой.

**Страницы BMS** ([6.3](#diag-arch-cells)). `s gb` регистрирует в помощнике второго
слушателя — на устройстве 1039 `BYDAutoGBDevice`, событие `9900001F`, — `u gb`
снимает его; ответ — та же строка, повтор безвреден, иное слово — `END err REFUSED`,
кончившийся сеанс отвечает вердиктом. Слушатель отбирает записи с CAN id `43A`, `43C`,
`43D`, sub 0, channel 2 (конверт 10 байт: id, sub, channel, счётчик), ставит время
`elapsedRealtimeNanos` и кладёт строку в очередь на 1024; отдельный поток печатает
её целиком. Каждая запись в stdout — ответ целиком (`BEGIN`, строка, `END`) или одна
строка страницы — идёт под одной блокировкой и одним `flush`, поэтому страница
никогда не попадает внутрь ответа. Приложение отличает строку страницы от ответа
по месту и метке: она стоит вне `BEGIN…END` и начинается с
`DENZA_SERVE_<nonce>:PUSH ` — эхо оболочки и шум этой метки не несут. Страница с
`FD` в первом байте у `43D` проходит как есть, отбрасывает её сборка. В машину по
этим строкам не уходит ничего, поэтому проверки перед запросом к ним не относятся;
сам помощник стартует только на стоянке. Пока подписка действует, часы простоя
стоят: чтение страниц и есть работа, а помощник всё равно умрёт с потоком ADB; `u gb`
запускает их заново. Слушатель снимается на `u gb`, `quit`, уходе по простою и любом
другом выходе (`release()`); если сеанс кончился, пока подписка действовала
(`FOREIGN_TRAFFIC`, `HELPER_FAILED`), помощник сначала печатает `e <КОД>`. Полная
очередь роняет страницы — сборка видит разрыв. Запросы `x` и `g` идут как прежде,
пока страницы текут.

`LocalAdbClient.ResidentSession` хранит текст, пришедший вокруг ответа (до `BEGIN`
и после строки `END`), оставляет из него только строки `…:PUSH ` своего nonce и
отдаёт их `pushed(ждать мс)`: если готовых нет, ждёт только первый байт сообщения
ADB (таймаут никогда не режет сообщение), подтверждает каждую запись и возвращает
пусто, если ничего не пришло. Невостребованные строки ограничены 256 КБ.

Перед **каждым** запросом помощник проверяет: белый список, профиль 170
(`persist.sys.AutoType`), P (`autoservice` 5, 1011, `89129008` = 1), скорость 0
(`autoservice` 7, 1013, `-1807745016`), менеджер диагностики в покое
(`sys.diagmgrsrv.task_bk = r@-1_0&w@-1_0`), не меньше паузы (по умолчанию
**100 мс**) от конца прошлого обмена. Таймаут запроса — от 1 до 6000 мс, обычный
4000. Ответ `7F <sid> 78` (блок просит подождать) не закрывает запрос: ждём до
таймаута.

Сборка ответа — `DiagnosticFrameAssembler` (чистая Java, в jar помощника):
- до первого запроса любой кадр чужой;
- кадр, который уже был в этом обмене, отбрасывается (сравнивается только
  объявленная длина);
- между обменами и в следующем обмене безвредны только отголоски прошлого: кадры
  с адреса прошлого ответа. Если два запроса подряд идут к одному блоку (`19 01`,
  затем `19 02`), первый кадр с ответом не на ту службу — запоздалый ответ на
  прошлую и тоже отбрасывается; от блока, которого в прошлом обмене не было, это
  `FRAME_SHAPE`;
- на один обмен не больше 64 буферов, считая дубли и «подождите».

Ошибки сеанса — `END err`:

| Код | Когда | Помощник после | Приложение |
|---|---|---|---|
| `REFUSED` | запрос вне белого списка или битая строка | живёт | `Refused` |
| `GUARD_PROFILE`, `GUARD_PARK`, `GUARD_SPEED` | не тот профиль, не P, скорость не 0 | живёт, запрос не отправлен | `NotParked` |
| `MANAGER_BUSY` | менеджер диагностики занят | выходит | `ChannelBusy` |
| `FOREIGN_TRAFFIC` | кадр не к текущему запросу (чужой тестер, сток) | выходит | `ChannelBusy` |
| `LOCK_BUSY` | замок держит другой читатель (только на старте) | выходит | `ChannelBusy` |
| `FRAME_SHAPE` | кадр не по форме, разрыв нумерации, больше 16 кадров или 4095 байт | выходит | `ChannelLost` |
| `TRANSPORT_REJECTED` | `set` вернул не 0 | выходит | `ChannelLost` |
| `HELPER_FAILED` | нет `autoservice`, класс устройства, исключение, `onError` слушателя, зависший main Looper | выходит | `ChannelLost` |
| `WRONG_UID` | помощник запущен не как shell | выходит | `Refused` |

`LocalAdbClient.ResidentSession.request` закрывает поток на любом `END err`,
поэтому со стороны приложения сеанс кончается после каждой ошибки, и в том числе
после «живёт»: следующий обмен откроет нового помощника. «Живёт» значимо для
хостового инструмента, который говорит с помощником напрямую. Код, которого
нет в таблице, приложение считает `Refused`; `DiagnosticBusLinesTest` сверяет
коды в исходнике помощника с таблицей.

**Отказ старта.** Помощник, который вышел до `READY`, виден приложению только как
закрытый поток — так «замок занят» и «не P» неотличимы от потерянного ADB. Поэтому
старт не выходит молча: отказ (`LOCK_BUSY`, `GUARD_*`, `MANAGER_BUSY`,
`HELPER_FAILED`, `WRONG_UID`) или кадр в окне тишины (`FOREIGN_TRAFFIC`) сначала
отпускает слушателя и замок, потом печатает `READY` (при кадре — сразу, не
дожидаясь конца двух секунд), а первая строка получает `END err <код>`, и процесс
выходит. Так же помощник поступает с чужим кадром между обменами: всё отпущено
сразу, причина — ответом на следующую строку. Без строки он уходит через 60 с.

### 3.5 Сторона приложения

`bus/DiagnosticBus.kt` — интерфейс и типы:
- `DiagRequest(address, uds, timeoutMs)` — создаётся только из разрешённого.
- `DiagReply`: `Answer` (полный ответ, положительный или `7F`, с `nrc`),
  `NoReply` (шлюз сказал 3/4 или помощник не дождался), `GatewayBusy` (5); у
  каждого `latencyMs` и `receivedNanos` из [3.3](#diag-arch-protocol).
- `DiagFailure` — сеанс, а не блок: `NoAccess` (нет доверенного ADB),
  `NotParked`, `ChannelBusy` (замок, менеджер, чужой трафик), `ChannelLost`,
  `Refused` (ошибка программы).
- `ResidentDiagnosticBus` — реализация на стейджере и `ResidentSession`; один
  обмен за раз (`Mutex`); открывает помощника лениво; после `ChannelLost` —
  одна попытка открыть заново и послать тот же запрос (все запросы — чтения,
  повтор ничего не меняет), после `ChannelBusy` — ничего, пока пользователь
  не нажмёт «Опросить снова». Политика «ничего» — у движка: шина сама не
  повторяет, а следующий вызов `exchange` снова откроет помощника. Отменённый
  обмен и `close()` закрывают поток сразу — закрытие сокета прерывает чтение.
  `AuthorizationRequiredException` → `NoAccess`.
- `FakeDiagnosticBus` (тестовые исходники `bus/`) отвечает по сценарию на
  запрос (`on(0x7E0, "190109").answer(...)`, шаги по порядку, последний
  повторяется; незаданный адрес — шлюз 3), ведёт журнал обменов, умеет
  `DiagFailure` шагом или `failNext`, и время по поддельным часам машины;
  байты — из `research/vehicle-diagnostics/*.json`.
- `DiagnosticBus.batteryPages()` — `Flow<BmsPage>`: сбор подписывает (`s gb`, на
  открытом помощнике или новом, с одной попыткой после потери, как у `exchange`),
  отмена отписывает (`u gb`). Чтение строк — `pushed(100 мс)` под тем же `Mutex`, что
  обмены, так что обмен ждёт не больше одного короткого чтения, а страницы — не
  больше одного обмена. Помощник, которого сменил обмен после потери, не подписан —
  поток кончается `ChannelLost`; `e <КОД>` кончает его отказом по таблице выше и
  закрывает связь. Просить снова решает движок. `FakeDiagnosticBus` пишет страницы
  сценарием (`page`, `failPages`, `failSubscribe`) и журнал `subscriptions`.

## 4. Протокол

Чистый Kotlin в `protocol/`, проверяется эталонами из исследований
(`obd-20261020.json`, `remaining-ecus-20261020.json`, `dtc-20261018.json`,
`lbms-dtc-20261018.json`, `dtc-reference-20261018.json`) и байтами трасс
`captures/diagnostics-obd-20261020/` и `captures/diagnostics-remaining-20261020/`,
переписанными в тесты (`DtcCodecTest`, `ObdCodecTest`, `DiagDecoderTest`).

Ответы ECM 21 октября добавили две регрессии `ObdCodecTest`: PID54 —
`unsigned16 − 32767` Па (`41 54 E8 B6` → 26807 Па); у PID56 байт B3 условный,
поэтому одиночный `41 56 80` даёт только B1=0%, без придуманного B3. Внутри
пакетного ответа короткую длину 56 без сведений о банках не угадываем, поэтому
поток спрашивает 56 одним PID с первого запроса ([6.1](#diag-arch-stream)).
Те же сеансы дали ещё три правки (в коде с 2026-10-21, на машине не запускались):
имя `09 0A` по J1979 (`ECM\0-EngineControl\0\0` → `ECM-EngineControl`), одометр
PID A6 (`41 A6 00 02 03 9D` → 13 199,7 км) и PID 44 `FFFF` при стоящем ДВС —
граничное значение, а не λ 2,000: «н/д».
Сырые ответы, первичные источники и границы проверки —
[находки](vehicle-data-findings.md#remaining-ecm-parameters-and-calibration-2026-10-21).

- **Вход для движка** — `DiagDecoder`: функции берут `DiagReply.Answer` и
  возвращают `Decoded` (`Ok`, `Negative(nrc)`, `Malformed(why)`). Сначала
  проверяется, что это ответ на свой запрос: положительная служба = запрошенная
  + `40`, та же подфункция, DID, PID или тип информации; `7F` — ровно три байта и
  про запрошенную службу. Иначе `Malformed`. `Polled.of(reply, decoder)` даёт
  чтение с качеством данных.
- **Память ошибок.** `59 01`: маска доступности, формат, число. `59 02`:
  маска доступности и записи по 4 байта. Число и список обязаны совпасть,
  маска доступности в обоих ответах одна, биты статуса записи — внутри неё,
  ~~коды — без повторов,~~ `19 02` той же маски и того же блока; иначе ответ
  «несогласованный», а не «0 кодов». Число 0 — память полная и пустая без
  `19 02`; ненулевое число без списка — не память. Запись, чей статус не
  попадает в маску запроса (блок маску не применил), не выбрасывается и ответ
  несогласованным не делает: запись показывается, а у памяти пометка «блок
  отдал записи вне маски» — спрятать запись на диагностическом экране хуже, чем
  показать лишнюю (решение 2026-10-20; в движке).
  > **Superseded 2026-10-21 (решение владельца):** повтор кода ответ несогласованным не делает —
  > каждая запись остаётся, как пришла, в порядке списка, см. «Повтор кода» ниже.
- **Повтор кода** (в коде с 2026-10-21, на машине не запускался). Полный живой `19 0A` ISG `7E6`
  (231 байт, 57 записей, 56 разных кодов) перечисляет `C1D487` дважды, на 28-м и 40-м месте
  ([находки](vehicle-data-findings.md#can-visibility-and-complete-isg-response-2026-10-21)),
  а штатный парсер IP-клиента (`libuds`, задача `C565C`) добавляет записи подряд, повторов не
  удаляя ([находки](vehicle-data-findings.md#stock-isg-reader-and-factory-script-source-2026-10-21)).
  Поэтому `DtcCodec.memory` и `listOnlyMemory` повтор не отвергают: запись на каждое вхождение,
  со своим байтом статуса, в порядке списка. Дальше по течению ничто не ключуется кодом: строки
  экрана блока и таблицы DTC системы, поиск в каталоге, счёт активных и исторических идут по
  записям, `last-scan.json` хранит байты ответов; повтор — две строки с одним описанием. Почему
  блок перечисляет код дважды, не установлено. Тесты: `DtcCodecTest` (реестр ISG как список
  `19 02` — 57 записей, повтор на своих местах; список без счётчика), `SystemPagesTest` (повтор
  у R_ZCU — три строки на экране блока и в таблице «Кузова», счёт по записям).
- **Формат кода.** `00` — SAE J2012: буква P/C/B/U, четыре знака и тип отказа
  (`C1170-09`). `01` (ISO 14229-1, у ADS `712`, а также у FMCU `7E3` и ISG `7E6`)
  — шесть hex-знаков без буквы: его нельзя читать как P/C/B/U по правилу, и строка кода
  показывает его как пришёл; ~~(только поиск в каталоге раскладывает код FMCU как
  J2012, см. «Сопоставление» ниже)~~ исключения с 2026-10-21 (решения владельца) — FMCU `7E3` и
  ISG `7E6`, чей формат `01` установлен совпадением с их реестрами `19 0A`: их код и показ, и поиск
  раскладывают как J2012 (`J2012.FORMAT_01_LAID_OUT`, `1B0019` → `P1B00-19`, `180219` →
  `P1802-19`), см. «Сопоставление» ниже. Остальные
  форматы — сырые байты. Имена типа отказа — общие SAE J2012-DA (`FailureTypes`),
  с пометкой источника; значения базовых кодов BYD не выдумываются.
- **Описание кода BYD** — два уровня. Оба дают строке кода описание простым
  текстом, без `≈` и без пометок; источник называется один раз на экран, в
  футере экрана кодов, и только когда на экране есть хоть одно описание. Нет
  описания — у строки остаются группа кода и общий тип отказа, без поясняющей
  фразы («Расшифровка BYD недоступна» больше не выводится, `DtcRow.note` пуст;
  решение владельца 2026-10-20).
  1. **Квалифицированный заводской словарь** — пока нет. Это документ с
     ревизией, применимостью к варианту блока и его ПО (`F194`), сопоставлением
     показа и сырого кода (для формата `01` — обязательно), страницей источника.
     Когда появится, он заменяет каталог там, где покрывает код.
  2. **Каталог публичного оглавления** мануала Z9GT PHEV 2024 — сделано.
     829 заголовков `research/vehicle-diagnostics/oem-dtc-public-index-20261020.json`
     (ДВС 496, BMS 206, передний привод 31, генератор 32, задние левый и правый по 32)
     и их машинный перевод `oem-dtc-public-index-ru-20261020.json` (ключ — раздел,
     код, `outlineId`; шапка: перевод заголовков, не заводской текст; `sourceSha256`
     привязывает перевод к индексу). Это кандидаты, а не расшифровка: в оглавлении
     есть коды с двумя разными заголовками, нет привязки к ПО
     ([находки](vehicle-data-findings.md#oem-dtc-manual-candidates-2026-10-20)).
     - **Данные:** оба файла попадают в APK как есть — задача Gradle
       `copy<Variant>OemDtcAssets` (`ResearchAssets` в `build.gradle.kts`) копирует их
       байт в байт в сгенерированные ассеты `diagnostics/`; второй копии нет.
       `scan/OemDtcAssets` читает их, `protocol/OemDtcIndex.join` соединяет один к
       одному (строка без перевода, перевод без строки, повтор ключа — каталога нет).
       В APK ≈41 КБ сжатыми (213 КБ JSON). Движок загружает каталог первым делом

### 5.2 Маски

> Решение владельца 2026-10-23: память читается маской `0D` — и ожидающие тоже — там, где блок
> их сообщает ([7.3](#diag-arch-v4)); как именно (доступность, откат на `09`), записывает волна чтений.

Память ошибок — `19 01 09`, затем `19 02 09`, если число больше нуля. Маска `09`
= отказ сейчас или подтверждён, это включает исторические (статус `28`).
Ожидающие для OBD-блоков — режим `07`. Маска `FF` не используется: у ECM она дала
258 записей непроверенных мониторов. `19 01 04` у `7E0` и `7E2` не ответил за
4 с — не используется.

Блок, чей `19 01` не отвечает (DCOBC: шлюз говорит «нет ответа»), читается одним
`19 02 09` (`DiagDecoder.dtcMemoryFromList`). `59 02` не несёт формата, поэтому
его коды остаются сырыми шестью hex-знаками, пока формат не известен по живому
`59 01`, — никогда не SAE по аналогии.

### 5.5 История кодов ПО (решение владельца 2026-10-21)

Снимок каталога устаревает с первым обновлением блока по воздуху, а обновить его из приложения нельзя, поэтому
сканер сам помнит на ГУ, что прочитал.

  родителем (адрес и DID, [5.4](#diag-arch-children)) — последний код; у каждого — день, когда он впервые
  прочитан, и изменения {было: код и версия, стало, день обнаружения}, до 32 на ключ.
- **Начало:** ключ, который ещё не читали, — код снимка каталога (`snapshotF194`, у модулей `snapshotCode`) с
  днём 2026-10-18 (`EcuCatalog.SNAPSHOT_DATE`), без версии; ~~у блока без кода в каталоге (маршруты стока) —
  первое чтение~~ с 2026-10-21 (решение владельца) и у `720`, `722`, `726`, `747`, названных маршрутами стока, —

  них прежние; первое чтение — начало только у `762`, у которого кода в кэше нет. Начало пишется в файл, только когда против него что-то узнано: машина такой, какой она
  ответила 2026-10-20, не пишет ничего.
- **Откуда:** только хорошие чтения (`SoftwareReads`) — положительный, правильный, ненулевой код: ворота

- **На экране:** в «Идентификации» блока под «Версия ПО · 22 F195» — «ПО обновлено · 12.11.2026» и «был
  ~~87F71A011402~~ 3.48.07 · 1A011402 · 4A520011E00D00047B» (версия первой, где была известна; с 2026-10-21 —

  «Идентификации» с 2026-10-21 шире половины DTC: 624 dp против 588, «Как опознан» — 576 (`scanner.json`

    рядом с улицей, °F переводится в °C, домен −40…50 °C (−40 — «н/д»), единица неизвестна — «н/д». Чтобы общий пакет
    не вырос, PM2.5 салона и улицы читаются только пока «Состояние» климата на экране (`ExtraPage.CLIMATE_STATE`).
  - C4: задние момент и ток (`1039·2850002C/3C`, `28500178/88`) — беззнаковые × 0,1: диапазон 0…3000 (было ±5000 и
    ±2000), перенос отрицательного (3276,8 и выше) — «н/д»; задние обороты 0…20000 его и так отсекали.
  - C3 (порог работы ДВС) не трогали: правило продукта исследование квалифицировало отдельно.

  Тесты исправлений — `DiagnosticExtrasTest`. Диапазон каждого GET отсекает недействительные
  коды прошивки, а не диагностирует: изоляция 0…60000, число ячеек и датчиков 1…253
  ([7.2](#diag-arch-systems)). Задние сигналы autoservice названы
  сторонами; в текущем коде «Электропривода» колонки ещё подписаны сокращениями,
  сторона сигнала — меткой «Л»/«П» в строке источника. Модельная привязка SMCU к
  левому, SMCU3 к правому найдена 2026-10-21 ([5](#diag-arch-catalog)); перенос
  в модель экрана ещё не сделан.

<a id="diag-arch-stream"></a>
### 6.1 Поток данных

Поток должен быть ровным и честным: по нему диагностируют, значит частота,
задержка и пропуски видны, а не угаданы.

- **На машине 2026-10-20 вечером** (фото владельца, ДВС работает, P): ECM отдал 45 PID,
  таблица «Потоковые данные» шла по кругу с частотой 0,4 Гц при обмене 15 мс — круг
  из 45 PID около 2,5 с. Отсюда страница одного параметра ([6.2](#diag-arch-param)).
  Текстовое значение PID 03 («замкнутый контур по датчику O2») не влезало в колонку
  значения и наезжало на название: с тех пор в колонке код (CL/OL), рядом — пара слов
  («замкн. петля»), а значение любой длины обрезается своей колонкой.
- **Что известно.** Исследовательский пробник прочитал 16 ответов за 13,2 с,
  из которых 2 с — тишина на старте и 8 с — его же паузы по 0,5 с: на обмен с
  запуском процесса пришлось ≲200 мс. Отдельно задержка обмена не измерялась. Шлюз
  отвечает «нет ответа» по своему таймеру быстро — пустой адрес поток не тормозит.
- **Откуда скорость.** Один резидентный помощник (нет запуска процесса на
  запрос); пока открыта вкладка, поток — единственная работа шины, автоскан
  стоит; пауза между обменами — параметр запуска помощника, начальное значение
  100 мс, на приёмке подбирается наименьшее без «нет ответа» и «занят» за 2 минуты.
- **Упаковка запросов.** Несколько PID в одном `01` так, чтобы ответ
  помещался в один кадр CAN (`41` и до 6 байт данных; каждый PID стоит свой байт
  плюс длину значения из таблицы протокола: например, `01 0C 0D` — обороты и
  скорость, или три однобайтовых PID). Раскладка — первая подходящая по порядку
  таблицы. PID, который один не влезает в кадр (`7A`, семь байт), в поток не
  входит; карты PID, `01`, `41`, `1C`, `13` и одометр `A6` читаются один раз с
  идентификацией. Пакет, на который блок ответил отказом или битым ответом, дальше
  спрашивается по одному PID. PID 56 спрашивается один с первого запроса
  (`LiveStream.ALONE`, с 2026-10-21): ECM отвечает на него одним байтом
  (`41 56 80`), внутри пакета такой ответ не делится, и раньше весь пакет с 56
  до конца сеанса уходил в одиночные запросы. Многокадровые ответы `01` с шестью PID — только
  после того, как приёмка покажет, что шлюз их собирает быстро.
- **Режим фокуса.** «Выбор PID» на вкладке: до 4 параметров, которые
  нужны сейчас (обороты, коррекции, датчик кислорода): весь круг фокуса, затем
  один пакет таблицы, и снова — фокус идёт через обмен, это самая высокая частота
  на график. Без фокуса таблица идёт по кругу. Порядок таблицы — как на доске
  «Потоковые данные», затем остальные PID по номеру.
- **Время у каждого значения.** Помощник ставит на ответ время прихода
  (`elapsedRealtimeNanos`) и длительность обмена; график строится по этим
  временам, пропуск («нет ответа», PID, который блок не прислал) рисуется
  разрывом, значения не интерполируются; ответ без числа (PID 44 `FFFF`) —
  «н/д» и тоже разрыв; кольцо — 60 с. В шапке вкладки —
  измеренная частота и задержка («4,6 Гц · 120 мс»), а не заданная: частота —
  самого частого PID за последние 10 с по временам машины, задержка — средняя
  за последние 20 обменов. Мин/макс — с открытия вкладки или кнопки сброса.
- **Норма** — только где она известна: ОЖ 80…105 °C (выход — только перегрев:
  прогрев не отказ), коррекции ±10 %, напряжение ЭБУ 13,2…14,8 В, датчик O2
  после катализатора 0,1…0,9 В (судим только при работающем ДВС), давление во
  впуске «ХХ 25…45» — подпись без суждения: холостой ход движок не отличает.
- **Быстрые сигналы машины.** Восемь «горячих» показаний `VehicleTelemetryHub`
  — обороты, работа ДВС, генерация, мощность и напряжение батареи, скорость, P,
  одометр — уже идут каждые 100 мс без запросов к блокам; на вкладке ДВС они
  показываются после PID с источником «autoservice · 100 мс», одна точка на
  новый проход хаба (у строки отрицательный `pid`).
- **Запись.** «Запись» на вкладке пишет поток в
  `filesDir/diagnostics/stream-<время>.csv` (`received_ns,address,pid,raw,value`):
  время прихода, адрес, PID, сырые байты, значение; разрыв — строка без байтов
  и значения; быстрые сигналы — с адресом `autoservice` — для разбора после
  поездки так же, как `captures/vehicle-log/`.
- **Ожидание.** До измерения — оценка: 4–8 обменов в секунду, то есть фокус из
  двух-трёх PID ≈4–8 Гц, таблица из 13 PID ≈1–2 Гц. Если меньше — сначала пауза
  и упаковка, потом решение владельца.

<a id="diag-arch-param"></a>
### 6.2 Один параметр на своей странице (решение владельца 2026-10-21)

Строка «Потоковых данных» открывает параметр отдельно: значение крупно, график во всю
ширину, окно 10 с / 60 с / 5 мин, мин, макс, среднее, норма полосой, изменение за секунду;
опрашивается только он, и как можно чаще. Доски — `scanner-sys-engine-rpm`,
`scanner-sys-engine-ect` (`sysParam`); контракт — `ParamKey`, `ParamView`, `ParamStats`,
`DiagnosticsActions.setParam`, `setParamPaused`, `resetParam`; ключ строки — `LiveRow.key` (с 2026-10-21
и у строк батареи; ~~`SignalRow.key`~~ — старой таблицы батареи больше нет).

- **Откуда открывается.** Строки потока ECM (страница «Двигатель», вкладка «Потоковые
  данные», и экран блока ECM) и строки «Потоковых данных» «Тяговой батареи». Строка без ключа
  (расчёт) не открывается. Страница — шаг стека: «‹ Потоковые данные» и Back возвращают.
- **PID** (`ParamKey.Pid`): пока страница на экране, шина возит только этот PID одиночным
  `01 xx` подряд, автоскан и прочие потоки стоят. Пауза помощника между обменами — 20 мс
  (строка протокола `g <мс>`, 0…500, [3.3](#diag-arch-protocol)); на «нет ответа» или «занят»
  пауза удваивается до 100 мс и такой остаётся, пока страница открыта; ушли со страницы —
  пауза снова 100 мс. Проверки стоянки помощник делает перед каждым запросом, как всегда.
- **Сигнал машины** (`ParamKey.Signal`): один GET `autoservice` по постоянной оболочке раз в
  100 мс (`DiagnosticExtra` по ключу); сигналы хаба — с его 100 мс. Остальной пакет GET стоит.
- **Кольцо** — 5 минут по времени машины; пропуск — разрыв. Окна 10, 60 и 300 с считаются
  движком все три (`ParamView.windows`): мин, макс, среднее, шкала графика с запасом,
  округлённая к сетке из 4–5 линий, подписи сетки, изменение за последнюю секунду, число
  точек. Частота и обмен — измеренные, как в [6.1](#diag-arch-stream).
- **Норма** — как в 6.1; нет нормы — «—» и без полосы. Значение вне нормы — оранжевым.
- **Запись** — для PID, в тот же CSV, что поток (6.1); у сигнала машины кнопки нет.
- **Экраны** (в коде 2026-10-21, `ui/ParamScreen.kt`; доски `scanner-sys-engine-rpm`,
  `-ect` и `scanner-sys-pack-cell` — минимум ячейки, сигнал машины без «Записи»). Шаг стека
  `ScannerRoute.Param(key)` над вкладкой, с которой открыли: у системы — рядом с колонкой, у
  экрана блока ECM — во всю ширину окна. Крошки кончаются на экране под страницей, голова
  называет параметр. Пока страница на экране, раздел держит `setParam(key)`, уходя — `null`;
  экран блока под ней остаётся открытым, поток его стоит. Голова — `name`, `aside`, `line` и
  МИН / МАКС / СРЕДН. выбранного окна; окно — вкладки «10 с · 60 с · 5 мин», выбор экрана, по
  умолчанию 60 с; слева значение крупно со свечением (оранжевым вне нормы), единица, НОРМА,
  ЗА 1 С, ТОЧЕК; справа график: полоса нормы, сетка с подписями, пять меток времени поровну
  от «−N с» до «сейчас», мин и макс окна пунктиром, след по времени машины с разрывом на
  пропуске и светящейся последней точкой. След — один путь, перестраиваемый на месте, не больше
  четырёх точек на столбец пикселей (первая, нижняя, верхняя, последняя), так что 5 минут при
  24 Гц стоят столько, сколько ширина графика. Пока движок не описал страницу, она стоит на
  строке: имя, значение, пустой график. Футер — «‹ Потоковые данные», «Пауза» / «Продолжить»
  (`setParamPaused`), «Сбросить мин/макс» (`resetParam`), «Запись» у PID (`setRecording`), справа
  частота.

**В коде** (движок; экран — отдельно):
- `scan/DiagnosticsSession` — `setParam`, `setParamPaused`, `resetParam`. Пока ключ PID задан,
  очередь отдаёт только `Work.Param` — одиночный `01 xx`; впереди может быть лишь кнопка
  «Прочитать DTC», идентификации, автоскан и потоки стоят. Пауза — `DiagnosticBus.setGap`:
  20 мс при открытии, на `NoReply` или `GatewayBusy` удваивается (20 → 40 → 80 → 100) и такой
  остаётся до ухода со страницы; уход или ключ сигнала — снова 100. Шина просит у помощника
  `g <мс>` перед следующим обменом и повторяет просьбу новому помощнику после потери. Отказы — как у
  потока (6): `NotParked` — пауза до хаба, занятый или потерянный канал — стоп до кнопки; открыть
  страницу или снять паузу — одна попытка вручную, не цикл. Ответ PID попадает и в строку таблицы,
  чтобы по возвращении она была свежей. «Пауза» останавливает опрос, страница остаётся;
  «Сбросить мин/макс» начинает цифры окон с текущего показания, след графика остаётся.
- `scan/ParamPage.kt` — `ParamSpec` (имя, `aside`, строка маршрута, единица, норма — как у строки,
  которая страницу открыла: таблица потока `LiveStream`, ряды ВВБ `SystemsBuilder.PACK`, быстрые
  сигналы `LiveStream.CarRow`), `ParamTrace` (кольцо 5 минут, пропуск — `Sample` без значения,
  частота — показаний в секунду за последние 10 с по времени ответов, обмен — среднее последних 20)
  и `ParamScale` (шкала: показания окна и полоса нормы, запас 5 % с каждой стороны, сетка
  с шагом 1, 2, 2,5 или 5 × 10ⁿ и не больше пяти линий). Окна 10/60/300 с —
  `ParamStats`: мин, макс, среднее и число точек — с последнего сброса, шкала — по всему следу
  окна, изменение за секунду — последнее показание против последнего на секунду раньше.
- Сигнал машины: GET пакета (`DiagnosticExtra`) или холодный сигнал хаба —
  `CarFeed.focus(SignalGet)`: `ExtrasPoller` шлёт по своей постоянной оболочке только этот
  `service call`, раз в 100 мс от начала до начала (подряд, если оболочка медленнее), каждое
  показание со временем `elapsedRealtimeNanos` головного устройства; сбой — пропуск и те же 5 с
  до новой оболочки. Остальной пакет стоит, его значения стареют как обычно. Горячий сигнал хаба
  берётся из его проходов, одна точка на новый проход; страница сигнала опрашивает ленту каждые
  100 мс.
- Частоты на странице — измеренные. На машине они не мерились: у PID это пауза плюс обмен
  (ожидание — шаг 5 приёмки, [9](#diag-arch-acceptance)); у GET один `service call` стоит
  ≈130 мс своего процесса (замер хаба, `VehicleSweepCadence`), так что
  «10 Гц» сигнала — верхняя граница, а не обещание; у горячего сигнала — цикл хаба, ≈250 мс.

<a id="diag-arch-cells"></a>
### 6.3 Ячейки и датчики батареи (решение владельца 2026-10-21)

> **Superseded 2026-10-21 (v2, «Ячейки» по обходу):** экран не рисует страницу за страницей, свежесть
> не считается по возрасту страницы («старше двух обходов»), шкала не строится от мин/макс
> (`ParamScale`) и столбики не стоят от среднего — что рисуется, меняется раз за обход, свежая позиция —
> обновлённая последним обходом, столбики — от удерживаемой опоры на симметричной сетке, есть пауза.
> Утверждения ниже исправлены на месте.

Вкладка «Ячейки» «Тяговой батареи»: 166 напряжений ячеек и 14 температур датчиков, как BMS
сама шлёт их страницами в своём потоке. Доски — `scanner-sys-pack-cells` (`sysPackCells`), `-partial`,
`-paused`; контракт — `PackCellsView`, `CellReading`, `SystemTab.CELLS`,
`DiagnosticsActions.setCellsVisible`, `setCellsPaused`.
Основание — [исследование 2026-10-21](vehicle-data-findings.md#live-passive-streams-and-paged-battery-telemetry-2026-10-21):
поток `1039 / 9900001F`, страницы `43A` (число ячеек и датчиков), `43D` (по три слова ячеек),
`43C` (по шесть кодов датчиков), sub 0, channel 2; разбор страниц — `research/vehicle-diagnostics/decode_battery_pages.py`
и его тесты; обход ячеек ≈5,5 с; совпадение с GET мин/макс и температурами проверено вживую.

- **Только слушание.** Запросов к блокам нет. Подписку держит тот же резидентный помощник
  ([3.2](#diag-arch-resident)): строки протокола «подписаться» и «отписаться» на поток и
  строки со страницами между ответами на запросы ([3.3](#diag-arch-protocol)). Подписка
  живёт, только пока вкладка «Ячейки» на экране (`setCellsVisible`) и не на паузе; ушли или
  «Пауза» — отписка.
- **Обход за раз (v2, решение владельца 2026-10-21: график «плясал»).** BMS шлёт 166 ячеек
  56 страницами за 5,5 с, а под нагрузкой вся батарея за обход уходит на ~4 мВ (запись
  `battery-page-telemetry-20261021.json`: два соседних обхода расходятся на −3…−5 мВ на ячейку).
  Страницы, нарисованные по мере прихода, ставили рядом два обхода: ложная ступень бежала по
  графику, разброс был ложным, автошкала прыгала с мин/макс, столбики от плавающего среднего
  переворачивались. Теперь движок собирает страницы как `decode_battery_pages.py` (позиция —
  порядок страниц BMS, страница `FD` в массив не входит), но рисуемое меняется раз за обход.
  Обход кончается, когда приходит страница с номером не больше предыдущей (снова 0 или любой
  откат); тогда снимок — прежний снимок, поверх которого легли страницы закончившегося обхода.
  Позиция, которую закончившийся обход не обновил, остаётся со старым значением и не свежая
  (рисуется блекло). До конца первого обхода рисуется пришедшее, всё свежее: график
  заполняется. Встал поток — блекнет всё: самая новая страница массива старше max(10 с, два
  обхода). Датчики (`43C`, 3 страницы) — по тому же правилу. Неполный обход — что пришло,
  остальное «—». Первый обход после подписки обычно хвост (подписка попадает в середину
  потока): его конец рисует только хвост, полный график — со следующим обходом.
- **Что значение.** `43A`: число берётся только 1…253 (254 и 255 — недействительные у прошивки,
  `battery-validity-followup-20261021.json`), иное оставляет прежнее. Слова ячеек `FFFE`/`FFFF`
  и коды датчиков `FE`/`FF` — не значения; к ячейкам применяется диапазон скалярных читателей
  (`VehicleKind.MILLIVOLT`, 1000…5000 мВ), вне него — нет значения. Сырой 0 датчика (−40 °C):
  штатный агрегат его пропускает — явное правило прошивки (`battery-stock-semantics-20261021.json`,
  «aggregate skips probe0», `gbdataservice` `CD40..D068`), и продукт так же не берёт его в МИН,
  МАКС, СРЕДН. и в обведённые крайние; плитка показывает «−40», как пришло: что 0 значит отказ
  датчика, источник не говорит (там же: «not evidence that 0 means sensor fault»).
- **Слова.** Напряжения — мВ как пришли; температуры — код − 40 (°C), как у уже проверенных
  GET. Мин/макс — первые по порядку BMS среди нарисованных; среднее и разброс — по
  нарисованным, блеклые тоже. Расположение ячеек и датчиков в батарее неизвестно и не рисуется.
- **График.** Столбик ячейки — мВ от опоры `cellRef`: целые мВ, сначала round(среднего
  снимка); держится, пока среднее снимка не уйдёт от неё больше чем на 1,0 мВ, тогда — снова
  round(среднего). Первый снимок ставит опору заново (пока первый обход заполняется, она
  держится так же). Сетка симметрична — −2s, −s, 0, +s, +2s, s из {1, 2, 5, 10, 20, 50, 100,
  200, 500} мВ, наименьшее, при котором 2s покрывает самую далёкую от опоры ячейку;
  расширяется сразу, сужается только после трёх обходов подряд, которым хватало меньшего (до
  самого широкого из них); пока первый обход заполняется — только расширяется. Подписи «−4»,
  «−2», «3 282», «+2», «+4»: минус U+2212, опора — своим значением с группами, как
  `Figures.number`. Обход в пути (`sweep`) — доля страниц, пришедших после нарисованного
  снимка, из страниц массива; нет на паузе, после конца подписки и до `43A`.
- **Пауза** («Пауза» / «Продолжить», `setCellsPaused`). На паузе подписка оставлена — ничего не
  читается, — вид держится как в момент паузы (и не блекнет), строка возраста —
  «пауза · снимок 07:36:12», настенное время самой новой нарисованной страницы; обход, который
  шёл в момент паузы, выбрасывается (а пауза до конца первого обхода делает пришедшее снимком).
  «Продолжить» подписывается снова — и после прерванного потока; удержанный снимок блекнет, пока
  его не обновит обход. Уход с вкладки снимает паузу.
- **Расшифровки в том же заходе** (значения названы прошивкой, исследование 2026-10-21):
  главный контактор `1032 / 34400010` (0 разомкнут, 1 замкнут) — ВВ-схема рисует ключ
  замкнутым или разомкнутым и подписывает словом, строка «Потоковых данных» батареи тоже;
  состояние заряда/разряда батареи `1009 / 34400018` (0 готов, 1 заряд, 2 заряд завершён,
  3 разряд, 4 заряд прерван, 5 отказ C10, 6 отказ пистолета, 7 отказ зарядного, 8 отказ сети AC,
  9 по расписанию, 10 разряд CBU, 11 тайм-аут, 12 разряд завершён, 13 заряд на паузе),
  зарядное `1009 / 27C0000A` (1 готово, 2 старт, 3 завершено, 4 прервано) и
  `1009 / 27C00008` (1 норма, 2 лёгкий отказ, 3 тяжёлый отказ) — строки «Потоковых данных»
  батареи. Холодильник и качество воздуха — нет: значения не названы.
- **Экраны** (2026-10-21, v2 тем же днём). `ui/CellsScreen.kt` — `sysPackCells()` построчно:
  столбик ячейки вверх или вниз от опоры, сетка с подписями (линия опоры ярче, подпись — её
  значение), линия обхода в пути с точкой у подножия графика (`packCells.cells.sweep` 2,
  `sweepDot` 3 → `ScannerSpec.PackCells.SWEEP`, `SWEEP_DOT`), мин и макс подписаны номерами BMS
  у концов своих столбиков, номера по оси через 20, датчики плитками с обведёнными крайними,
  головы с мин, макс, средним (и разбросом у ячеек). Между снимками столбики едут от прежних
  смещений к новым одной анимацией 300 мс (`MOVE_MS`, на досках её нет); столбик, которого не
  было, встаёт сразу. Не свежая ячейка — серый столбик, не свежий датчик — непогашенная
  плитка с блеклым числом; не пришедшая — без столбика, «—» у датчика. Доски —
  `scanner-sys-pack-cells` (обход нарисован, следующий пришёл на 34 из 56 страниц, 0,4 с
  назад), `-partial` (нарисован обход, пропустивший последние шесть страниц ячеек и последнюю
  датчиков: 16 ячеек 150…165 и датчики 12, 13 — от обхода до него, блеклые; следующий на 50 из
  56, поток стоит 2,6 с) и `-paused` («Продолжить», «пауза · снимок 07:36:12»). Все три
  держит `PackCellsBoardContractTest`: значения доски проходят через `PackCells` страницами,
  обход за обходом, и опора, сетка с подписями, головы, крайние, блеклые позиции, обход в пути,
  возраст и кнопка на доске — ответ движка; доски сошлись с движком без правки. Голова — та
  же, что у других вкладок батареи; футер — одна кнопка «Пауза» / «Продолжить», возраст
  (`PackCellsView.age`) и страницы `1039 · 9900001F · 43D 43C`. Пока вкладка впереди, раздел

  данные», «Флаги GB/T 32960», «DTC», «Блоки». ВВ-схема кладёт нож ключа на оба контакта, когда

  контактор»; неизвестно — нож поднят, слова нет (доска `scanner-sys-hv`: замкнут, как на машине).

  «разряд», «готово», «норма») прокручивается под шапкой, как таблица кодов.

**В коде** (движок и экран; на машине не запускался, v2 на эмуляторе не сверялась):
- Транспорт — строки `s gb` / `u gb` и строки страниц помощника ([3.3](#diag-arch-protocol)),

- `scan/PackCells.kt` — `PageArray` переносит правила `decode_battery_pages.py`: слово —
  little-endian, позиция = страница × слотов + слот, страница за пределом массива (`FD` у `43D`)
  и страница не той длины в массив не входят, у `43C` — наблюдённая сумма байтов 255; слово, не

  отдельно от нарисованного снимка; откат номера кладёт их поверх снимка (`snapshots`), у каждой

  правилу разбора: страницы 0…N−1 подряд по счёту из `43A`; до `43A` обход не считается, длина
  массива — до последней позиции со значением. Свежая позиция — обновлённая обходом, давшим
  снимок (до первого снимка — любая пришедшая), при самой новой странице массива не старше

  возраста «обход 5,5 с · 0,4 с назад» (последний полный обход ячеек, возраст самой новой
  страницы по `elapsedRealtimeNanos` головного устройства); до страниц — «ждём страницы BMS»,
  до полного обхода — «обход не завершён · …», после конца подписки — «поток BMS прерван · …»,

- `DiagnosticsSession.setCellsVisible(true)` — одна подписка на показ вкладки, рядом с работой:

  заряда батареи», «Зарядное устройство, состояние», «Зарядное устройство, отказ» со словами
  прошивки, пустой единицей и ключом страницы параметра; код без названия — «код N», не

- Штатная сборка тех же страниц (`battery-stock-semantics-20261021.json`,

### 6.4 Журнал сканов (решения владельца 2026-10-23)

Сканер живёт в машине и потому может помнить её во времени: с каких пор стоит код, что изменилось
между двумя сканами, что для этой машины «обычно». Журнал на ГУ копит сканы и снимки ячеек и отвечает
на эти вопросы экранам «Сводка», «Код», «Батарея · Здоровье», «Журнал» и отчёту ([7.3](#diag-arch-v4)).

- **Когда пишется — только по явному действию** (решение 1 из [7.3](#diag-arch-v4)). Одна запись
  скана — автоскан, который дошёл до конца: при открытии раздела (прошлому скану больше 10 минут или
  его нет) или по «Опросить снова». Одна запись на блок — «Прочитать снова» у законченного скана
  (вид `MODULE`; чтение блока посреди автоскана войдёт в его запись). Одна запись снимка — «Снять
  ячейки сейчас» (`DiagnosticsActions.saveCells()`), и только когда «Ячейки» нарисовали целый обход:
  половина первого обхода — это два обхода рядом ([6.3](#diag-arch-cells)), не снимок. Скан, показанный
  из `last-scan.json`, остановленный или на паузе автоскан, поток, идентификация открытого блока —
  не записи. Фонового опроса, записи по стоянке или по концу зарядки нет.
- **Запись скана** (`JournalScan`): конец (стена) и время первого обмена, вид `FULL` / `MODULE`,
  пробег, VIN (поле есть, заполняется, когда скан его прочтёт), число обменов и медиана ответа; по
  каждому блоку в порядке каталога (`JournalModule`) — адрес, сокращение, статус, ответил ли, прочитана
  ли память целиком (`memoryRead`), маска запроса и маска доступности, записи (`JournalRecord`: код,
  как его печатает экран, три байта, формат, байт статуса, откуда — «19 02 09» или режим OBD «03»,
  «07», «0A»), `F194` (код ПО), `F195` (если его прочитал этот скан или открытый в сессии блок),
  медиана ответа, MIL; величины на конец скана (`JournalVitals`) — 12 В, SOC (в десятых, где их
  читала страница потока батареи), SOH, ток ВВБ, мин/макс ячейки и разброс, изоляция двух каналов в
  МОм (показание GET, читаемое как кОм, / 1000), мин/макс датчиков, MIL любого OBD-блока, готовность
  мониторов ECM (PID 01).
- **Откуда пробег и 12 В.** Пробег — одометр хаба `autoservice` 1014 `4A502010` (тот же, что у журналов
  поездки), иначе PID A6 ECM, если ECM открыт в этой сессии и его карты его перечисляют, иначе нет.
  12 В — GET 1001 `43400028` (`DiagnosticExtra.LV`, транзакция 7). Все величины — общий пакет GET и
  хаб, только свежие ([6](#diag-arch-engine)); канал диагностики за ними не ходит.
- **Снимок ячеек** (`JournalCells`): время самой новой нарисованной страницы (стена), SOC, ток,
  пробег, 166 напряжений и 14 температур в порядке BMS (нет значения — пусто; сырой 0 датчика —
  −40 °C, как пришёл), номера BMS с единицы первых минимальной и максимальной ячейки и датчика (сырой
  0 датчика крайним не бывает), разброс, `fullCharge` — SOC ≥ 95 % в момент снимка.
- **Где и сколько.** `filesDir/diagnostics/journal/`: `scans.jsonl` и `cells.jsonl`, запись — строка
  JSON. Запись дописывается и синхронизируется (`JournalFile.append`); строку, обрезанную выключением
  питания, чтение пропускает, а следующая запись начинается с новой строки, так что обрезанная стоит
  только себя. Предел — 500 сканов и 200 снимков: полный скан — около 14 КБ (68 блоков меньше 200 байт
  и их записи), 500 — около 7 МБ, несколько явных сканов в день на полгода и больше при окне экранов
  30 дней; снимок — около 1,3 КБ. Файл, переросший предел на десятую часть или бюджет 16 МиБ / 1 МиБ,
  переписывается целиком новейшими записями через временный файл и переименование
  (`JournalFile.replace`): обрыв оставляет прежний файл. Сессия читает журнал один раз за процесс
  рядом с работой (автоскан его не ждёт), пишет на рабочем потоке по одной записи.
- **Что выводится** (`JournalFacts`, чистые функции):
  - жизнь записи (адрес + код как напечатан, `JournalCodeLife`): впервые (время, пробег), последний
    раз, все сканы с ней, «в N сканах из M» — из сканов с первого, прочитавших память блока целиком,
    «новая» — нет в предыдущем чтении того же блока (у первого чтения блока в журнале новых нет); ушедшие
    — были в предыдущем чтении блока, нет в этом (`gone`);
  - сравнение двух сканов (`compare`, по умолчанию — с предыдущим полным): новые, ушедшие, без изменений
    (со сменой байта статуса), «не прочитаны» — код есть в одном, а блок в другом не прочитан, это ни
    новое, ни ушедшее; смена `F194` / `F195` по блокам; дельты величин;
  - обновления ПО во времени (`softwareEvents`): изменения истории кодов ([5.5](#diag-arch-software)) со
    временем первого скана того дня с новым кодом, и смены `F194`/`F195` между соседними чтениями блока,
    которых история не знает;
  - «обычно» (`usual`): p10–p90 за 30 дней при ≥ 5 значениях, линейно между рангами; ряды по дням за
    30 дней (`daily`, медиана дня, день без значений — пусто); величины — `JournalQuantity`: 12 В, SOC,
    SOH, разброс ячеек в покое (по GET BMS на конец скана), изоляция двух каналов, датчики, пробег,
    медиана ответа, разброс снимков и разброс при полном заряде (снимки `fullCharge`);
  - слабейшая ячейка (`weakestCell`): чаще всех минимальная по снимкам («№ 9 · 7 из 9 снимков», при
    равенстве — меньший номер); последний снимок при полном заряде (`lastFullCharge`).
- **В коде:** `scan/Journal.kt` (типы, `JournalData`, `JournalStore`, `FileJournalStore`,
  `MemoryJournalStore`, `JournalJson`, `JournalLimits`), `scan/JournalEntries.kt` (записи из результатов
  блоков, показаний и `PackCells`), `scan/JournalFacts.kt`; `DiagnosticsSession` — параметр
  `journalStore`, `journal: StateFlow<JournalData>`, `saveCells()`. Тесты — `JournalStoreTest`
  (записи из байтов автоскана 2026-10-20 19:31, строки туда и обратно, обрезанный хвост, пределы,
  порядок), `JournalFactsTest`, `JournalSessionTest`. Экранов журнала нет; на машине не запускался.

  v1 (`diagnostics.*`) удалены вместе с ним; полноширинные системные доски v3 (`scanner-scan`,
  `-topology`, `-bms`, `-drives`, `-hv`, `-brakes`, `-adas`) — 2026-10-20 вечером, их сменили
  `scanner-sys-*`.
- Язык — диагноста: DTC, PID, NRC, маска, биты статуса, «запрос → ответ».
  Состояния названы словами: «не читали», «нет ответа», «нет адреса». Никаких
  выдуманных расшифровок кодов BYD.
- Без оговорок и дисклеймеров (решение владельца 2026-10-20): на экране только
  данные и названия. Нет сносок о происхождении имён, «только чтение»,
  «пример», «не проверено», пояснительных абзацев и знака `≈` у имён (поле
  `inferred` в каталоге остаётся для кода и документов). Ограничение, без
  которого данные читаются неверно, выражается видом — «—», разрыв графика,
  цвет, подсветка общего значения, — а не фразой. Источник описаний кодов из
  каталога мануала — одна строка в футере экрана кодов. Правда об ограничениях
  живёт здесь и в [находках](vehicle-data-findings.md#diagnostics-and-dtc-2026-10-18).

### 7.1 Как экраны устроены (в коде с 2026-10-20)

- Пакет `feature/diagnostics/ui/`. Вход — `DiagnosticsScreen(model, actions, onClose)`;
  навигация внутри раздела — `ScannerRoute`: автоскан («Список» / «Топология»), система с
  вкладкой (`SystemTab`), блок по адресу с вкладкой. Стек «назад» — `ScannerStack`: колонка
  делает его `[Автоскан]` или `[Автоскан, система]`, блок кладётся сверху, «Назад» и «‹ …»
  снимают его — в систему и на ту вкладку, откуда его открыли; крестик и «Назад» на автоскане —
  `onClose`. Пока экран блока открыт, раздел зовёт `setModuleOpen`; пока впереди «Потоковые
  данные» блока — `setLiveVisible`. Строка потока с ключом кладёт сверху страницу параметра
  (`ScannerRoute.Param`, [6.2](#diag-arch-param)), «Назад» и «‹ Потоковые данные» снимают её. Как
  устроены колонка и страницы систем — 7.2.
- Вкладки блока: с OBD — «DTC и готовность», «Потоковые данные», «Идентификация»;
  без — «Ошибки DTC», «Идентификация». Экран DTC выбирается данными: OBD без записей —
  списки Mode 03/07/0A и UDS, плашка PID 01, мониторы; OBD с записями — коды, четыре
  счёта по сервисам, мониторы; UDS с записями — коды с битами статуса матрицей и
  разбор байта статуса выбранной строки; UDS без записей — что запрошено и биты маски
  `09` (доска `scanner-esp-dtc`). Экран блока — во всю ширину окна, без колонки. Блок, которого
  нет в `modules`, открывается из строки автоскана: маршрут, протокол, память «не читали».
  ~~Системные экраны «ВВБ», «Электропривод», «Ассистенты», «Тормозная система»,
  «Высоковольтная система» (`SystemScreens.kt`)~~ — удалены 2026-10-20 вечером, их содержимое —
  вкладки систем (7.2).
- Числа — `ScannerSpec`, держится против `scanner.json` тестом `ScannerSpecContractTest`
  (цвета, все стили текста, геометрия каждого экрана, колонка, машина сверху, выноски и схемы,
  раскладка топологии). Параметры топологии (колонки, плитка, шаг, разбиение группы) — только
  там. Слова, которые экран выводит сам (чипы статусов, разбор байта статуса, фильтр «Только с
  DTC», строка автоскана, «снимок …», метки колонки, подпись PID-битмапов, легенда только для
  видимых видов плиток), —
  `ScannerWords`, тест `ScannerWordsTest`.
- Слово стоит в строке своего стиля: базовая линия там, где её ставит `scanner.js`;
  ряды слов (крошки, вкладки, переходы к группам, футер, бейджи) раскладываются по
  недокруглённым ширинам с межбуквенным интервалом последней буквы, который Android
  на конце строки не считает; «→» рисуется линией по базовой линии разложенного текста.
- Отладка: `ScannerFixtures` (debug) строит `DiagnosticsModel` из сцен `scanner-*` — колонку
  и страницы систем из `scanner-sys-*`, блоки из досок блоков — и открывает раздел стеком
  доски (у `scanner-esp-dtc` это «Шасси» под блоком); `LuminoforFixtureActivity` рисует на ней

  2026-10-20 вечером на `emulator-5580` (2560 × 1600, 320 dpi): 0,65–2,15 % пикселей, средняя
  разница 0,40–1,36 уровня; экраны блоков 0,83–1,71 %. 2026-10-21, после ролей блоков: 0,61–2,15 %,
  средняя разница 0,38–1,33 уровня. Позже 2026-10-21, с «Ячейками», ключом ВВ-схемы и четырьмя
  строками батареи: все 31 доска `scanner-*` 0,61–2,15 %, «Ячейки» 1,15 и 1,13 % (`-partial`; это v1 — v2 с опорой, линией обхода и паузой на эмуляторе не сверялась), ВВ 1,20,
  «Потоковые данные» батареи 1,70 (прежняя таблица; поток 2026-10-21 с доской `compare.py` не сверялся). Остаток — растеризация глифов (у Chrome
  на досках чернил на ~15 % больше, чем у Android на тех же шрифтах): больше всего у топологии

  двенадцать полноширинных досок сходились на 1,25–1,94 %.
- Описание кода (`DtcRow.description`): в таблице кодов блока — до двух строк в колонке
  «Описание» вместо группы кода, остаток второй строки обрезается; в строке неисправности
  ДВС — заголовок, переносится, под ним тип отказа. Источник (`DtcView.source`) — первая
  заметка футера. Перенос по пробелам один на доске и на экране (`twoLines()` /
  `ScannerWords.twoLines`); путь с описанием в таблице кодов сверен на временной сцене
  (1,47 %), постоянной доски с ним нет — у `747` нет раздела в каталоге.
- Топология — девять колонок (у колонки систем — по 112 dp, плитки 100 × 36) с шагом 40 по
  вертикали, в колонку входит девять плиток. С 2026-10-21 группы 9 / 9 / 7 / 19 / 19 / 4 / 1:
  «Силовая», «Шасси», «Ассистенты» — по колонке; «Кузов» и «Салон» — по три (9 / 9 / 1),
  «Климат» под хвостом кузова, «12 В» под хвостом салона; группы «Назначение не установлено»
  больше нет. ~~«Кузов» продолжается во второй колонке над «12 В», «Назначение не установлено» —
  в трёх (9 / 8 / 8)~~ — раскладка до 2026-10-21. Тест `ScannerSpecContractTest` проверяет, что
  каждая колонка помещается над футером, а последняя — в ширину области.
  Колонка-продолжение висит на предыдущей, магистраль доходит до последней колонки,
  открывающей группу. Состояние плитки — её вид; вместо адреса слово стоит, только где
  вид его не скажет: «ИСТ n», «АКТ n», сбои опроса (`ScannerWords.tileState`).
- Кнопка футера шириной в недокруглённую ширину подписи с отступом только слева: с
  отступом и справа подпись не помещалась на долю пикселя и обрезалась на всех экранах.
- Модели пока не хватает (экран обходится без или выводит сам): сырого ответа памяти
  ошибок (`59 01 …` на плашке маски), шкалы графика потока (`LiveRow` без диапазона —
  экран масштабирует по своим 60 с), тона «список» у значения поля идентификации, времени

- Кнопки без досок: «Выбор PID» (панель до четырёх PID), «Запись» / «Стоп записи»,
  «Продолжить опрос» и «Опрос… N/M» на автоскане, выделение кода для разбора статуса.

### 7.2 Раздел вокруг систем (решение владельца 2026-10-20)

Раздел строится вокруг систем машины, как сервисный режим Tesla: системы колонкой слева,
одна система — одна вкладка, первым — «Автоскан» всех блоков. Доски — `scanner-sys-*` в
Люминофоре (`scanner.js`: `rail`, `shell`, `sys*`; данные стоянки 2026-10-20); контракт —
`DiagnosticsModel.rail`, `systemPages`, `Scheme` в `scan/DiagnosticsModel.kt`.

- **Колонка** (`rail`, 216 dp): «Автоскан» с меткой «68/68», черта, затем системы в порядке
  `CarSystem`. Метка системы — только коды её блоков: «АКТ n» (оранжевым), иначе «ИСТ n»,
  иначе ничего; «OK» не пишется. Колонка стоит от шапки до футера; содержимое справа
  шириной 1000 dp (с полями 24).
- **Системы и их блоки** (запрос; блок может стоять в двух системах и считается в обеих):

  | `CarSystem` | Блоки | Вкладки |

  | `CHASSIS` | ESP/IPB 782, BSCM 7E5, EPS 783, RWS-L 582, RWS-R 796, IDC 597 | Состояние, Потоковые данные (с 2026-10-21), DTC, Блоки |

- **Голова системы** — как у блока: название, «· …» (`aside`), моно-строка (`line`),
  счётчики справа (`counters`). **DTC** системы — одна таблица на все её блоки: блок с
  адресом на первой своей строке, черта между блоками, код, тип отказа, описание (каталог,
  иначе группа кода), статус числом и словом; строка открывает блок. **Блоки** — строки
  автоскана.
- **Состояние — мнемосхемы** (`Scheme`), значения из `autoservice` (`DiagnosticExtras`,
  хаб) и памяти блоков; нет значения — «н/д», не ноль:
  - `Hv` — ВВ-схема `systems.hv` в раскладке колонки (`hvRail`), без подписей машин.
  - `Pack` — батарея с зарядом заливкой, полюса к шине (U, I), изоляция двух каналов на
    корпус с нормой, шкалы ячеек (3 000…3 700 мВ) и температур модулей (−20…60 °C).
    **Изоляция (2026-10-21).** Оба канала (`1039·43A00018`, `1039·26200010`) — целое 0…60000:
    штатный сборщик GB/T 32960 берёт то же поле и обрезает его на 60000
    (`research/vehicle-diagnostics/insulation-consumer-20261021.json`), а выше — недействительные
    коды прошивки, `FFFE` и `FFFF` в их числе. До правки диапазон был 0…65534, и `FFFE` выходил
    «65,5 МОм» и проходил норму. Теперь код выше 60000 — «н/д» (схема, ВВ-схема, таблица
    «Потоковых данных»), никогда не 60000 и не судится (~~без «OK»/«ВНЕ НОРМЫ»~~ — с 2026-10-21 в таблице
    нет колонки оценки, вне нормы — оранжевое значение). Единица — кОм: это
    ближайшая известная (единица поля GB/T 32960, которое штатный сборщик наполняет из этого
    FID), на этой машине не доказана; решение владельца 2026-10-21 — оставить кОм и норму
    500 Ом/В от напряжения ВВБ. Число ячеек (`1001·43A00008`) и датчиков (`1039·43A00010`) —
    1…253: 254 и 255 — недействительные счёты прошивки
    (`battery-validity-followup-20261021.json`), «н/д». Показание таблицы батареи, которого нет,
    пишется «н/д», как строки состояний, а не «—».
  - `Drives` — машина сверху: ДВС, генератор и передний мотор на передней оси, два задних
    мотора, VCU и PDC-VCU в центре; значения моторов выносками. Задний левый — SMCU 744,
    задний правый — SMCU3 745 ([роли по каталогу модели, 2026-10-21](vehicle-data-findings.md#ecu-roles-and-reverse-catalog-crosswalk-2026-10-21)):
    выноска называет и сторону, и блок («ЗАДНИЙ ЛЕВЫЙ · SMCU 744»).
    Состояние трёх приводов (`1023/2D0001D1`, `2D0001D5`, `2D0001D7`) в выноски не взято:
    штатный сборщик отчёта переводит сырые 0/1/2/3 в коды GB/T 32960 3/1/2/4, но смысл
    сырых значений не проверен (на стоянке 2026-10-20 все три — 3), а разбор прошивки сам
    называет их перечислением провода без значения
    ([vehicle-data-findings.md](vehicle-data-findings.md#consumer-semantics-and-remaining-tests-2026-10-21)).
    Взять можно после чтения в пяти состояниях машины: выключена, ON, Ready, тяга, рекуперация.
    **Состояние генерации (2026-10-21).** Выноска мотора-генератора кончается строкой
    «энергосистема: …» — состояние генерации энергосистемы `1006·34F0000A` (хаб,
    `VehicleSignal.GENERATION_STATE`, холодный опрос) словами штатного `BYDAutoEnergyDevice`:
    1 «генерирует», 2 «завершено», 3 «ошибка»; 0 — штатный INVALID, а не «выключено», он, любой
    другой код и отсутствие показания — «н/д»
    (`research/vehicle-diagnostics/isg-source-boundary-20261021.json`). Это слово энергосистемы,
    а не собственное состояние ISG 7E6: привязки поля к блоку нет, поэтому строка называет
    энергосистему. Доска `scanner-sys-drives` — как на стоянке, «энергосистема: н/д».
  - `Engine` — воздушный тракт: впуск (IAT), дроссель (TPS), коллектор (MAP), блок (RPM,
    LOAD, УОЗ, ОЖ; снизу коррекции и петля), катализатор (CATT B1S1), датчик O2 (B1S2).
    Значения — из потока ECM: пока «Состояние» двигателя на экране, поток идёт, как на
    «Потоковых данных» (`setLiveVisible(0x7E0, …)`).
  - `Chassis` — машина сверху: давление и температура каждой шины у своего колеса, ESP/IPB
    в носу, EPS на передней оси, BSCM над левой передней шиной ~~пунктиром к ESP/IPB~~.
    > **Superseded 2026-10-21:** BSCM `7E5` стоит отдельно, без линии к ESP/IPB `782`: общей
    > аппаратной или программной идентичности у них не найдено, связь не доказана
    > ([роли блоков](vehicle-data-findings.md#ecu-roles-and-reverse-catalog-crosswalk-2026-10-21),
    > [тормоза и VCU по OBD](vehicle-data-findings.md#brake-and-vcu-obd-data-2026-10-21); `64bd2536`,
    > `01bcea25`). Плитки на прежних местах; доска `scanner-sys-chassis` и `ChassisScheme`
    > (`SchemeScreens.kt`) изменены вместе. На машине не запускался.
  - `Body` — машина сверху: двери на бортах (закрыта — голубым, открыта — оранжевым),
    выноски дверей (положение, замок, окно), фары, LA_BCM и R_ZCU по бортам, F_ZCU и
    B_ZCU внутри, UWB-ключ в центре с четырьмя антеннами по углам.
  - `Adas` — машина сверху: поле обзора каждого радара клином, плитки датчиков выносками,
    ADC в центре, IPA сзади.
  - `Climate` — улица → климат-контроль → салон (температура, PM2.5); TMIM над блоком,
    PTC под ним, датчик качества воздуха AQDM у салона.
  - `Safety` — машина сверху: SRS в центре, электронатяжители ремней у передних сидений
    (MSRZ — водитель слева, MSRF — пассажир справа), радар присутствия детей CPD сзади.
  - Добавки 2026-10-21: у `Chassis` — подруливание RWS-L/RWS-R у задних колёс и IDC
    (подвеска, положение кузова) в центре; у `Body` — радары дверей SDR у своих дверей,
    приёмник радиоключа HFRM, бесключевой доступ SEC, правый NFC R-NCM, проекция двери
    багажника PDCMB.
  - `Lv` — шина DC → DC-DC (DCOBC) → линия 12 В с напряжением, АКБ (LBMS) под ней, зоны
    кузова на линии.
  - **Показания схем (2026-10-21, шаг 2b).** Показания выборки

    прочитан; в голове справа «ТРЕВОГ» — число поднятых, оранжевым, когда оно не ноль; ничего не

- `Drives` — PDC-VCU слева от машины на уровне VCU, пунктир к нему; задние выноски «ЗАДНИЙ
  ЛЕВЫЙ · SMCU 744» и «ЗАДНИЙ ПРАВЫЙ · SMCU3 745», подписи между задними моторами нет.
- `Hv` — задние инверторы «Инвертор задний левый/правый»; четыре блока на шине шире прочих
  (168 dp, `hvRail.units` с третьим числом), чтобы название не обрезалось; задние машины
  нарисованы как работающие, без пунктира.
- `Chassis` — RWS-L и RWS-R под плашками задних шин, выноска к заднему колесу; IDC в центре.
- `Body` — плашки дверей и плитки фар и доменов у краёв области (24 dp); в промежутке между
  плашкой и машиной — радар своей двери (передние над выноской двери, задние под ней) и справа
  у средней стойки NFC R-NCM; в центре столбиком HFRM, UWB-ключ, SEC; PDCMB справа у кормы,
  выноска к закруглению заднего угла.
- `Climate` — AQDM под зоной салона на ножке, как PTC и TMIM у блока.
- `Safety` — SRS в центре, MSRZ слева и MSRF справа у средних стоек (между передней и задней
  дверью), CPD сзади внутри машины; футер — ~~«Прочитать DTC»~~ с 2026-10-21 «Обновить» и «снимок …»: на схеме
  места и ремни (см. «Показания схем»).
Сверка 2026-10-21 (до показаний схем; доски кузова, шасси, привода, ВВ, 12 В и безопасности с тех пор изменены и
не сверялись): схемы 0,61–1,19 % (безопасность 0,61, шасси 0,80, кузов 1,06, привод 1,02,
ВВ 1,19, климат 0,68), автоскан 1,83, топология 2,15, DTC кузова 2,06, «Блоки» кузова 1,77,
сравнения 1,48 и 1,59.

<a id="diag-arch-v4"></a>
### 7.3 Прибор для диагноста: концепт v4 (решения владельца 2026-10-23)

Раздел перестраивается по странице «Концепт для диагноста (v4)» холста «Диагностика · инженерное
меню» (<https://claude.ai/artifact/KKgyNjETKzx6kxxbzMZBim>), одобренной владельцем 2026-10-23 с
правками ниже. Сканер живёт в машине и отвечает на три вопроса диагноста: что не так, с каких пор,
чем доказать. Норма молчит, светится отклонение. Доски `scanner-*` переносят страницу в Люминофор,
экраны идут за досками (порядок — 7.1).

**Решения владельца 2026-10-23.**
1. Опрос — только по явному действию: открыли раздел (автоскан), «Опросить снова», «Прочитать
   снова», «Снять ячейки сейчас». Фонового опроса, опроса по стоянке или по концу зарядки нет.
   Журнал копит именно эти сканы и снимки ([6.4](#diag-arch-journal)).
2. Читать больше: память — маской `0D` (сейчас, ожидающий, подтверждённый) там, где блок это
   сообщает; снимки `19 03` / `19 04` и расширенные данные `19 06` у открытого кода; у OBD-блоков
   стоп-кадр Mode `02` и результаты тестов Mode `06`. Всё это чтения; на машине они
   квалифицируются приёмкой с владельцем.
3. Читать VIN: `22 F190` и OBD `09 02`.
4. Отчёт без QR: «Сохранить» кладёт его в «Загрузки» — PDF для людей и JSON сырых ответов.

**Что меняется на экранах.**
- Колонка: «Сводка», «Блоки», одиннадцать систем, «Журнал». Метка пункта — число записей и знак
  вида: ● активный (красный), ◌ ожидающий, ○ в истории (оранжевые). «68/68» не пишется, пока
  ответили все.
- «Сводка» — вход раздела: вердикт («Активных неисправностей нет»), строка скана, контрольные
  величины (12 В, изоляция, Δ ячеек, SOH; вне нормы — оранжевые), все записи последнего скана по
  системам и блокам с датой первого прочтения, «N блоков без записей».
- «Блоки» — таблица всех блоков: сначала с записями, затем без; F194, медиана ответа, фильтры
  «Все / С записями / Без ответа / ПО изменено». Вкладка «Топология» снимается: плитки по системам
  повторяли список. Карта появится снова, когда станут известны шины CAN.
- Экран кода: смысл (каталог мануала; у общих кодов SAE — заголовок того же кода из любого раздела
  каталога), блок-адресат кода потери связи и его состояние сейчас, байт статуса в порядке 7 → 0 с
  «·» на битах вне доступности, «как прочитан» (запрос и ответ, запись выделена), тот же тип отказа
  в других блоках, хронология по журналу, стоп-кадр (`19 04` / Mode `02`) и счётчики (`19 06`) —
  сырьём там, где расшифровки нет.
- «Тяговая батарея · Здоровье» — первая вкладка: таблица «сейчас · опора · 30 дней» (SOH, разброс
  ячеек в покое, разброс при полном заряде — по снимкам «Снять ячейки сейчас» при SOC ≥ 95 %,
  слабейшая ячейка по снимкам, изоляция двух каналов, температуры, флаги GB/T 32960, записи BMS),
  ячейки от среднего и датчики. Опора двух видов: норма («≥ 0,28») и «обычно» этой машины
  (p10–p90 журнала за 30 дней, от пяти значений).
- «Потоковые данные» получают режим «Графики»: до четырёх сигналов на общей оси времени, курсор
  читает все сразу, полоса нормы, «Метка», «Запись».
- Схемы систем — тёмная кабина: без «OK · DTC 0» и синих рамок у исправного, значения белые,
  выключенное приглушено, отклонение оранжевое; на ВВ-схеме — разность напряжений шины к ВВБ.
- «Журнал»: хронология сканов, обновлений ПО и снимков ячеек, жизнь каждого кода с первого
  прочтения, величины по сканам; сравнение двух сканов — новые и ушедшие коды, ПО, величины.
- «Отчёт»: что войдёт (коды, блоки и F194, батарея, двигатель, сырые ответы, запись потока) и
  «Сохранить в Загрузки».
- Шапка: машина · пробег · P · 12 В · медиана обмена · время.
- Правила элементов: цвет — это смысл (красный — сейчас; оранжевый — было или вне нормы; белый —
  значение; серый — подпись; синий — касание и живое); «OK», «ответил», «готов» цветом не пишутся;
  одна величина — одна единица (изоляция в МОм везде); шкала мини-графика не уже нормы или
  разрешения × 20; счётчик в шапке появляется, только когда есть что сказать.

## 8. Безопасность и соседи по каналу

  службы.

  сказать владельцу, не повторять.
