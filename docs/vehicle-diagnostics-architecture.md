# Диагностика автомобиля: архитектура

Раздел «Сервис → Диагностика»: автоскан блоков машины, их память ошибок,
потоковые данные OBD, идентификация и системные экраны (высоковольтная часть,
ВВБ, привод, тормоза, ассистенты). Только чтение. Документ владеет устройством
раздела: транспортом до блоков, белым списком запросов, каталогом блоков,
движком опроса, моделью экранов и порядком приёмки. Факты о машине — что
отвечает, коды, прогоны — остаются в
[vehicle-data-findings.md](vehicle-data-findings.md#diagnostics-and-dtc-2026-10-18).
Вид экранов — холст «Диагностика · инженерное меню», страница «Сканер (v3)»,
одобрен владельцем 2026-10-20: <https://claude.ai/artifact/KKgyNjETKzx6kxxbzMZBim>.

Решение владельца 2026-10-20: раздел — строка в «Сервисе», без своего значка в
лаунчере и без отдельного APK. Отдельный APK не может: диагностике нужен shell,
а новая ADB-идентичность на этой машине не получает окна разрешения
([adb-authorization-recovery.md](adb-authorization-recovery.md#the-prompt-is-never-drawn-on-this-car-live-2026-08-29)).

## 1. Что такое раздел

«Сервис» → строка «Диагностика» → полноэкранная страница. Назад — в «Сервис».
Строка существует только в сборке `-Pdiagnostics` (`BuildConfig.DIAGNOSTICS`,
`ServicePanel`), пока владелец не примет раздел на машине; флаг снимает он.

Экраны — по одобренной странице «Сканер (v3)»:
- **Автоскан** — две вкладки: «Список» (блоки по системам, адрес, протокол,
  DTC активные и в истории, статус) и «Топология» (те же блоки плитками в
  колонках по системам). Сверху итог: ответило, DTC активных, в истории,
  память прочитана, MIL.
- **Блок** — вкладки «Ошибки DTC» (коды, тип отказа, биты статуса матрицей,
  что запрошено и какой маской), «Идентификация» (что ответил блок и что знает
  кэш обновлений), для OBD-блоков ещё «Готовность» (мониторы) и «Потоковые
  данные» (PID таблицей: значение, мин/макс, норма, график 60 с).
- **Системы** — «Высоковольтная система» (мнемосхема), «ВВБ», «Электропривод»,
  «Тормозная система» (ESP/IPB `782` и OBD-интерфейс `7E5`), «Ассистенты»
  (семь блоков рядом).

Раздел заменяет окно v1 целиком: `VehicleDiagnosticsWindow`, `DiagnosticRenderer`,
`DiagnosticFrame*`, `DiagnosticReadQueue`, `VehicleDiagnostics`, `VehicleDtcProxyMain`,
`DtcProtocol`, доски `main-diagnostics*`. Показания из `autoservice`
(`DiagnosticSignals`, `DiagnosticExtras`) переходят в раздел как источник
системных экранов.

<a id="diag-arch-transport"></a>
## 3. Транспорт

<a id="diag-arch-wire"></a>
### 3.1 Провод (доказан)

- `BYDAutoMqttDevice` (устройство 1033) из shell UID: `set(int[]{0xAA00010A},
  BYDAutoEventValue)` с `bufferDataValue` = запрос; ответы — слушатель на
  `0x9900010A` (`onDataEventChanged` или `onDataChanged`).
- Запрос: `0A`, адрес запроса big-endian (2 байта), длина UDS (1 байт), UDS.
- Ответ: `0A`, адрес ответа (= запрос + 8), длина фрагмента, число кадров,
  номер кадра с 1. В первом кадре — результат шлюза (`1` ответ, `2`
  отрицательный ответ, `3` нет ответа, `4` таймаут диагностики, `5` занят), и
  данные с байта 7; в следующих — с байта 6.
- Буфер приходит длиннее объявленного (240 байт с мусором в хвосте): читаем
  ровно объявленную длину. Одинаковый кадр может прийти дважды — второй
  отбрасываем.
- Многокадровая сборка: число кадров одно на весь ответ, номера подряд, иначе
  ответ битый. Все ответы исследований были однокадровыми.

<a id="diag-arch-resident"></a>
### 3.2 Резидентный помощник

Один процесс shell UID на открытый раздел, а не процесс на запрос, как у v1.
Причина — цена: у v1 одно чтение стоит ≈14 с (2 с тишины + окно 12 с), автоскан
43 блоков по три запроса занял бы полчаса, потоковые данные невозможны.

- `DiagnosticBusMain.java` запускается через `LocalAdbClient.ResidentSession`
  так же, как помощник поворотников (`AdbTurnSignalEventChannel`): стейджер
  кладёт jar по SHA-256, команда `exec app_process ... serve <nonce> <пауза мс>`.
  Jar — `diagnostic-bus.jar`, на машине `denza-diag-bus-<sha256>.jar`
  (`ShellProxyJar.DIAGNOSTIC_BUS`); в jar входят `DiagnosticBusMain.java`,
  `DiagnosticWhitelist.java`, `DiagnosticFrameAssembler.java` и общий
  `ShellProxyBootstrap.java` (`ShellProxyJarAssetsTest` держит список против
  классов, которые помощник называет). Из APK помощник не грузится никогда: не
  положился jar — раздел без канала.
- Старт: UID 2000; общий замок `/data/local/tmp/denza-dtc-read.lock` берётся
  на всю жизнь процесса (исключает исследовательские пробники, второго себя и
  читателя ADS); проверка стоянки; регистрация слушателя; **2 с тишины** — любой
  кадр в это время значит, что канал занят кем-то ещё; затем `READY`. Старт,
  который не удался, тоже кончается `READY` — см. «Отказ старта» в
  [3.3](#diag-arch-protocol).
- Процесс умирает вместе с потоком ADB (EOF на stdin), по `quit` и сам — после
  **60 с без запросов**. Приложение откроет его снова при следующем запросе;
  своему помощнику оно доверяет 50 с после последнего обмена, чтобы не попасть в
  его уход.

<a id="diag-arch-protocol"></a>
### 3.3 Построчный протокол

Запросы (одна строка — один обмен, по одному за раз):

```
x <seq> <адрес 3 hex> <uds hex> <таймаут мс>     например: x 17 7E0 190109 4000
quit
```

Ответ — между `DENZA_SERVE_<nonce>:BEGIN` и `…:END ok` / `…:END err <КОД> <пояснение>`:

```
a <seq> <кадров> <мс> <нс> <uds hex>   полный ответ блока, положительный или 7F
n <seq> <результат> <мс> <нс>          3, 4 — нет ответа; 5 — шлюз занят; T — таймаут помощника
```

Время в каждом ответе — измерение, а не допущение: по нему строится график
потоковых данных с честными промежутками и меряется шаг автоскана (шаг 2
приёмки). `мс` — от вызова `set()` до последнего кадра ответа, а для `n` — до
кадра с результатом шлюза или до своего таймаута. `нс` — момент этого кадра на
машине, `SystemClock.elapsedRealtimeNanos`, снятый в слушателе до перехода на
main Looper. В приложении это `DiagReply.latencyMs` и `DiagReply.receivedNanos`.

Пауза между обменами — параметр запуска, `serve <nonce> <пауза мс>`, от 0 до
500, по умолчанию 100 (`ResidentDiagnosticBus(gapMs)`): на приёмке её подбирают
без пересборки.

Перед **каждым** запросом помощник проверяет: белый список, профиль 170
(`persist.sys.AutoType`), P (`autoservice` 5, 1011, `89129008` = 1), скорость 0
(`autoservice` 7, 1013, `-1807745016`), менеджер диагностики в покое
(`sys.diagmgrsrv.task_bk = r@-1_0&w@-1_0`), не меньше паузы (по умолчанию
**100 мс**) от конца прошлого обмена. Таймаут запроса — от 1 до 6000 мс, обычный
4000. Ответ `7F <sid> 78` (блок просит подождать) не закрывает запрос: ждём до
таймаута.

Сборка ответа — `DiagnosticFrameAssembler` (чистая Java, в jar помощника):
- до первого запроса любой кадр чужой;
- кадр, который уже был в этом обмене, отбрасывается (сравнивается только
  объявленная длина);
- между обменами и в следующем обмене безвредны только отголоски прошлого: кадры
  с адреса прошлого ответа. Если два запроса подряд идут к одному блоку (`19 01`,
  затем `19 02`), первый кадр с ответом не на ту службу — запоздалый ответ на
  прошлую и тоже отбрасывается; от блока, которого в прошлом обмене не было, это
  `FRAME_SHAPE`;
- на один обмен не больше 64 буферов, считая дубли и «подождите».

Ошибки сеанса — `END err`:

| Код | Когда | Помощник после | Приложение |
|---|---|---|---|
| `REFUSED` | запрос вне белого списка или битая строка | живёт | `Refused` |
| `GUARD_PROFILE`, `GUARD_PARK`, `GUARD_SPEED` | не тот профиль, не P, скорость не 0 | живёт, запрос не отправлен | `NotParked` |
| `MANAGER_BUSY` | менеджер диагностики занят | выходит | `ChannelBusy` |
| `FOREIGN_TRAFFIC` | кадр не к текущему запросу (чужой тестер, сток) | выходит | `ChannelBusy` |
| `LOCK_BUSY` | замок держит другой читатель (только на старте) | выходит | `ChannelBusy` |
| `FRAME_SHAPE` | кадр не по форме, разрыв нумерации, больше 16 кадров или 4095 байт | выходит | `ChannelLost` |
| `TRANSPORT_REJECTED` | `set` вернул не 0 | выходит | `ChannelLost` |
| `HELPER_FAILED` | нет `autoservice`, класс устройства, исключение, `onError` слушателя, зависший main Looper | выходит | `ChannelLost` |
| `WRONG_UID` | помощник запущен не как shell | выходит | `Refused` |

`LocalAdbClient.ResidentSession.request` закрывает поток на любом `END err`,
поэтому со стороны приложения сеанс кончается после каждой ошибки, и в том числе
после «живёт»: следующий обмен откроет нового помощника. «Живёт» значимо для
хостового инструмента, который говорит с помощником напрямую. Код, которого
нет в таблице, приложение считает `Refused`; `DiagnosticBusLinesTest` сверяет
коды в исходнике помощника с таблицей.

**Отказ старта.** Помощник, который вышел до `READY`, виден приложению только как
закрытый поток — так «замок занят» и «не P» неотличимы от потерянного ADB. Поэтому
старт не выходит молча: отказ (`LOCK_BUSY`, `GUARD_*`, `MANAGER_BUSY`,
`HELPER_FAILED`, `WRONG_UID`) или кадр в окне тишины (`FOREIGN_TRAFFIC`) сначала
отпускает слушателя и замок, потом печатает `READY` (при кадре — сразу, не
дожидаясь конца двух секунд), а первая строка получает `END err <код>`, и процесс
выходит. Так же помощник поступает с чужим кадром между обменами: всё отпущено
сразу, причина — ответом на следующую строку. Без строки он уходит через 60 с.

<a id="diag-arch-whitelist"></a>
### 3.4 Белый список

`feature/diagnostics/bus/DiagnosticWhitelist.java` — одна правда для обеих
сторон: приложение проверяет запрос при создании (`DiagRequest`), помощник —
ещё раз перед шиной. `DiagnosticWhitelistTest` перечисляет разрешённое и
запрещённое.

| Разрешено | Зачем |
|---|---|
| адрес `700`–`7F7`, кроме функционального `7DF` и адресов ответов OBD `7E8`–`7EF` | физические запросы к одному блоку |
| `22 F194`, `22 F195`, `22 F18A`, `22 F197` | номер ПО поставщика, версия ПО, поставщик, имя системы |
| `19 01 <маска>`, `19 02 <маска>` | число и список DTC |
| OBD `01` + 1–6 PID | состояние, готовность, потоковые данные |
| OBD `03`, `07`, `0A` | сохранённые, ожидающие, постоянные коды |
| OBD `09 00`, `09 04`, `09 0A` | поддерживаемая информация, калибровка, имя блока |

Всё остальное отклоняется, в том числе сессии (`10`), сброс (`11`), очистка
(`14`, OBD `04`), доступ (`27`), управление связью (`28`), запись (`2E`, `3D`),
управление входами-выходами (`2F`, OBD `08`), процедуры (`31`), tester present
(`3E`), настройка DTC (`85`), VIN (`22 F190`, `09 02`). Длина UDS — не больше 7
байт (один кадр CAN).

### 3.5 Сторона приложения

`bus/DiagnosticBus.kt` — интерфейс и типы:
- `DiagRequest(address, uds, timeoutMs)` — создаётся только из разрешённого.
- `DiagReply`: `Answer` (полный ответ, положительный или `7F`, с `nrc`),
  `NoReply` (шлюз сказал 3/4 или помощник не дождался), `GatewayBusy` (5); у
  каждого `latencyMs` и `receivedNanos` из [3.3](#diag-arch-protocol).
- `DiagFailure` — сеанс, а не блок: `NoAccess` (нет доверенного ADB),
  `NotParked`, `ChannelBusy` (замок, менеджер, чужой трафик), `ChannelLost`,
  `Refused` (ошибка программы).
- `ResidentDiagnosticBus` — реализация на стейджере и `ResidentSession`; один
  обмен за раз (`Mutex`); открывает помощника лениво; после `ChannelLost` —
  одна попытка открыть заново и послать тот же запрос (все запросы — чтения,
  повтор ничего не меняет), после `ChannelBusy` — ничего, пока пользователь
  не нажмёт «Опросить снова». Политика «ничего» — у движка: шина сама не
  повторяет, а следующий вызов `exchange` снова откроет помощника. Отменённый
  обмен и `close()` закрывают поток сразу — закрытие сокета прерывает чтение.
  `AuthorizationRequiredException` → `NoAccess`.
- `FakeDiagnosticBus` (тестовые исходники `bus/`) отвечает по сценарию на
  запрос (`on(0x7E0, "190109").answer(...)`, шаги по порядку, последний
  повторяется; незаданный адрес — шлюз 3), ведёт журнал обменов, умеет
  `DiagFailure` шагом или `failNext`, и время по поддельным часам машины;
  байты — из `research/vehicle-diagnostics/*.json`.

<a id="diag-arch-codec"></a>
## 4. Протокол

Чистый Kotlin в `protocol/`, проверяется эталонами из исследований
(`obd-20261020.json`, `remaining-ecus-20261020.json`, `dtc-20261018.json`,
`lbms-dtc-20261018.json`, `dtc-reference-20261018.json`) и байтами трасс
`captures/diagnostics-obd-20261020/` и `captures/diagnostics-remaining-20261020/`,
переписанными в тесты (`DtcCodecTest`, `ObdCodecTest`, `DiagDecoderTest`).

- **Вход для движка** — `DiagDecoder`: функции берут `DiagReply.Answer` и
  возвращают `Decoded` (`Ok`, `Negative(nrc)`, `Malformed(why)`). Сначала
  проверяется, что это ответ на свой запрос: положительная служба = запрошенная
  + `40`, та же подфункция, DID, PID или тип информации; `7F` — ровно три байта и
  про запрошенную службу. Иначе `Malformed`. `Polled.of(reply, decoder)` даёт
  чтение с качеством данных.
- **Память ошибок.** `59 01`: маска доступности, формат, число. `59 02`:
  маска доступности и записи по 4 байта. Число и список обязаны совпасть,
  маска доступности в обоих ответах одна, биты статуса записи — внутри неё,
  коды — без повторов, `19 02` той же маски и того же блока; иначе ответ
  «несогласованный», а не «0 кодов». Число 0 — память полная и пустая без
  `19 02`; ненулевое число без списка — не память. Запись, чей статус не
  попадает в маску запроса (блок маску не применил), не выбрасывается и ответ
  несогласованным не делает: запись показывается, а у памяти пометка «блок
  отдал записи вне маски» — спрятать запись на диагностическом экране хуже, чем
  показать лишнюю (решение 2026-10-20; в движке).
- **Формат кода.** `00` — SAE J2012: буква P/C/B/U, четыре знака и тип отказа
  (`C1170-09`). `01` (ISO 14229-1, у ADS `712`, а также у FMCU `7E3` и ISG `7E6`)
  — шесть hex-знаков без буквы: его нельзя читать как P/C/B/U. Остальные
  форматы — сырые байты. Имена типа отказа — общие SAE J2012-DA (`FailureTypes`),
  с пометкой источника; значения базовых кодов BYD не выдумываются.
- **Расшифровка кода BYD** появится на экране только из квалифицированного
  словаря: документ с ревизией, применимостью к варианту блока и его ПО (`F194`),
  сопоставлением показа и сырого кода (для формата `01` — обязательно), страницей
  источника. Строка показывает источник рядом с текстом. Публичные оглавления
  мануала Z9GT PHEV (2026-10-20: ~500 кодов ДВС, 206 BMS, по 31–32 на привод) —
  только кандидаты: в них есть коды с двумя разными заголовками, нет привязки к
  ПО, стороны задних приводов не связаны с SMCU/SMCU3
  ([находки](vehicle-data-findings.md#oem-dtc-manual-candidates-2026-10-20)). До
  словаря — «Расшифровка BYD недоступна» и общий тип отказа.
- **Биты статуса** — восемь независимых флагов ISO 14229-1 (TF, TFTOC, PDTC,
  CDTC, TNCSLC, TFSLC, TNCTOC, WIR); «подтверждённый» не значит «активный».
  Бит вне маски доступности — «не поддержан», а не «нет».
- **Идентификация.** `F194`, `F195` — hex; `F18A`, `F197` — ASCII без хвостовых
  пробелов, `00` и `FF`; ASCII, который не печатается, остаётся hex.
- **NRC** — имена ISO 14229-1 (`10`, `11`, `12`, `13`, `14`, `21`, `22`, `31`,
  `33`, `35`, `36`, `37`, `78`, `7E`, `7F`) и русская подпись; неизвестный —
  номером. `11`, `12`, `31`, `7E`, `7F` — «не поддерживается», остальные —
  «отказано». `78` последним словом обмена — «нет ответа»: окончательный ответ
  так и не пришёл.
- **OBD.** PID по SAE J1979 для всех 46 PID, которые перечисляет ECM (42
  значения и битовые карты `20/40/60/80`); незнакомый PID — сырые байты.
  Ответ на несколько PID делится по длинам из таблицы; незнакомый PID посреди
  такого ответа — `Malformed`; PID, которые блок не прислал, — отдельный список
  (не поддерживает). PID `01` — MIL, число кодов, тип зажигания по биту B3 и
  готовность мониторов: искровой набор C0–C7 = катализатор, подогрев
  катализатора, EVAP, вторичный воздух, GPF (C4/D4, раньше «кондиционер» или
  резерв), датчики O2, их подогрев, EGR/VVT; дизельный — свой. `41` — мониторы
  этой поездки, первый байт резервный, «не включён» = «отключён в этой
  поездке». Режимы `03`/`07`/`0A` — коды J2012 по два байта, первый байт —
  число, длина обязана совпасть. `09 00` — карта, `09 04` — CALID по 16 байт
  ASCII, `09 0A` — имя блока, 20 байт ASCII.
- **Качество данных** (`DataQuality`) — отдельно от состояния машины: не опрошен,
  нет ответа, шлюз занят, отказано (NRC), не поддерживается, несогласованный
  ответ, устарело (прочитанное старше заданного срока), прочитано, полный ответ
  без кодов. Только последнее (`provesNone`) даёт «ошибок нет», и только для
  маски или режима, которые спрашивали.

## 5. Каталог блоков

`ecu/EcuCatalog.kt` — все 46 адресов страницы «Сканер (v3)»: адрес запроса

карте), группа (силовая, шасси,
ассистенты, кузов, салон, климат, 12 В, назначение не установлено), сокращение

выведена из сокращения, основание имени (`F194`, маршрут стока, OBD `09 0A`,
нет маршрута), ожидаемый `F194` или имя `09 0A`, алиасы с версиями ПО и железа
из кэша обновлений, понимает ли блок UDS и OBD, квалифицирована ли память ошибок
живым чтением (19 блоков, включая OBD-интерфейс тормозов `7E5`), отвечает ли
`19 01` (`dtcCountAnswers`: нет только у DCOBC), формат DTC из живого `59 01`,

имена у обоих одинаковые, различает сокращение. У блоков без установленной роли короткое имя —
«ПО <версия из кэша>». `741` — само головное устройство, его MCU («Салон»,
`Media`): маршрутная карта стока называет `741/749` `Media_BYD_00200001`, а
`media_softcode_mapping.json` из ProductLineOTA ставит вернувшийся `F194`
`4B450011E0930034E2` модулем `mcu` у ПО мультимедиа «denza», чей общий код
`4B450011E093003401` и лежит в кэше обновлений. Ворота сверяют `F194` с кодом
MCU, не с общим.

Алиасы и версии: из `remaining-ecus-20261020.json` для 33 адресов, ответивших на
`F194` в этом прогоне; для `7E2`, `7E3`, `7E6`, `7E7`, SMCU и SMCU3 — из
`ecu-inventory-cache-20261018.json` по совпадению кода ПО; у DCOBC — из полного
кэша (`captures/diagnostics-discovery-20261018/`), в research его версий нет.
У кузовных блоков с именем по маршруту алиас — `ecuId` маршрутной карты без
версий: `F194` не читали, и версия из кэша была бы чужой.

`EcuCatalogContractTest` держит каталог против `research/vehicle-diagnostics/*.json`:
46 записей, все с маршрутом, 19 с квалифицированной памятью; каждый адрес,
вернувший `F194`, есть, и коды совпадают; нет адреса, который ни разу не
ответил; алиасы и версии — те же, что в кэше; формат DTC — тот, что блок
сообщил; OBD — там, где ответила карта PID; кузовные алиасы есть в маршрутной
карте на том же адресе; каждое чтение каталога проходит `DiagnosticWhitelist`.

### 5.1 Ворота идентичности

Где каталог знает `F194`, автоскан сначала читает его. Не совпал — блок
«другой», память ошибок не читаем: маршрут или прошивка поменялись, и имя на
экране было бы ложью. У `720`, `722`, `726`, `747`, `762` `F194` не читали,
их имя — из маршрутов стока; у `7E5` — из OBD `09 0A`.

<a id="diag-arch-masks"></a>
### 5.2 Маски

Память ошибок — `19 01 09`, затем `19 02 09`, если число больше нуля. Маска `09`
= отказ сейчас или подтверждён, это включает исторические (статус `28`).
Ожидающие для OBD-блоков — режим `07`. Маска `FF` не используется: у ECM она дала
258 записей непроверенных мониторов. `19 01 04` у `7E0` и `7E2` не ответил за
4 с — не используется.

Блок, чей `19 01` не отвечает (DCOBC: шлюз говорит «нет ответа»), читается одним
`19 02 09` (`DiagDecoder.dtcMemoryFromList`). `59 02` не несёт формата, поэтому
его коды остаются сырыми шестью hex-знаками, пока формат не известен по живому
`59 01`, — никогда не SAE по аналогии.

<a id="diag-arch-candidates"></a>
### 5.3 Кандидаты заводской карты

Полная заводская карта (`research/vehicle-diagnostics/factory-ecu-map-20261020.json`,
225 записей сервера — варианты, а не установленные блоки) даёт 86 маршрутов. 44 из
них — блоки каталога (кроме OBD-интерфейса `7E5` и ADC, которого карта ведёт по
DoIP, а ответил он по CAN `712`), 37 CAN-маршрутов и 5 DoIP — нет: RWS-L/R, AQDM, PLR/PLL,
R-NCM, ERP, IDC, VR, CPD-радары, четыре SDR, DPAC1/2, задние и боковые фонари
(RL/TL), MCPA, ASSY, RCP, WCM_RM, INFC, BWA, FRL, RMCU, ETC, HUD, пять UWB; по
Ethernet — CDC SoC/FPGA, три лидара, ADC.

Продукт их не опрашивает. Каталог держит только то, что ответило на этой
машине (`EcuCatalogContractTest`), а сервер перечисляет все варианты модели.
25 из 37 CAN-кандидатов сидят на адресах `5xx`, вне белого списка `700`–`7F7`;
DoIP транспорт не умеет вовсе (конверт MQTT не выбирает шину). Путь в каталог —
одно чтение `22 F194` по этому списку исследовательским прогоном с владельцем:
ответившие с кодом из кэша попадают в каталог, а белый список расширяется до
конкретных `5xx`, а не диапазоном.

<a id="diag-arch-engine"></a>
## 6. Движок опроса

`scan/DiagnosticsSession` живёт, пока раздел открыт (старт и стоп по жизненному
циклу страницы), и публикует `DiagnosticsModel` (`StateFlow`).

В коде: `DiagnosticsSession` (очередь, остановки, публикация), `ModuleProcedure` и
`ModuleResult` (чтение блока и его итог), `IdentProcedure` (открытый блок),
`LiveStream` (поток), `ModelBuilder` и `SystemsBuilder` (модель экранов),
`ScanStore`/`FileScanStore`, `CsvStreamSinks`, `CarFeed`; фабрика главного
процесса — `DiagnosticsSession.of(context)` (`DiagnosticsSessions`). Тесты —
`DiagnosticsSessionTest`, `LiveStreamTest`, `ScanStoreTest` на `FakeDiagnosticBus`
со сценарием «машина сейчас» из байтов `research/vehicle-diagnostics/` (`CarNow`).

- **Работы:** автоскан, чтение одного блока (кнопка), идентификация открытого
  блока, поток OBD. Очередь с приоритетами: кнопка пользователя > идентификация >
  шаг автоскана > поток. Один обмен за раз. Единица работы — целый блок для
  первых трёх и один обмен для потока, поэтому автоскан уступает между блоками и
  никогда внутри блока. Пока видна вкладка потока, автоскан стоит; кнопка и
  идентификация идут.
- **Автоскан по блоку:** ворота (`22 F194`, у `7E5` — `09 0A`, у кузовных по
  маршруту стока — нет) → `19 01 09` → `19 02 09`, только если число > 0 (у DCOBC —
  сразу `19 02 09`, [5.2](#diag-arch-masks)); для OBD-блоков (`7E0`, `7E2`, `7E5`)
  ещё `01 01`, `03`, `07`, `0A`. Ворота не прошли (другой `F194`, нет ответа,
  отказ) — больше ничего не спрашиваем. Порядок — `EcuCatalog.routed`, ECM первым.
  Итог блока (`ModuleResult`) выводится только из его ответов: «нет ответа» —
  блок не ответил ничем; «DTC не читали» — ответил на ворота, память не прочитана;
  «другой блок»; «отказ» (NRC на чтение памяти); «несогласованный ответ»;
  иначе OK, «история» (подтверждённые без testFailed) или «активные» (testFailed
  или MIL). Записи вне маски запроса показываются, у памяти — `outsideMask`.
  Для OBD-блока без UDS память — Mode 03.
- **Цена полного автоскана** на «машине сейчас»: 100 обменов — 41 ворота
  (40 `F194` и `09 0A`), 44 `19 01`, 3 `19 02` (DCOBC, `720`, `747`), 12 OBD.
  При паузе 100 мс и задержке 100–200 мс это 20–30 с, плюс ≈3 с на старт
  помощника; блок, который не отвечает, стоит до 4 с своего таймаута.
- **Когда стартует:** при открытии раздела, если прошлому скану больше 10 минут
  или его нет; иначе показан прошлый, в полосе — «Показан скан 16:31, 5 мин
  назад», кнопка «Опросить снова».
- **Остановки** — без повторов по кругу:
  - `NotParked` — пауза, вверху «Только на стоянке: P и 0 км/ч». Работа
    продолжается сама, когда общий `VehicleTelemetryHub` (не канал диагностики)
    снова видит P и 0 км/ч, или по «Опросить снова». Если хаб уже видел P и
    0 км/ч, когда помощник отказал, сначала хаб должен увидеть выход из P: так
    расхождение двух проверок стоит одного отказанного обмена, а не цикла.
  - Перед каждым обменом движок смотрит на хаб: машина вне P или едет — пауза
    без запроса. Любой `END err` закрывает поток ADB, и следующий обмен поднимает
    нового помощника (≈3 с), поэтому то, что точно получит отказ, не посылается.
  - `ChannelBusy` — стоп до «Опросить снова», вверху «Канал занят штатной
    диагностикой или другим читателем»; `ChannelLost` (шина уже раз переоткрыла
    помощника), `NoAccess`, `Refused` — тоже стоп до кнопки.
- **Хранение:** последний скан — `filesDir/diagnostics/last-scan.json`: время,
  по каждому блоку итог словами и сырые байты каждого обмена (запрос, ответ или
  результат шлюза, мс, время на машине). Читаются обратно только байты, итог
  выводится заново тем же `ModuleResult`; файл, который не разбирается или
  содержит запрос вне белого списка, — не скан. Сохраняется по завершении
  автоскана и после кнопки «Прочитать DTC» у законченного скана.
- **Открытый блок** (`setModuleOpen`): один раз `22 F194/F195/F18A/F197` у
  UDS-блока; у OBD-блока карты PID `01 00/20/40/60`, пока карта указывает на
  следующую, `01 1C`, `01 01`, `01 41`; у OBD-блока без UDS (`7E5`) — `09 0A`,
  `09 04`.
- **Поток OBD** — [6.1](#diag-arch-stream).
- **Показания `autoservice`** для системных экранов: общий `VehicleTelemetryHub`
  под `VehicleWatcher.DIAGNOSTICS` (значения держатся по своему сроку) и пакет
  GET `DiagnosticExtras` каждые 5 с через один постоянный shell со сроком 15 с.
  Пакет расширен сигналами приводов и изоляции, которые ответили в сводном
  опросе каталога 2026-10-20 (IGBT задних, обороты, момент, ток, второй канал
  изоляции, число датчиков, контактор). Задние сигналы autoservice названы
  сторонами, а какой мотор у SMCU, какой у SMCU3, не установлено: в «Электроприводе»
  колонки подписаны сокращениями, сторона сигнала — отдельной строкой с `≈`.

<a id="diag-arch-stream"></a>
### 6.1 Поток данных

Поток должен быть ровным и честным: по нему диагностируют, значит частота,
задержка и пропуски видны, а не угаданы.

- **Что известно.** Исследовательский пробник прочитал 16 ответов за 13,2 с,
  из которых 2 с — тишина на старте и 8 с — его же паузы по 0,5 с: на обмен с
  запуском процесса пришлось ≲200 мс. Отдельно задержка обмена не измерялась. Шлюз
  отвечает «нет ответа» по своему таймеру быстро — пустой адрес поток не тормозит.
- **Откуда скорость.** Один резидентный помощник (нет запуска процесса на
  запрос); пока открыта вкладка, поток — единственная работа шины, автоскан
  стоит; пауза между обменами — параметр запуска помощника, начальное значение
  100 мс, на приёмке подбирается наименьшее без «нет ответа» и «занят» за 2 минуты.
- **Упаковка запросов.** Несколько PID в одном `01` так, чтобы ответ
  помещался в один кадр CAN (`41` и до 6 байт данных; каждый PID стоит свой байт
  плюс длину значения из таблицы протокола: например, `01 0C 0D` — обороты и
  скорость, или три однобайтовых PID). Раскладка — первая подходящая по порядку
  таблицы. PID, который один не влезает в кадр (`7A`, семь байт), в поток не
  входит; карты PID, `01`, `41`, `1C`, `13` читаются один раз с идентификацией.
  Пакет, на который блок ответил отказом или битым ответом, дальше
  спрашивается по одному PID. Многокадровые ответы `01` с шестью PID — только
  после того, как приёмка покажет, что шлюз их собирает быстро.
- **Режим фокуса.** «Выбор PID» на вкладке: до 4 параметров, которые
  нужны сейчас (обороты, коррекции, датчик кислорода): весь круг фокуса, затем
  один пакет таблицы, и снова — фокус идёт через обмен, это самая высокая частота
  на график. Без фокуса таблица идёт по кругу. Порядок таблицы — как на доске
  «Потоковые данные», затем остальные PID по номеру.
- **Время у каждого значения.** Помощник ставит на ответ время прихода
  (`elapsedRealtimeNanos`) и длительность обмена; график строится по этим
  временам, пропуск («нет ответа», PID, который блок не прислал) рисуется
  разрывом, значения не интерполируются; кольцо — 60 с. В шапке вкладки —
  измеренная частота и задержка («4,6 Гц · 120 мс»), а не заданная: частота —
  самого частого PID за последние 10 с по временам машины, задержка — средняя
  за последние 20 обменов. Мин/макс — с открытия вкладки или кнопки сброса.
- **Норма** — только где она известна: ОЖ 80…105 °C (выход — только перегрев:
  прогрев не отказ), коррекции ±10 %, напряжение ЭБУ 13,2…14,8 В, датчик O2
  после катализатора 0,1…0,9 В (судим только при работающем ДВС), давление во
  впуске «ХХ 25…45» — подпись без суждения: холостой ход движок не отличает.
- **Быстрые сигналы машины.** Восемь «горячих» показаний `VehicleTelemetryHub`
  — обороты, работа ДВС, генерация, мощность и напряжение батареи, скорость, P,
  одометр — уже идут каждые 100 мс без запросов к блокам; на вкладке ДВС они
  показываются после PID с источником «autoservice · 100 мс», одна точка на
  новый проход хаба (у строки отрицательный `pid`).
- **Запись.** «Запись» на вкладке пишет поток в
  `filesDir/diagnostics/stream-<время>.csv` (`received_ns,address,pid,raw,value`):
  время прихода, адрес, PID, сырые байты, значение; разрыв — строка без байтов
  и значения; быстрые сигналы — с адресом `autoservice` — для разбора после
  поездки так же, как `captures/vehicle-log/`.
- **Ожидание.** До измерения — оценка: 4–8 обменов в секунду, то есть фокус из
  двух-трёх PID ≈4–8 Гц, таблица из 13 PID ≈1–2 Гц. Если меньше — сначала пауза
  и упаковка, потом решение владельца.

<a id="diag-arch-screens"></a>
## 7. Экраны

- `DiagnosticsModel` — неизменяемый снимок для экранов: шапка (связь, P,
  скорость, ДВС, время), итог автоскана, блоки по группам с состоянием, деталь
  выбранного блока (DTC, идентификация, готовность, поток), системы со сроком
  годности каждого значения.
- Compose-раскладка (строки, сетки, прокрутка), а не холст с зонами нажатия, как
  у v1. Порядок работы по `CLAUDE.md`: сначала доски, затем экраны; экран готов,
  когда `compare.py` сводит его снимок с доской до сглаживания. Доски —
  `tools/design-canvas/luminofor/scanner.*`, двенадцать `scanner-*` (страница
  «Сканер (v3)», перенесённая в рисовальщик Люминофора; что исправлено при
  переносе — в README Люминофора, «The scanner»); `diagnostics.*` — доски окна v1.
- Язык — диагноста: DTC, PID, NRC, маска, биты статуса, «запрос → ответ». Имя по
  сокращению — со знаком `≈`. Состояния названы словами: «не читали», «нет
  ответа», «нет адреса». Никаких выдуманных расшифровок кодов BYD.

<a id="diag-arch-safety"></a>
## 8. Безопасность и соседи по каналу

- Только чтение — белым списком на обеих сторонах; тест перечисляет запрещённые
  службы.
- Замок `denza-dtc-read.lock` общий с исследовательскими пробниками и читателем ADS.
- Сток: свойство менеджера, 2 с тишины на старте, выход при чужом кадре.
- Проверка стоянки — перед каждым запросом в помощнике, не только при старте.
- Падение `com.byd.avc` — тревога по `CLAUDE.md`: снять `logcat -b crash -v time`,
  сказать владельцу, не повторять.
- Пробники остаются в `research/` и `tools/`; продукт их не импортирует.

## 10. Порядок работ

шаг собирался сам.
